    Automation and external tools¶

    Licensing — Free, with paid parts. Hooks, your editor, your terminal and your file manager are free. Sequences of your own are custom-actions and the workflow recipes are git-flow. What a licence adds

    Four things that are about running something: sequences of the app's own verbs, git-flow as editable recipes, the hooks git would run, and your editor, terminal and file manager.

    Named sequences¶

    "Check out main, pull, check out prod, pull, rebase onto main, check out main" — six things somebody types every week, under a name, run with one press.

    A step is a verb this app already has, and never a command line¶

    That is the decision the whole feature is shaped by, and three things follow:

    1. Every refusal is a controller's own — a dirty working tree, a diverged history, a branch that does not exist — in the words you would have seen pressing the button.
    2. Nothing new can execute. This grows no way to run a program, unlike the custom command, whose whole subject is running one.
    3. The editor offers a real list rather than asking you to remember git's spelling.

    What is given up is everything git can do that this app has no verb for, and the honest answer to that is the vocabulary getting longer one verb at a time rather than a text field that runs whatever is in it.

    The vocabulary is published, with each verb's fields, so the editor draws a drop-down and then the arguments for whatever was picked. A verb the list does not hold is dropped on load and on save, so a hand-edited file naming rm -rf gets a step dropped rather than a sequence that runs it.

    It stops, and says which step and why¶

    The interesting question is not what happens when a sequence works. It stops where it stopped: the refusal is reported with its position — "step 3 of 6, check out prod" — the log holds the steps that did run, and nothing after the failure is attempted.

    There is no "continue on failure", per step or otherwise, because a sequence that carried on past a refused checkout would do the rest of its work on the wrong branch.

    A merge or a rebase that stopped is not a step that ran. Both report success for a conflicted result — the index is written and the Conflicts surface finishes it — and that is a state for somebody to settle rather than something to run four more writes on top of.

    A clean stop is different, and getting that wrong made --no-ff unusable: this app's merge also stops on a clean normal merge, waiting to be committed. "A merge that stopped is not a step that ran" was right about conflicts and was applied to every stop, so a --no-ff step — the whole of what git-flow is — reported "stopped on conflicts" every time. A conflicted stop still ends the sequence in the same words; a clean stop is a merge waiting to be committed, and the step after it commits one.

    Placeholders¶

    Resolved
    %current-branch Per step, as it runs
    %default-branch Per step
    %starting-branch Once, when the run starts
    %<your-key> From what you type when you press Run

    Per step is the point: a sequence moves HEAD, so "check out main, pull, check out %current-branch" would otherwise come back to where it began.

    %starting-branch is the exception that proves it, and is what makes a finish sequence possible at all: "check out the trunk, merge the branch I was on, delete it" cannot be written with %current-branch, because after the first step that is the trunk — so the second would merge it into itself and the third would delete it.

    A sequence can ask for one value, which is the smallest thing that makes "start a feature called X" writable: without it a sequence can only ever do fixed things, and a branch name baked into a recipe is a recipe for one branch. It is not a widening of the rule above — what arrives is a value landing in a field a verb already had. A missing value is refused before the first step rather than resolving to an empty string: half of feature/ is a branch nobody meant to make, and a sequence that found out on step three would have moved HEAD twice already.

    Global, and kept in JSON¶

    Not per repository: that sequence is the same errand in every checkout you have. It is JSON beside the settings rather than in them, written through on every edit, and nothing recorded can carry a credential — a step is a verb id and arguments that are refs, remotes and messages.

    Three routes¶

    • Manage → Actions makes and edits them, beside the list.
    • Actions ▾ on the top bar runs one from wherever you are, saying which step it is on.
    • Each sequence is its own palette entry under its own name, because a name is how one is found and a single "Run an action…" entry would put the thing you typed three letters of one level further away.

    Sequences that ask for a value are left out of the palette route rather than offered and refused: the palette is built in the shell, which has no field to type a branch name into, so the entry could only ever run with nothing.

    Workflow recipes¶

    git-flow's six errands as ordinary sequences — feature, release and hotfix, start and finish.

    There is no git-flow controller. A workflow is an opinion, and one held in a controller is one the app imposes — on branch names it guessed, in an order it chose, with no way for anybody to disagree. Adding a recipe makes an ordinary sequence instead: it lands in the same file as everything else, renamable, editable, deletable, and adaptable the first time somebody's trunk is not called what this app assumed.

    How to use one¶

    1. On Manage → Actions, open Add a recipe and pick one.
    2. It lands as an ordinary editable action: rename it, reorder the steps, change a branch name. Nothing about it is special afterwards.
    3. Run it from Actions ▾, from anywhere.

    The trunk is %default-branch so a recipe travels between repositories; develop is a literal, because it is git-flow's own name for a branch this app has no way to discover — and an editable copy is exactly what a project that calls it something else needs.

    Adding one twice makes two rather than refusing, unlike creating a sequence by name: a second copy to adapt is the ordinary reason to press it again.

    Hooks¶

    Manage → Hooks. A hook is an executable file in one directory with a name git looks for, and every refusal here follows from that: nothing about a hook is in a commit, in the index or in any reflog.

    Where the hooks are is a question, not a constant. core.hooksPath moves the directory, and a repository that sets it runs nothing from .git/hooks — so a list hard-coded to that path was confidently showing hooks that could not fire and hiding the ones that would. It is read first, and resolved against the working tree when relative.

    That is also what makes this right inside a linked worktree: hooks live in the common directory and a worktree's .git is a file, so the old reading reported "no hooks" — the one answer that is never true.

    The tab says whether the path came from config, because "these are the hooks" and "these are the hooks because config says so" are different things to be told, and it prints the resolved directory in full.

    The executable bit is what git looks at, so it is what "enabled" means. A file's presence, its name and its permissions are three separate facts and the list carries all three:

    • .sample is not a state — it is a different filename, one git never looks for, and the samples are what git init leaves behind. So a sample is something to install from.
    • An inactive hook is a real hook git will not run. The old list drew any file it found as installed, which is the worst way round: a pre-commit git silently skips looks exactly like one guarding every commit. The count line is "%1 of %2 run" rather than the list's length.

    One asymmetry in the write path is deliberate. A hook created here is made executable, because a file git will not run is not what somebody who has just written one meant by "save". An existing hook's bit is left exactly as it was: enabling is its own verb, and saving an edit to a hook you deliberately switched off must not switch it back on behind you.

    Nothing is read that cannot be edited. A hook may be a compiled program or a megabyte of generated shell, and a program loaded into a text editor is a program destroyed by the first save. The refusal names the file and its path, so it can be edited where it is — and the editor draws that sentence instead of the box, since an editor beside "this could not be read" is an invitation to press Save.

    An unknown name is listed but never created. A file in the directory is shown whatever it is called, marked "not a hook git runs", because it is there and hiding it would be the old column's fault in the other direction; it may be edited, too, since something put it there. Creating one is refused — a new file git will never look at is not a hook.

    Deleting is the one thing here that nothing can undo, so it asks, and the dialog offers switching it off instead — which is what most people asking to delete a hook actually want. Its Delete is deliberately not the primary. A sample is never deleted at all.

    On Windows, 'enabled' means the file is there

    NTFS has no executable bit, and Qt answers the question there from the file's extension — so a hook called pre-commit reads as not executable however it was written, and every row on a Windows checkout would have said "will not run" about hooks git runs perfectly well.

    Switching one off then has no mechanism and is refused by name rather than reporting success having changed nothing: renaming it is a name git does not look for, and deleting a hook to "disable" it would be a destructive act behind a reversible-sounding word. Switching one on is refused too, for the opposite reason: it is already true.

    Sharing a hook is not something this offers, and the editor says so: a hook is in no commit, so it is not pushed and nobody else gets it. Doing it means committing one somewhere and pointing core.hooksPath at that directory, which is a decision about a repository rather than a verb this app can perform.

    Your editor, terminal and file manager¶

    Open ▾, on the workspace bar and on every fleet card.

    It works before you have configured anything¶

    The first version gated every route on a command being set, which meant no button, no menu row and no palette entry out of the box — a feature whose only way in was a settings page you would visit if you already knew it was there.

    With nothing stored, the first of a small candidate list present on the PATH is taken. Discovered rather than shipped as a constant, because a default naming a program nobody has is worse than none — the button would be there and pressing it would say code could not be started — and the settings row says which one was found and that it was found rather than chosen.

    Every candidate takes a path as an ordinary argument, which is the whole test for being on the list: a terminal editor started detached with no terminal around it opens nothing and reports success.

    The extra directories a windowed process does not inherit are searched too — ~/.local/bin, /usr/local/bin, /snap/bin, Nix's profiles — because a Homebrew editor is invisible to an app launched from the Dock. Flatpak is out of reach and the code says so: its exports are named by application id, so matching them would mean a second list of app ids for the same programs.

    They are command templates, not program names¶

    code %1, wezterm start --cwd %1 — because the interesting cases here are all arguments: a new window, a folder opened as a workspace, a shell started somewhere. A field that took only a program would have to grow a second for its arguments and a third for their order.

    %1 may appear anywhere or not at all — a terminal that takes its directory from the one it was started in wants no placeholder — and the path is passed as the process's working directory either way.

    It is not a shell, and that ceiling is why a stored command is safe to run

    No pipes, no &&, no redirection, no substitution, no globbing. The settings file is a text file, and a template that reached a shell would be one line of somebody else's editing away from arbitrary execution the next time the app started.

    The path is substituted after the split, inside whichever argument holds it, so a folder called my repo, one with a quote in it, or one called --upload-pack=… is one argument and cannot become two. Anything that genuinely needs a shell goes in a script and the script is named here.

    A command naming a program that is not here is kept and reported. One can be installed tomorrow, and refusing to store the line would be this app deciding what may exist then — so the row prints what would run and that it would fail, and the failure names the program and the field to change rather than a bare "could not be started".

    One button, and the destinations are a list¶

    Editor, Terminal and Open remote were three buttons side by side on the bar and two more on every card — three controls for one question, each appearing and disappearing on its own as a command is set or a remote is added, so the strip changed width under the pointer.

    The rows are drawn from one file that both menus use, because two copies had already drifted three ways: the folder row existed on the bar's menu and not on the card's, the forge row read "Open remote" in one and "Open in GitHub" in the other with two palette wordings behind them, and the order differed.

    Every label is a whole verb — "Open in editor" rather than "Editor" — because the rows are read in two places and only one of them has a button saying "Open in…" above it.

    Showing the folder needs no setting at all: the desktop decides what opens a directory, so this app's part is one url. The label is the platform's proper noun — Finder, File Explorer, or "file manager" elsewhere — because a Mac reader looks for the first and finds nothing under the third. Three names and not two is what the Windows port cost that row: the ternary it replaced is the shape a two-platform project acquires everywhere, right up to the moment a third arrives and the else starts answering for a case nobody chose it for.

    Where the verbs are¶

    A file has no per-row button — a button per row is a palette entry per row, and the alphabet does not stretch to a file list — so it is a row of the Changes context menu and a button beside a commit's file on History.

    Two file lists deliberately do not carry it. A stash's file is a stashed version, so an editor there would open a different file from the one on screen; and a pull request's files are on somebody else's branch, which this checkout may well not have at all.

    A commit's file opens as it stands on disk, and the button says so — an editor takes a path, and a commit's copy of a file is an object with no path. Restore is how the commit's version is reached. A path that is not there is refused by name, because an editor handed one creates an empty file, and the commonest way to arrive at one is a row for a file some commit deleted.

    On Windows, a .cmd shim is refused rather than wrapped

    startDetached runs an executable image, and a .cmd or .bat is a file for the command interpreter — so it fails. That is not an edge: it is how VS Code and several others put themselves on PATH.

    The obvious repair is cmd /c, and it is refused: cmd re-parses what it is handed, so &, |, ^ and % in a path would stop being inert, and a folder called a & b is not exotic. This file's whole guarantee is that nothing it holds reaches a shell, and buying one platform's convenience with it would be the worst trade available.

    So discovery passes over a shim and falls through to the install directory where Code.exe is, and a typed one is refused by name with the .exe named as what to type instead.

    A command of your own¶

    A third template, and deliberately not a sequence step: that class's guarantee that every step is one of this app's own verbs is not being traded away for one feature. This is the other thing entirely — an arbitrary program, run once, handed three facts, whose failures are its own.
    %1 The repository
    %2 The branch
    %3 The picked paths, one argument each

    %3 is what makes it a second template rather than a longer first one: a list has to arrive as a list, so it must be an argument of its own and expands to as many as there are — to nothing at all with nothing picked, rather than to an empty string a program would read as an argument meaning "". An argument that merely contains %3 is refused by name, because --file=%3 means one thing with one path and nothing honest with three, and a command whose argument list changed shape with the size of a selection is one that does something different depending on how many rows were lit.

    Nothing is discovered here, unlike the two above: nobody can guess what somebody else wants to run. Empty means empty and every route is absent while it is.

    It is two settings, because the name is what the control is made of. A button reading "Run", a palette entry reading "Run" and a legend line reading "Run" say nothing about what would happen, and this is the one verb whose subject is a program nobody but its author knows anything about. A command with no name counts as unset.

    The button is on Changes' own header rather than the file menu: with nothing picked it is still a perfectly good thing to press — "run my script on this repository" is what most of these are — and a row reached by right-clicking a file would make an empty selection unreachable.
