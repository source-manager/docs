    History, graph and search¶

    Licensing — Free, with paid parts. The walk, the graph, the search, blame, file history and comparing two refs are free. A permalink is forge-links, the proposal and CI columns are forge, and bisecting from a commit is bisect. What a licence adds

    The graph on the left, a commit's message, files and diff on the right, and a search box that narrows the walk rather than the rows on screen.

    The surface opens where you are¶

    On your own branch's tip rather than at the top of the list, with that commit selected so its files and its diff are already on screen. The list positions there once, when it is first filled for this repository — doing it on every refresh would drag the view back after every staged hunk, and moving a list somebody is reading is worse than opening in the wrong place. Nothing is hidden by it: the newer rows are one scroll up.

    Lane 0 is the branch you are on¶

    Lanes used to be handed out in the order commits came off the walk, which is by time across every ref — so which branch got the leftmost column depended on who had pushed most recently, and your own branch wandered between columns from one refresh to the next. That is the one lane worth being able to find without reading it, because a graph is scanned down a column.

    A colour belongs to a lane, not to a column. When the colour was the column, a recycled column handed its colour to whatever branch took it next, so a thread you were following changed colour at the row where an unrelated branch ended — and the trunk's colour was whichever column it landed in, so "which branch does work land on", the one question a graph answers without a label being read, was answered differently from one refresh to the next.

    Colour nought is now reserved for the default branch and handed to nothing else, from the row where the trunk's tip is drawn and down: above that row those commits are the branch that is ahead of the trunk, and colouring them as the trunk claims the thing the graph is there to disprove.

    The ref chips wear that colour, so a branch's pill and the column its commits are drawn in are one thing rather than two — with the hue driving the ground and the border while the label stays the ordinary ink, because a lane colour is tuned to be a stroke on the window and asking it to be small text over a wash of itself is a second job it cannot do. A tag keeps its outline, so a tag and a branch at one commit are not the same object with only the name to tell them apart.

    Chips are drawn before the subject, in the same column. They spent a while as a column of their own after it, on the argument that the subject should start in the same place on every row — which is true and cost more than it bought: a chip at the end of a line whose subject had already elided into the gap sat inches from the commit it labels.

    Six search scopes¶

    Any field is the default and is the union of the rest — and it tries the cheap fields first, so a hit on message, author or hash costs nothing extra and skips the diff entirely. Only a commit none of them match is diffed, and paths and content are then checked off a single diff.

    Scope Matches
    Message subject and body
    Author name or address
    Hash full or abbreviated
    Path files the commit touched
    Content text on added or removed lines — git's log -G
    Issue a ticket id one of your link rules recognises, or the url it points at

    Content matches changed lines only, which is -G rather than -S: a commit that merely sits near the text did not change it.

    Every match says why it is in the list, when the reason is not already on screen — the body line, the path, the changed line. The row renders only a subject, so a match against the message body reads as a match against nothing without it.

    The search is batched and abandonable¶

    Doing it synchronously froze the window: on a 4000-commit repository with thousand-line files a content search blocks for ~2.3 s, and since changing the scope re-ran it, clicking through the chips meant six of those back to back.

    Each batch runs to a time budget rather than a commit count, because what a commit costs varies by orders of magnitude between comparing a field and diffing a large file. Measured, that holds the longest freeze at 11–14 ms on both a light and a heavy repository.

    Starting a search cancels whatever was running; Stop keeps what has already been found. It stops after 5000 commits and says so, since even responsive scanning has to end somewhere.

    The same question is answered once¶

    A refresh runs after every staged hunk, on every working-tree event, and whenever the window comes back to the foreground. Each of those used to re-run the whole walk — or the search — from the first commit, which is what people saw as the list flicking, and what threw away a search that had been running for several seconds.

    The walk is a pure function of the refs, HEAD and the narrowing, so an unchanged reading is an unchanged answer and there is nothing to do. Three skips follow:

    • A question already answered serves the list it has.
    • A question already being answered is left running.
    • A question you stopped is left stopped — pressing Stop is an instruction, and a refresh that changes nothing has no standing to overrule it.

    Search is its own verb for exactly that reason: after a Stop the query is unchanged, so pressing Search used to do nothing whatever.

    Filters, which compose with the search¶

    The scope sits against the search field with no gap, because "search the messages for X" is one question and it used to take reading a placeholder, finding the matching chip on a row of its own below, pressing it, and then typing.

    Three more are folded behind one chip that carries how many of them are in force. That count is not decoration and is the whole reason folding them is safe: a narrowing nobody can see is indistinguishable from a repository with nothing in it. The section also opens by itself whenever the count is above zero.

    • Author — name or address, anywhere in either. Not the same thing as the Author scope, which decides what the query is matched against and can only be one thing at a time; the filter is what makes "content search for foo, by kate" askable.
    • A period — two dates, typed or picked. The committer's time is what is compared, because that is what git log --since compares and what the row beside it draws; filtering on the author's date while printing the committer's would put a rebased commit outside a period its own row says it is inside.
    • Signature — any, signed, not signed, signed with a key. A filter rather than a seventh scope, because "does it carry a signature" is a fact about the commit and filing it among the scopes made it exclusive with searching the message — and left the commonest reading of it, "which of these did nobody sign", unaskable at all.

    Everything is filtered during the walk, so the ref filters, the query and these compose: narrowing to a branch narrows the search with it. That also means a period can make the walk cross a hundred thousand commits to reach a fortnight in 2019, which is exactly the shape that must be abandonable.

    Both the author and signer pickers are filled from what the walk scanned rather than from what it kept — built from the matches, narrowing to kate would leave kate as the only suggestion, so the field would stop suggesting the moment it was used.

    Nothing here is persisted: a period restored on launch hides most of the history behind a control nobody remembers setting.

    The empty state names which narrowing emptied the list — the author and both ends, with "anyone", "the first commit" and "today" standing in for the ends that are not bounded. "No matches" reads as a repository with nothing in it.

    The walk is batched too¶

    Unbounded, linear, and most of a second at thirty thousand commits — on the thread that draws. It is batched now, with one budget spent before returning, so almost every repository anybody opens is complete when the surface asks, with its graph in hand and no flicker through an empty list on the way to a full one. A large one has done exactly one budget's work and yielded.

    The lane pass is deliberately not batched: it needs the whole list, so running it per batch would be quadratic in the size of the history. The graph is drawn only once it is ready — a graph over a growing list would show connections to commits that are not on screen, which is why a filtered list draws no graph either.

    What a commit row says¶

    The subject, and up to five more columns you can switch off individually. Two of them are worth explaining:

    The proposal is a number the forge wrote into its own merge or squash subject, naming a page this window already draws — so pressing it goes to the Pull requests surface rather than out to a browser. A commit that landed by fast-forward or rebase carries no number anywhere, which is a blank rather than a guess (drawn as nothing rather than as a dash, which reads like a value), and where the subject cannot say, the forge is asked — a request per commit, spent lazily as rows scroll past, with a cap, and answered from the cache thereafter. A negative answer is stored too, because "this commit went through no proposal" is a real answer and the commonest one on a branch anybody pushes to directly.

    The ticket is somebody else's system, and opens there. A number in ordinary prose is deliberately not read as a proposal: #142 in a subject somebody typed is a ticket, and matching it as a proposal would put a link to the wrong system on half the rows.

    The column set is stored as the off list, because an enabled-list cannot tell "nobody has chosen" from "everything is switched off" — and a column added by a later build would be hidden by an enabled-list written before it existed, silently, on exactly the machines that have been running longest. The ticks live on the History page, where the width each column costs is in front of you.

    Rows are tight by default, and the roomier reading is a preference: a history is the one list somebody scans thousands of rows of looking for one, so how many fit on a screen is most of what makes that quick.

    A commit's contents¶

    Selecting a commit reads what it changed — the file list, then the one file being read — on demand, once per selection, because History is thousands of rows and none of it is worth knowing until a row is chosen.

    A commit is diffed against its first parent. For a merge that means the side it brought in, which is what git show prints and the only reading with a per-hunk shape; a root commit is diffed against the empty tree.

    The message sits above the file list in a fixed-width column, capped and scrollable rather than elided. It used to elide on the last line that fitted, which said there was more and offered no way to reach it: the one place in the app that draws a whole commit body could not be used to read one, and the message that happened to be cut is exactly the one worth reading — the one whose author had something to explain.

    The commit menu¶

    Right-click, or the ⋮. Reset, detach, restore a file, revert, cherry-pick, rebase onto this, bisect from here, reword, edit, a permalink, a patch, notes, "Explain this commit", "Changelog since this", and open on the forge.

    Blame¶

    Per-line, with the file's revision list beside it. A plain click picks the line and lights the commit that last touched it; ⇧-click extends the range and leaves the commit alone, because somebody selecting fourteen lines is not asking to relight the graph fourteen times.

    A blame survives a refresh. It used to be cleared outright, and the complaint that ended that was exact: open a file in Blame, click away to another application, come back, and the panel was empty. Nothing about the window regaining focus changes who last touched a line. What actually invalidates an annotation is HEAD moving, so that is what re-blames it — and it re-asks for the revision as it was asked for, because somebody who opened HEAD means "as it stands now" and re-blaming the sha HEAD was would pin the panel to a commit that has since been rewritten.

    File history¶

    "What happened to this file", which is the question next to Blame's and not the same one: blame says who last touched each line as the file stands now, and is therefore silent about a change that was later overwritten and about the day the file was moved.

    Reached from a file row's menu on Changes, or by name from the palette.

    The tracked path moves as the walk goes back, and that is why every row carries its own. Rename detection is paid for at the one step where a rename can be found, and from there down the file answers to its old name — so the row that moved it prints both names with an arrow between them, and the diff beside it says that a first-parent diff of the new path necessarily reads as an add. A list whose paths silently change halfway down reads as a bug in the list.

    Most commits are answered without a diff at all: the commit's blob id for the tracked path is compared against each parent's, and one that matches any of them is skipped. That is git's own history simplification, and it is why a merge that took one side's copy is absent — the commit on that side did the work and the walk reaches it anyway.

    An empty answer says which one it is: no repository, an unborn HEAD, a path nothing has ever held, a walk stopped at its limit, a walk cancelled. None of them is an error, because none of them is a failure, and rendering "the path is misspelt" the same way as "still going" is how a reader learns not to believe a surface.

    Where change has landed in a file¶

    A strip beside the file history, banded top to bottom, each band the count of commits whose diff touched that part of the file. It answers "does change cluster at the top, the middle or the end", which a list of commits cannot show.

    It is a proportion and never a line number

    Line 40 in a commit from 2019 is not line 40 today, and following a line forward through every subsequent change is what blame does at blame's price. So a hunk is banded against the length of the file as it stood in that commit, and the sentence under the strip is not optional — a strip drawn beside a list of commits is read as line numbers by everybody unless something says otherwise.

    The hunk ranges are free; the denominator is a blob read per commit, which is exactly the cost a batched walk exists to refuse. So the banding sits behind a control that prints the price, and it publishes once rather than as it goes: a distribution over the first tenth of a history is not "the distribution so far", it is a different number that would move under you. For the same reason cancelling keeps nothing.

    Comparing two refs¶

    The Compare surface, reached by name. It answers "what lies between these two", and its whole design follows from the fact that the question has two answers and they are routinely confused:

    • A..B diffs the two trees as they stand.
    • A...B diffs from the merge base of A and B to B.

    On a branch that is merely ahead they agree, which is why the confusion survives — the difference is invisible until the day it matters, and then it says a branch deleted a file it never touched.

    The label is the feature, and it is computed beside the trees that were actually diffed, so a label composed somewhere else cannot drift from what is on screen. A mislabelled diff is worse than no diff, because both readings render as something plausible and neither announces itself.

    Both commit lists are read in both readings: in two dots the left-only commits are the ones whose work shows up as removals; in three dots they are exactly what is being ignored. One list would have made the distinction invisible again at the one place somebody is trying to learn it.

    Three dots across histories that never met has nothing to diff from, so it is refused by name and points at the other reading — rendering an empty file list there would say "these two agree", which is the one conclusion somebody will act on and the opposite of the truth. Two dots is unaffected, and says so without it being an error.

    From the page you can write a patch in the reading on screen, or open a proposal with the left as the base and the right as the head.

    The reflog¶

    Every ref update git makes is journalled, and that journal is the only record of a commit nothing points at any more. It is therefore the answer to "I have just lost an hour of work", and the reason a hard reset is survivable at all.

    The claim other clients make here is false

    Tower sells "Undo everything", one keystroke, no qualifications. The reflog records refs, not files. A commit that left a branch is still in the object database and can be reached again; an uncommitted edit that reset --hard wrote over was never in an object at all. A button that cannot tell those apart is at its most confident exactly when it is most wrong, because it is pressed at the moment the work was destroyed.

    So the surface prints two sentences and never merges them — the commits come back, the working tree does not — and the verb is "Put HEAD back", not "Undo".

    The mode is always mixed and is not a parameter: soft would leave the index holding the tree of the commit you are walking away from, which reads as a pile of staged changes nobody asked for; hard would overwrite the working tree, which is the one thing no reflog can give back.

    An emptiness has three causes and they are not the same news — a ref with no history, a journal pruned to nothing, and reflogs being switched off in config. Only the third means there is no undo here and there will not be one later either.

    refs/stash has a reflog too, and so does every local branch. All of them are listed and any can be read, because the entry explaining where a branch went is in the branch's own log when the move was made from another worktree. Only HEAD's entries are restorable — moving somebody else's ref from a log viewer is a branch write.
