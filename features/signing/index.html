    Signing¶

    Licensing — Free. Signing and verifying, in all three formats. What a licence adds

    Three questions that look like one: what this repository would sign with, how a buffer actually gets signed, and whether a signature somebody else made is good.

    libgit2 cannot sign, and that decides everything else¶

    There is no signing call in the library. What it offers is the three-step dance its own header documents — build the commit's text without writing an object, have something else sign those bytes, then write the object with the signature in its header.

    The "something else" is a program, because that is what git does too: git has never held a signing implementation either, and gpg.program exists precisely so a user can name theirs.

    So this is the second thing in the app that shells out, and it keeps the subtree rules verbatim: arguments go as an argument list, never a command line and never a shell; no terminal prompt is allowed; and the program is asked rather than merely found, since one on the PATH that will not run leaves every control live and every press failing.

    Three formats, because gpg.format has three values¶

    gpg.format Program Note
    openpgp gpg -bsau <key> The default
    ssh ssh-keygen -Y sign -n git -f <key> - Needs no keyring at all, which is why the format exists
    x509 smimesign -bsau <key> Presents gpg's interface over S/MIME, so it takes the same arguments

    Shipping two and refusing the third would leave somebody whose employer mandates S/MIME with a client that reads their config, understands it, and declines — worse than one that never looked.

    x509 is implemented and unexercised

    No test here has run smimesign. What is pinned is that the format resolves to that program with those arguments.

    gpg's exit code is not the test, and that is git's own finding: gpg exits 0 having warned instead of signed — an expired key, a subkey with no signing capability — so success is asserted from SIG_CREATED on the status channel.

    A refusal, never an unsigned commit¶

    The one outcome this whole feature exists to prevent is a commit that was asked to be signed, was not, and said nothing.

    No program, a program that will not start, a key that will not load, a passphrase with no agent to supply it, a wait that expired — each is a named sentence and a write that did not happen. There is no fall-through, because a repository whose policy is "everything is signed" is one where an unsigned commit is worse than no commit.

    The plan and the write refuse in the same string, asserted by a test.

    Three different answers to "is this ready"¶

    Not an inconsistency:

    • Probing — "would this work at all", for the settings page — is asynchronous and lazy, because a blocking gpg --version at startup is a wait every session pays for a feature most never use.
    • Signing is synchronous and deliberately does not consult the probe: a commit cannot be half-made, the signature has to be in hand between two libgit2 calls, and the alternative is making every write path in the app asynchronous to buy a responsive window during an operation that normally takes milliseconds. What that costs is stated: while a passphrase prompt is up the window does not repaint, and if the two-minute wait expires nothing is written.
    • Verification is asynchronous, because nothing waits on it.

    The per-commit override, in one direction only¶

    A tick on Changes reading "commit without a signature, this once", absent unless commit.gpgsign is on.

    Skipping a signature is a decision about this commit — the key is not to hand, the machine is somebody else's — and it is the case people actually hit. Signing one commit in a repository that signs none is a decision about the repository, there being no key configured for the app to name, and the honest way to make it is commit.gpgsign, which every other git tool then reads too.

    It is keyed to config rather than to whether the program was found, for one reason: the probe answers a moment later, so a tick gated on it would appear under the pointer at the instant you were aiming at the commit button.

    A tag's signature is in its body¶

    Unlike a commit's, which goes in a header. libgit2 has no signing variant of its tag call, so a signed tag is the object's own header lines assembled by hand with the armour after the message.

    The printed command is -s rather than -S, which is git's own asymmetry: git tag -s is the signing verb and it replaces -a, a signed tag being annotated by construction.

    The replays sign, and git does not¶

    git cherry-pick and git rebase do not re-sign what they replay unless they are given -S. So a signed history quietly loses its signatures the moment anything is rebased onto a new base — every commit comes out unsigned, and nothing says so.

    This app follows commit.gpgsign in both replays instead. That is a departure from git, and the argument for it is that the replayed commit is a new object with a new committer: the signature on the original could not travel with it even in principle, since it signs bytes that include the parent and the committer. So the choice is not "keep the old signature or make a new one" — it is "make a new one or leave a gap", and a repository whose policy is that everything is signed wants the former.

    It covers all six sites, including the four folds and rewords, which had no signing variant and would otherwise have come out unsigned while the picks beside them were signed — the worst of the two outcomes, because a history that is mostly signed is one nobody audits.

    A signature that cannot be made stops the replay, in the signing layer's own sentence rather than a generic "could not commit <sha>": the cause is a key or a program, and naming the commit would hide it.

    Reading somebody else's signature¶

    Four verdicts, drawn as a mark on the commit row with a tooltip naming it:
    good Verified
    bad Cryptographically unsound
    unknown Sound, and the signer is not on any list this machine has
    unsigned There is no signature

    Plus four states about the reading rather than the signature: known, asking, spent (the per-list ceiling was reached), failed.

    unsigned is drawn rather than left blank, and that is the whole reason the column is legible. Drawing nothing for it is the obvious economy and exactly the mistake: a blank would mean both "there is no signature" and "nothing has looked yet", and the second is the ordinary state of every row that has just scrolled into view. So it is a faint hollow dot, and a genuinely blank square means only that this row has not been answered.

    It is asked per visible row¶

    Verifying is a subprocess per commit and a history is thousands of rows, so a row asks as it is drawn — the cost follows what you are looking at rather than how long the history is. Presence is free and settles most rows without a process starting, and an unsigned commit is deliberately not charged to the ceiling: spending it on the free answer would make a long unsigned history stop answering half way down for no reason you could see.

    Only one process runs at a time: a process per row all at once is a fork bomb with a scroll bar.

    Two answers that must not be wrong¶

    A missing allowed-signers file is unknown and never bad. The ssh verify verb answers "is this from somebody on the list", and with no list the answer is no — for every ssh signature, including every good one. Reported as bad that would be this app accusing a colleague of forgery because a file is missing. So the verdict is taken in two steps: is the signature cryptographically sound at all (which needs no list), and only then, is its signer allowed.

    The format is read from the signature and never from gpg.format. A repository that has moved from gpg to ssh holds both kinds, and asking gpg about an SSH signature produces "no valid OpenPGP data" — which drawn as bad would accuse somebody of forgery for having signed the older way. Config decides what is written; the armour on the object decides what is read.

    Searching for signed commits¶

    The history's signature filter — any, signed, not signed, signed with a key — matches presence and never validity, and the field says so where it is offered.

    Validity is a subprocess per commit inside a walk that is batched against a ten-millisecond budget precisely because it cannot be run again casually, so a filter that quietly meant "validly signed" would answer a question nobody asked at a price nobody agreed to.

    Signed with matches a key, and the field says that too. A person's name is not in a signature — gpg keeps it in the keyring and ssh in allowed_signers — so producing one means running the signing program per commit. What is in the bytes is the identity that can be read without one: an SHA256:… fingerprint for SSH, computed as ssh-keygen -lf computes it, and the 16-hex issuer key id for OpenPGP. An X.509 signature has a signer this cannot name and drops out rather than being guessed at.

    The settings page reads and never writes¶

    The four values are git's own, read by every other git tool on the machine, and a second set of fields here would be a quieter route to writing them with none of git's own per-repository / per-user / system-wide semantics around them.

    What the page does carry is the half you cannot see from your own config file: the program that was found, said to be found rather than chosen, and whether it would run. The allowed-signers row is absent off gpg.format = ssh, and says plainly when there is no file — because without it every ssh signature verifies as an unknown key, which is a different piece of news from a bad one and must never be drawn as one.
