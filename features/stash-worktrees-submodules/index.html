    Stash, worktrees, submodules, subtrees¶

    Licensing — Free, with paid parts. Create, apply, pop and drop a stash, and everything about worktrees, submodules and sparse checkout, are free. Rewriting a stash is stash-rewrite and subtrees are subtree. What a licence adds

    Four tabs on Manage, plus sparse checkout. Everything here is about something the repository holds beside its history.

    Stash¶

    Push, pop, apply, drop and branch, plus four verbs that are rare or unique.

    Stashing only what is staged¶

    git stash push --staged has no libgit2 equivalent — the library's stash always takes the whole working tree, and its keep-index flag only puts the staged changes back afterwards. So the entry is assembled by hand, in a shape git stash list, git stash show and apply --index all read as their own.

    The harder half is taking the staged change back out of the working tree, because a reverse patch takes its pre-image from the index and so cannot be laid over a file that also has unstaged edits — the ordinary case in an app that stages hunks and lines. A file with none is checked out of HEAD again, or deleted where the stash is what created it; a file with both is rebuilt by a three-way merge with the index as the common ancestor, the working tree as ours and HEAD as theirs, which leaves the never-staged edits sitting in the file.

    A merge that will not resolve refuses the whole operation, by path, before anything is written: half a stash is worse than none.

    Editing a stash¶

    A stash is an immutable commit reached only through refs/stash's reflog, and libgit2 offers no store or replace — so editing one means building a new stash commit and putting it back in the same stack slot. Three things make that work:

    • Un-recording a change is not deleting an entry. Removing a path from the stash's tree makes the stash say "this file was deleted", so applying it would delete the file. The path is instead reset to the base commit's version, leaving the stash recording no change for it. A path the stash itself created has no base version, and there the entry really is dropped.
    • Every tree the stash owns is rewritten, the index parent included — or apply --index would resurrect a file that was just removed. The base parent is left alone; it is real history.
    • The reflog has no "replace entry N". The entries above the target are read out, dropped, and re-appended around the new one — and refs/stash is updated before the rebuilt log is written, because updating a ref appends a reflog entry of its own that would otherwise leave a duplicate at the top of the stack.

    Renaming rewrites both the commit's message and the reflog entry's, because what git stash list prints comes from the reflog and changing only the commit would look right in the app and wrong in git. The On <branch>: prefix is preserved, since the branch is recorded nowhere else.

    Duplicating is additive — a second reflog entry pointing at the same commit. Nothing is rewritten, dropping one leaves the other, and editing one rewrites only that entry, at which point they stop sharing.

    Restoring individual files is the non-destructive counterpart to removal: paths are checked out of the stash's tree into the working tree and the stash is untouched.

    Stashing is free forever

    Create, apply, pop and drop are never gated: stashing is where work goes to be safe. Editing a stash is what a licence adds.

    Worktrees¶

    List, add, remove, and switch — and switching is just opening the other path, so every controller re-reads from the new working tree. Removal therefore refuses to delete the one that is currently open.

    git's own list reports only linked worktrees, so the main one is synthesised from the repository's common directory and always listed first. Opening a linked worktree resolves the same set, because every lookup goes through the common directory rather than the worktree's own gitdir.

    Submodules¶

    The full lifecycle: add, init, update, sync, set-url, deinit, and "open this as a repository" — the last being the cheapest useful thing here.

    Two files, and only one of them is history. .gitmodules is tracked: it is what the project says about its submodules, and a comment somebody wrote in it is as much a part of the tree as any other line. .git/config is this checkout's private copy, written by init and sync and taken back by deinit. Every write edits the one entry it was asked about and leaves every other line where it found it — nothing here reads a file into a model and writes the model back.

    That is also why set-url does not sync and sync does not set a url: they write different files, one of them is a commit and the other is not, and doing both at once would hide which half the rest of the team is going to receive.

    Adding is three steps and stopping after the first is the hazard: the entry and the gitlink are prepared, the clone fetches, and the pair is staged. Skip the last and the entry and the clone exist while the index records no gitlink — a submodule registered, present and untracked all at once. The middle step is the only one that can fail for a reason outside this repository, so a clone that fails is rolled back: .gitmodules restored byte for byte, the directory and the modules entry removed.

    Init and clone are two buttons because they are two different promises. Init copies the url into .git/config and touches nothing else: instant, offline, and the one step that always works where the clone has no credential to offer a private remote. Update needs a remote to answer. Folding them into one control would make the cheap certain thing inherit the expensive uncertain one's failure mode.

    Not initialised is a state, not a fault — it is what every fresh clone looks like.

    Deinit refuses rather than clobbers, and there is no force¶

    It is the only thing in this app that deletes a repository's working tree, and it is only allowed at all because the objects live in the superproject's .git/modules rather than under the working copy — so Init brings the same clone back.

    That reasoning fails in exactly three cases and each is refused by name:

    1. Uncommitted changes, untracked files included — those are in no tree, so no tree can restore them.
    2. Commits no remote-tracking ref can reach. Computed as a revwalk with every local tip pushed and every remote ref hidden, which is exact where comparing a branch against its upstream is not: a submodule normally sits on a detached HEAD with no branch and no upstream, and a commit made there is the case most worth catching.
    3. The old layout where the git directory sits inside the working copy, and removing it would take the history along.

    No force exists. Every refusal names something to go and settle in the submodule, and the row already opens it as a repository. A flag that skipped the check would be the only route in this app to losing work that is nowhere else.

    Subtrees¶

    Somebody else's repository vendored into a folder of this one — and the only feature here that runs the git command line.

    git subtree is a shell script that ships with git. There is no subtree API in libgit2 and there never has been: its four verbs are a subtree merge with a rewritten path prefix, a synthesised squash commit, a push of a split history, and the split itself, which rewrites history. Reimplementing them would be a feature the size of the rebase engine, built from a shell script's semantics, with every subtle case this app's own to be wrong about.

    So it runs the script and reads what it says. The cost is stated rather than assumed: with no git, the tab draws a sentence naming that libgit2 has no subtree support at all, rather than controls that cannot work. git is asked rather than merely found — a git on the PATH that will not run would otherwise leave every button live and every press failing — and asked asynchronously and lazily, because a blocking probe in a constructor is a wait every session pays for a feature most never open.

    Two rules apply here that do not to a read-only probe, because these calls write: every argument goes as an argument in a list, never a command line and never a shell; and a prefix is refused if it is absolute, contains .., or is a bare ., since a prefix reaches a path and is the one thing you type that could name a write outside the checkout.

    There is no list, so the list is inferred. git keeps no registry — no config section, no file — but git subtree writes a git-subtree-dir: trailer into the commits it makes, so the list is a walk of the history looking for it. That finds subtrees added at the command line years before this app existed, which a record of the app's own would not; and a prefix somebody deleted by hand goes on being listed, saying "folder gone" rather than dropping out.

    The walk is O(history), so it is asked for rather than refreshed — one commit message per commit is cheap per commit and not cheap in total, and this was in the general refresh for a while under a comment calling it "the same order of work as the tag list". A tag list is O(refs).

    What is remembered is what git does not keep. git subtree pull takes the url and the branch as arguments every time and keeps neither, so without a note every pull is a retyping. They live in .git/config, not .gitmodules, because git records nothing here for a teammate to receive.

    Squashing is on by default, which is the opposite of git's own default and deliberate: without it every commit of the other project is replayed into this history, which is what makes subtrees unpopular.

    Removing one is git rm -r and a commit, because git subtree has no remove — refused while anything under the prefix is uncommitted, that content being in no commit and no reflog.

    Sparse checkout¶

    Which of a repository's directories are on disk at all.

    Reading needs no git; writing does. What is in force, whether cone mode is on and how many entries the index is skipping are answered through libgit2. The verbs shell out — and the reason is stronger than the subtree's: writing the pattern file and setting the config is four lines, and doing it would produce a repository that is configured and inert. libgit2 has no sparse support of any kind: it knows what the skip-worktree bit is and sets it nowhere. The file would be there, the config would be true, every file would still be on disk, and nothing on screen could tell that from a sparse checkout that happens to include everything.

    Cone mode only, with the caveat on the tab rather than in a comment. git has two pattern languages: cone takes directories and non-cone takes full gitignore-style patterns. A directory picker is a control somebody can use, where a field accepting a negated recursive glob is one where a mistyped pattern silently removes a thousand files — and, the half that decides it, the refusal has to be exact: deciding whether a path survives a proposed set is a line of arithmetic in cone mode and a reimplementation of git's matcher in the other, and a refusal computed by a matcher that disagreed with git's would be a promise this app cannot keep, in the one direction where being wrong deletes uncommitted work.

    A repository already using non-cone patterns is read and reported, never converted.

    It refuses over the files, by name, before anything is written. Narrowing deletes from the working tree, and anything uncommitted in a directory that is leaving is in no commit and no reflog. git's own sparse-checkout set warns and carries on; that is a state to be in deliberately rather than one to arrive in from a directory picker.

    The picker is HEAD's tree and not the working directory, which is the whole point: a directory that is already skipped is not on disk, and a filesystem listing would leave it out of the one control that could bring it back. Ticks assemble a proposed set and Apply spends it, because a checkout per tick would be a dozen working-tree rewrites for one decision — and an empty set is refused rather than read as "everything", since in cone mode it means the root's own files and nothing else.

    Implemented and unexercised

    The sparse verbs run git sparse-checkout, which no test here does: a suite that ran one would be asserting git's behaviour rather than this app's, and would fail on any machine whose git predates cone mode. What is pinned is the reading, the cone matcher, and that the plan and the verb refuse in the same words.
