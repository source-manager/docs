    Changes and staging¶

    Licensing — Free. Staging, discarding, ignoring and deleting are free, at every granularity. What a licence adds

    Two lists — staged and unstaged — a diff beside them, and the commit box. The tab carries a count of what it holds, which is the union of the two lists rather than their sum: a file with some of its changes staged is in both, and it is listed once.

    Three granularities¶

    Stage Unstage Discard Revert
    File ✔ ✔ ✔ (asks first) ✔ from a commit
    Hunk ✔ ✔ ✔ ✔
    Line ✔ ✔ ✔ ✔

    Line-level staging reconstructs a patch from the lines you picked and applies it; hunk-level goes through the index API directly. Both key a selection to a line's index within its hunk, which is why the unified and split diff layouts cannot disagree about which line a click meant.

    Space stages or unstages whatever is picked — the same verb the tick is rather than a second spelling of it, so a folder stages what is under it, a set of eleven stages eleven, and every refusal is the one the tick would have made.

    Flat or a tree, and one choice for both lists¶

    Anything carrying a path becomes rows: a directory row per level with the count of everything beneath it, and files labelled by basename. The Changes lists and a commit's files on History are the same component with the same folds.

    Which reading is in force is a habit rather than a decision per list, so it is remembered in the settings — a property on a surface would forget itself every time, since the surfaces are loaded on demand.

    A tick on a folded directory stages everything under it. That case used to be broken rather than absent: it called a verb with a path git does not hold, so it silently did nothing.

    What a verb acts on¶

    There are two different questions and they are kept apart. The file being read is one — a panel draws one diff — and what a verb acts on is a set, because somebody picking eleven files to discard is not asking to read eleven diffs.

    The set comes from two places and they compose:

    • A multi-selection. ⌘/Ctrl-click adds and removes, ⇧-click extends from an anchor in the list's own order, and a plain click replaces the lot and sets the anchor. The anchor is written by a plain click and a ⌘-click and left alone by a shift-click, which is what lets a run be re-aimed by shift-clicking somewhere else rather than started again.
    • A directory — a verb chosen on a folder acts on every file under it.

    The selection is scoped to one list, because "staged" and "unstaged" decide what every verb here means and a set spanning both would make Stage ambiguous by construction.

    Every row of the set is lit, not only the one being read, because a verb acts on the set and the set has to be visible. Right-clicking inside the set keeps it; right-clicking outside it selects that row.

    The wording follows the count: the menu's header says "11 files" rather than naming one of them, and two verbs are absent for a set rather than relabelled — Ignore writes a rule per path, and Blame is one file's story.

    A verb over a set is one operation, not eight hundred¶

    Discarding a folder's worth of files used to lock the window for several seconds with nothing on screen saying anything was happening, and the cause was not that any one file is slow. It was that a set was eight hundred operations: per call, open the repository, build a whole status list to answer about one path, write the index, take a snapshot, append a row to the operation log, and emit a change that turns into a full status refresh of every list. None of those costs is per file; every one is per operation.

    The same fault was in three more verbs, and the worst of them had no confirmation in front of it — "Stage all" was a loop, measured at 2806 ms for 800 files.

    Measured over 800 one-line files:

    Before After
    Opening the discard confirmation 1205 ms 9 ms
    Discarding 3972 ms 75 ms
    Staging 2806 ms 60 ms
    Unstaging 3056 ms 60 ms
    Longest single stretch the window is frozen the whole 5.2 s one 13 ms budget

    All four are one operation now, over shared machinery: one status walk, one snapshot, one log row, one refresh, and the index and working tree written a chunk at a time against a time budget. Progress is in the operation banner, because a sweep of eight hundred files takes long enough to walk away from, and Stop is never gated.

    Chunk sizes differ per verb because what a chunk costs differs: discard's is 32 (one index write and one tree walk however many paths), staging's is 16 (adding a path hashes the file, so the cost is bytes rather than calls), and resolving's is 8 (each file costing a three-way merge to write).

    The refusals are collected and said once. A toast holds the last message, so eight hundred of them would report one.

    Discarding¶

    Discarding a file takes it back to the last commit, index and working tree both — a verb that only reset the working tree would be the third of three overlapping half-undos and would leave the file still listed, reading as the button not having worked.

    Discarding a hunk goes back to the index, and the asymmetry is a fact about where a hunk comes from rather than a taste for one: the only hunks on screen belong to one of the two diffs the panel draws, and undoing one can only mean undoing it against the side it was measured from.

    A hunk of the staged diff has no discard at all, and that is the answer rather than a gap — undoing a hunk of HEAD-to-index is unstaging it, the button is already in that row, it is reversible, and an unrecoverable second spelling of it alongside would be a trap. Throwing staged work away is unstage, then discard.

    What it refuses, and what it offers instead¶

    • A renamed file's discard undoes the rename — the old name comes back out of HEAD and the new one goes. This used to be refused, with a sentence telling you to untick the file and discard the old name: two operations to undo one, the second naming a path no longer on screen.
    • Deleting what no commit holds is the second answer, behind a tick. For an untracked file there is nothing to go back to, and the refusal was right about the verb and unhelpful about the intention. The tick is drawn from the same plan field the operation reads, so the offer and the operation cannot drift, and it is off every time the dialog opens — a destructive option still on from last time is one nobody chose.
    • A conflicted path is refused. Marker text is not the new side of a diff, and settling it belongs to Conflicts.
    • A selection with nothing undoable in it is refused. An empty patch applies cleanly and reports success for having done nothing, which is exactly how a destructive verb comes to be trusted.

    The confirmation lists every path¶

    It listed eight and then "… and 412 more", defended on the grounds that a list which has to be scrolled to be counted is one nobody counts — but the count is in the title, so nothing there was doing the counting, and what the cap actually did was hide four hundred and twelve of the files about to be destroyed from the only place they are named.

    A row also says what will happen to it where that differs from the dialog's sentence, since a set is the one case where the promise cannot be true of every path. One file keeps the exact sentence; a set gets a deliberately weaker one, because there is no sentence true of eleven files at once.

    Nothing is confirmed at hunk or line level. A hunk is a gesture inside a diff and a line is a keystroke, and a dialog per line is a habit rather than a confirmation. What replaces it is refusing, and the fact that the result lands somewhere you can look at it.

    Ignoring a file¶

    Entered from the file, and offering the four rules people actually ask for — this file, this extension in this directory, this extension anywhere, this whole directory — with the exact line on screen before it is written. A .gitignore is one of the few files in a repository that is composed rather than generated, and describing the intention while writing the line out of sight is how a client ends up being the thing whose output has to be checked afterwards.

    Three things about it are load-bearing:

    • A tracked file is not ignored by a .gitignore entry at all. Ignore rules decide only what happens to paths git is not already following, so a file in the index goes on appearing in git status however many rules name it. A tracked path is refused by name, with the git rm --cached that would make a rule mean something.
    • The line is appended, and no code path can do otherwise. The file is opened in append mode, a missing final newline is made good in front of the new line, and the line ending is copied from what the file already uses — one LF line in a CRLF file is a whitespace change in every tool the repository passes through.
    • A rule that would lose is refused rather than written. The .gitignore files between the root and the path are read for re-inclusion (!) lines, and each is asked whether it covers this path — because libgit2 and git disagree here, and libgit2 reports a path a deeper file re-includes as ignored.

    Rules that would mean nothing are absent rather than greyed: no extension rules for a file with no extension, no directory rule for a file at the repository root. A leading dot is part of a name rather than the start of an extension, so .env is offered one rule and not three.

    The list is virtualised, and had to be¶

    Both lists were built row by row, which is right for the forty changed files this surface is normally opened on and ruinous for a branch switch, a generated directory or a reformatting sweep. Measured through the shell, before a pixel was painted:

    Changed files Build time
    1,000 0.27 s
    3,000 2.2 s
    6,000 13 s

    And a tap of the modifier then cost another 2.8 s, because every row declares two commands and the registry was growing at twice the rate of the list.

    It is now 22 rows and 208 commands built, whatever the count is — 0.16 s at six thousand files. The section headings and the empty notes are rows of the same list, because anything that has to scroll with the rows has to be one of them.

    One consequence you can see: the two bulk buttons ("Stage all", "Unstage all") live on a heading, and a heading three thousand files down does not exist — so each keeps a palette entry of its own that stands in while the button is scrolled away, and exactly one copy is ever listed.

    The gestures on a row¶

    A double click stages or unstages — a third route to the tick, adding a hint key and no palette entry. On a directory the first click folds and the second is dropped, since a fold toggled twice lands back where it started and reads as a press that did nothing.

    A right-click opens a menu, and every row of it is a second route to something the surface already draws — staging is the tick; Discard, Ignore and Blame are the three buttons above the diff — except Open in editor and File history, which are reachable nowhere else and are therefore the two rows that are in the palette.

    Opening the menu selects first, because Discard, Ignore and Blame all act on the selection and each reads a plan taken at selection time. A menu acting on the row it was opened over while those plans described a different file would be right about the name and wrong about the offer.
