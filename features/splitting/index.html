    Splitting a branch¶

    Licensing — Paid. This page is stacked-branches. What a licence adds

    A proposal nobody will review because it is too big is the commonest complaint anybody makes about anybody else's work, and the answer everywhere else is "split it up" — which until now meant leaving the app for a terminal and an afternoon of rebase -i and checkout -p. This is that errand as one operation, at four granularities: a commit, a file, a hunk, or the lines picked out of one.

    What comes out is a stack of branches, each based on the one before it, each proposable on its own. What is not touched is the branch you split: it keeps its commits, its hashes, its upstream and its pull request.

    How to split one¶

    1. On Manage → Branches, open a branch's ⋮ — or right-click the row — and choose Split into a stack.
    2. Check the On field at the top. That is the branch the first part will sit on; it arrives filled in with the branch's recorded base, or the trunk as this checkout has it, and it has to be a branch you actually have (see below).
    3. Press Fill this one on the part you are loading. Everything you take goes there until you choose another part. Any part can be filled, the last one included.

    4. Take change, at whatever size suits it:

      You want Where to press
      A whole file Take on the file's row in the middle pane
      A whole commit the Commits chip, then click the commit's row
      One hunk click the file to read it, then Take hunk in the hunk's header
      Some lines click each line in the diff, then Take 3 lines

    5. Give each part a branch name and a commit message. The sentence under the header says what is still missing, and once it is clear it says how many changes will land in the last part instead.

    6. Press Split. You land back on Branches with the new branches there, and you propose each one from its own row.

    Cancel costs nothing. Nothing on that page writes: an assignment is a note the app keeps until you press Split, so walking away drops the arrangement and leaves the repository exactly as it was.

    The last part is whatever is left over¶

    Parts partition the branch's diff, and the last one takes everything you did not assign. That is what makes the parts add up to the branch: nothing can be dropped by an arithmetic mistake, because the last part's tree is the branch's tree.

    You can still fill it like any other part, and its row says so — "2 pieces, and everything left over". Doing that is a convenience rather than a mechanism: what you put there was already going there. But "these files in part 1 and those in part 2" is what splitting something in two means, and with two parts the second one is the remainder, so the page would otherwise refuse the most obvious arrangement there is. A change still belongs to one part only, wherever you put it.

    Where nothing is left for the last part, the split is refused by name — give it something, or make one part fewer.

    Nothing is rewritten, and that is why it is safe¶

    Each part's tree is synthesised from the branch's diff rather than replayed: part n's tree is the base tree with the pieces of parts 1…n applied, worked out by walking the diff and emitting each line or not. Three things follow, and each is a state this operation cannot reach:

    • A conflict is not possible. Not unlikely — impossible. The selections are disjoint subsets of one diff, so composing them is concatenation rather than a merge. There is no stop point and nothing for the Conflicts surface to finish.
    • The working tree and the index are never written. It is the only write in the app that does not care whether your working tree is dirty, and it runs perfectly well while a rebase, merge or cherry-pick is half-finished, because nothing it touches is in their way.
    • HEAD does not move and your branch is not touched. The parts are new branches beside it. That is what makes the whole thing reversible.

    Everything is checked before one object is written — every name, every piece, every message — because a split that made two branches and then found the third name taken would leave a stack that is neither what you asked for nor what was there.

    A commit is a shortcut, and it says when it is a coarse one¶

    Pressing a commit takes every file it touched. Where its files are its own — the ordinary shape of a branch somebody wants split, "the API change and the docs change" — that is exactly its work.

    Where another commit in the range touched one of the same files, the row is tagged shares files and what you get is the whole file rather than that commit's lines. This is not a shortcoming to be fixed: a commit's contribution to a file a later commit rewrote is not in the branch's diff at all, because the lines it wrote are gone. The tag is there so a coarse selection is one you chose rather than one you were not told about.

    Files that can only be taken whole¶

    Some files are tagged whole only, and the row says which of four reasons it is: it is binary, so it has no lines to pick from; the branch deletes it, and taking some of its lines would leave a shorter file rather than remove one; it moves, and a hunk of one name is a claim about the other; or only its mode changed, so there is no hunk to take.

    Two parts may hold different hunks of the same file — that is the point of hunk granularity. What is refused is the same piece in two parts.

    The base has to be a branch you have¶

    The On field takes a local branch, and only local branches are offered. A stack is recorded per branch in this checkout, so there is nowhere to record one against origin/main — the server's copy of the trunk is not something the first part can sit on. Pointed at one anyway, the page says so and names the branch to use instead.

    The diff itself is measured from the merge base, which is what a pull request shows and the only reading that stays right when the base branch has moved on since you cut yours. Measured from the base's tip instead, a part would carry the base's own newer commits backwards — a plausible-looking diff that undoes somebody else's work.

    Undoing one¶

    Manage → Operations carries one row: Delete the N branches it made. There is nothing about your branch to put back, because it was never modified.

    It works while the parts are untouched. Commit onto one of them and it is refused by name rather than forcing over your work — a part's commit is not reachable from HEAD, so the delete has to be forced, and what earns forcing it is that the tip is still exactly where the split left it. Unmoved, that commit is a synthesis whose every line is still in the branch it came from, so dropping it loses nothing. A branch you have already deleted by hand is not a failure, so a split half tidied up can still be finished from the log.

    What it deliberately does not do¶

    • A part lands as one commit. Assign three of the branch's commits to a part and their changes arrive as a single commit, not three: a part is a synthesis, so there is no original commit for it to preserve. Where keeping the commits matters, reorder them with the interactive rebase first and split the result.
    • The parts are authored by you, now. A synthesis is a mixture with no single author, so there is no original authorship to carry. They are signed where your repository signs commits — see Signing.
    • Your existing pull request is untouched by a split. Splitting writes only names that were free, so closing or re-pointing the original is your decision on the forge. Where the errand is "take this out of that proposal", the other verb crosses that line on purpose and says so — see Taking pieces out of a proposal.
    • A part need not compile. Take half a hunk and you can leave a file that does not build. That is true of every tool offering this granularity, and it is your judgement rather than something the app will refuse.

    What is verified¶

    The synthesis is checked byte for byte at all four granularities against a repository built to order, including the two shapes where an off-by-one would hide: taking an addition without the removal it replaced, and taking one line out of a block of three. The guarantee the whole design rests on — that the parts add up to the branch — is asserted as a tree equality, and the plan and the operation are required to refuse in the same sentence, so what the page promises cannot drift from what the button does.

    The page's own arrangement logic is covered separately. What no test here covers is a repository with more than one local branch drawn in the QML suite: the shared fixture has one, and adding another would move counts other suites assert — so the git behaviour is pinned in C++ and the page's behaviour is pinned against a branch that is deliberately not there.
