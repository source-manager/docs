    Writing a commit message¶

    Licensing — Free, with paid parts. The box, the template, the marks, the trailers and recall are free. What the staged paths and the log are evidence of, and the subject-shape check, are commit-help; the drafting verbs are ai. What a licence adds

    The box on Changes, and everything the app knows that would help fill it in. The rule the whole thing is built on is guidance, never enforcement: nothing refuses a commit for the shape of its message, nothing rewrites what you typed, and every control that does change the text goes through the field's own undo stack so ⌘Z takes it back.

    What is on it¶

    • commit.template, laid into an empty box, with the surface saying which file it came from. Comment lines are stripped here, since this app has no editor session for git commit to strip them in.
    • The 50/72 marks, measured in the face the box is actually drawn in.
    • Co-author trailers, from a picker over the repository's recent authors, appended in GitHub's own Co-authored-by: spelling.
    • Conventional-commit type chips — a shortcut row you choose in the settings. Six by default; add perf, ci, build or your own, or empty the list and draw no chips at all. It is a habit rather than a fact about a repository: somebody who writes perf: writes it in every checkout they work in.
    • Recall of recent messages, from two sources kept in their own sections.

    Two sources of recall, and why they stay apart¶

    The preference holds the last twenty messages typed into that box, globally. That is what your own wording looks like across every checkout you work in, and it is the only source that answers before anything has been read.

    The repository's own log is the other, and it is what the preference cannot be: it is empty on a clone made this morning, which is precisely the moment somebody most needs to see how this repository writes its subjects, and it holds twenty messages where a convention is visible in two thousand.

    Choosing the log rather than a second file of the app's own settles three things at once: there is no schema to version, no rows to drop when a repository leaves the fleet, and no copy of anybody's prose on disk — a commit message is the words you wrote, and the only defensible place to keep those is the one git already keeps them in.

    One walk, two readings:

    • The vocabulary is everybody's, because which types and scopes a project uses is a fact about the project, and inferring it from one address would answer nothing at all on a fresh clone.
    • The recall list is filtered to this checkout's own user.email — the address git would sign the next commit with — because offering another person's whole message to be committed under your name is not recall.
    • The completions are everybody's with your own ranked first.

    Nothing is walked because a surface was opened: the log is read by the first keystroke in the box, or by the recall list being opened. What is read is then kept and re-walked only when the repository or HEAD has moved.

    The suggestion strip¶

    Under the box, and it is where the two kinds of help sit side by side — which is the thing nothing else in the field ships.

    The offline half: inference that states its basis¶

    suggestionsFor() answers a row per suggestion and the basis is never empty. This app's rule everywhere is that an inferred thing names its evidence, and a commit type is the most consequential inference in the set: a wrong feat: is wrong in the changelog, in the release notes and in whatever reads the log a year later.

    So there is deliberately no "the source files changed, so this is probably a feature". A feature and a fix touch the same files in the same directories, and where the paths decide nothing the answer is empty, with the sentence saying so — which is also the sentence that teaches where the line is. The paths decide a type only where they genuinely do: every staged file a test, a document, a build file or CI configuration.

    Once a type has been typed by hand, the one thing left that the paths do decide is where the change lives, so the second kind of row adds the deepest directory the staged files share. A scope is only offered where this repository's subjects carry scopes; a segment that only names a layout convention (src, lib, app) is not a scope, since fix(src): says nothing fix: does not; and a scope that repeats the type is dropped, test(tests): being the same word twice.

    A declaration outranks an observation. A commitlint type-enum array is lifted out of the JSON, YAML or JavaScript spelling and those are the types that may be suggested, because a declaration is a rule somebody wrote down and the counts are a pattern somebody noticed. Nothing is evaluated — a commitlint.config.js that computes its types from a required module is a program, and running one is not something a git client does.

    The generated half¶

    A model's draft, in the same strip, marked as generated and naming the model that answered. See Asking a model, including @ai — write the part that carries intent, mark where the machine should fill in, and the two are blended.

    The offline inference is not a fallback for when no model is configured: it is cheaper, it is offline, it needs no key, and it states its basis, so where the paths genuinely decide something it is the better answer, because you can check it.

    Reaching the strip by keyboard¶

    The keyboard really moves into it, by Tab and by ↓ alike. A highlight that walked a list while the caret went on blinking in the box would be two cursors, and which of them Enter belongs to is not something a reader should have to work out.

    • Tab is the shape everybody has met under a box of completions.
    • ↓ steps in from the subject or from the end of the message. Not only from the end: the suggestions are about the subject, so a reader who had typed both could never have reached a suggestion about the line they were on.
    • ↑ off the top, ↓ off the bottom, Enter having taken a row, Esc having taken none, and Tab again all hand the keyboard back.
    • Nothing is highlighted until ↓ is pressed. With a row pre-selected, Enter would commit a line the app guessed rather than the one you typed.

    Both keys fall through with nothing to suggest, which is the common case, so Tab goes on indenting and ↓ goes on moving the caret.

    Pressing a row writes the subject line only, so a paragraph already typed under it survives being offered a better subject.

    The shape a subject is expected to have¶

    A regular expression the first line is matched against, a warning sign beside the box when it does not match, and the sentence behind the sign. Nothing else.

    It warns and never refuses. No commit is blocked, no button is greyed, no word is rewritten. A client that enforced a convention would be enforcing somebody else's rule with no way to see it — the app is not a linter.

    A regular expression rather than a switch, because "which shape" is the whole question: a project with PROJ-88: … subjects is as entitled to a check as one with feat(scope): …. The default is Conventional Commits in commitlint's own type set, spelled out rather than derived from your chip row — taking perf off a chip row is not a statement that a colleague's perf: commit is malformed.

    Three states and never two: no pattern at all is a project with no convention and the mark is absent rather than green (a tick beside every message anybody types is chrome), and a pattern that will not compile is reported as not ok with a sentence naming the setting rather than the message.

    A repository's own pattern outranks the setting, in .git/config under the app's own key — which shape a project's subjects take is a fact about the repository, the same for everybody who works on it, where a setting is one reader's habit. Per checkout rather than committed, because .git/config is not cloned, which is also what makes a stored pattern safe to act on.

    Amending HEAD¶

    A tick on the commit box. It amends over the tree the index currently writes, which is what makes it pick up newly staged work and what makes an untouched index leave the content alone. An empty message keeps the one the commit has, which is --no-edit. The author and their timestamp survive and the committer does not, as git does it: who wrote the change and when are facts about the change.

    Only HEAD, and it says so. An older commit is reworded by stopping on it in a rebase, which this app has — see Rewriting history. Nothing amends while an operation is in flight.

    A published commit is warned about, once, and amended anyway. Rewriting a pushed commit on a branch of your own is ordinary, and refusing it would be this app deciding how somebody else's branch works — but the consequence is not visible from the button. "Published" is ahead == 0 against the upstream: local, no network, and no promise beyond what the last fetch left.

    The tick is absent rather than present-and-refusing on an unborn branch or during a stopped operation.
