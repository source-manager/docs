    Undo, backups and the log¶

    Licensing — Free, with paid parts. The reflog is free, and so are the backups a destructive verb takes before it writes. The operation log and the way back it offers are operation-log. What a licence adds

    Manage → Operations. One row per operation, newest first, with the git command beside it — and a way back where one exists, and a sentence where one does not.

    This is the feature the comparison calls effectively unique in the field, and what makes it so is not that it exists but that most of it is refusals.

    Why "Undo everything" is not offered¶

    A log makes that button look even more plausible than a reflog does — every row names an operation, so surely every row reverses. It is the same falsehood: git records refs, not files. A commit that left a branch is still in the object database; an uncommitted edit that reset --hard wrote over was never in an object at all.

    So a row does not carry "undoable". It carries what kind of thing it did, and what is offered follows:

    Kind Meaning What is offered
    ref-move A ref moved and nothing on disk was destroyed A mixed reset back to where it was
    inverse Additive, with a real inverse that has its own name That inverse, named for what it does
    destructive It overwrote files Nothing, and a sentence — unless a backup was taken
    remote It left this machine Nothing, and a sentence
    none Nothing to take back Nothing

    The inverse button never reads "Undo". It reads "Delete the tag again": deleting a tag is not the undoing of having made one, and the shorter word hides which of the two is about to run.

    Mixed is not a parameter. Soft would leave the index holding a tree nobody staged; hard would overwrite the working tree, which belongs behind the reset dialog that counts and names what it is about to destroy.

    A ref-move recorded without the commit it moved from degrades to none rather than reaching you as a reset to nowhere. The fast-forward merge is the real case: it never enters the in-progress state, so nothing ever published the commit it came from, and that row honestly points at the reflog instead.

    Two arguments decide a kind, and only the call site holds them¶

    reset --hard is destructive where soft and mixed are ref-move; a forced worktree removal is destructive where an unforced one is none, because unforced refuses anything uncommitted.

    A commit is the case worth arguing out. It moves a ref, so a mixed reset genuinely undoes it — and it is honest precisely because that reset writes no file, so the working tree comes out byte for byte as it went in and the change lands back on Changes. Undoing a hard reset the same way would restore the commits and quietly not the files, which is the same button making two different promises.

    A detach is not a ref move, and calling it one is the neatest way to get this wrong: no branch moved, and a mixed reset against a detached HEAD drags it back and leaves the repository detached — indistinguishable from having gone back, and the next commit made there is orphaned. That row points at re-attaching.

    There is no redo; there is "Run again"¶

    Re-applying is not the inverse of having reversed, because the repository has moved — the commit is not where it was, the remote holds different refs. So it re-issues the operation through the controller that owns it, with every precondition re-checked against the repository as it stands.

    The list is short and excludes everything destructive (running a reset twice is running it once more), the plain force push, and the clone, which the second time round is a clone into a directory that now exists.

    An undo says so¶

    Pressing "Put the files back" changed something on disk and the log itself drew nothing, which is indistinguishable from a button that does not work. Both verbs have one exit for that, so the sentence is said once rather than at a dozen call sites — and the channel is deliberately narrow: a verb whose result is visible where it was pressed says enough by changing what is drawn.

    What is recorded, and where the row is written¶

    Everything whose completion signal says which verb ran is recorded centrally: rebase, cherry-pick, merge, push, pull, clone, fetch, an ignore rule.

    Everything else records at the call site, and the reason is stated rather than hidden. One signal is emitted identically by a soft reset, a mixed reset, a hard reset, a detach and a re-attach — and the difference between the second and the third is the entire difference between an operation this app may offer to reverse and one whose consequences are in no journal at all. Another says a list moved and not what moved it; another cannot tell a stash push from a duplicate or a pop from a drop.

    Guessing there would put an Undo on precisely the row where pressing it proves the button was a lie.

    A call site records once, at the point the operation is over — the call has been made and its result is known, or a plan function has refused. Both are the operation: the plan's refusal is the sentence you were already shown before pressing, and "I confirmed it and nothing happened" is a question a log owes an answer to. An early return on "no repository is open" is deliberately not recorded, because nothing was attempted — a log filling up with rows for half-typed forms is one nobody reads to the bottom of.

    The command is never stored¶

    An entry holds the id and the arguments, and the row resolves the command on every read — so correcting a spelling in the registry corrects the log with it. A rendered string on disk would be a second copy of every command in the app, going stale in the one place whose output is meant to be run somewhere the app cannot see.

    An id the registry does not know renders nothing, here as everywhere.

    That is also why two rebase routes are two ids rather than one with an argument: rebase -i prints a line that stops and opens an editor when pasted, which is honest for a plan you read and edited and misleading for one nobody was shown.

    It is kept, in JSON, and per repository¶

    A log that vanished on quit answers "what did I just do" and not "what did I do on Friday". The settings file is for choices and a growing list of records in it is an abuse of the shape; a database earns itself by answering differently-shaped questions and by being a cache, which this is not.

    Entries carry the checkout they were recorded in, the surface reads only the open one, and a repository leaving the fleet takes its rows with it. Nothing recorded can carry a credential: the arguments are refs, paths, branch names and messages, and the one remaining route — a clone url with userinfo in it — is redacted before the entry is built, with a test reading the file's bytes back.

    Two launches used to erase each other's log

    The file is one per machine, and both copies read it once, held the rows in memory and rewrote the whole thing on every operation — so the second one to write erased everything the other had recorded since it loaded. What went with those rows was not only the history: the backup tokens hang off them, so every way back they offered went too, silently, in the one part of the app whose whole subject is saying what it did.

    Recording re-reads the file immediately before appending now. That does not make it safe against two writers landing in the same instant, but it collapses the window from a whole session to a single write. The token a row is identified by had to be re-seeded with it — two readers continuing from the same number would share an identity, and "Put the files back" on one would reverse the other.

    What the log keeps, and what it costs¶

    Three bounds, because they bound three different things and you reach for whichever matches the reason you came: days, entries per repository, and megabytes of snapshots.

    Zero is no bound in all three, which is a real answer rather than an off-by-one: somebody who wants every operation they have ever run should not have to type a large number and hope. It is also why the age default is not infinite — a row whose copies the store's own cap dropped long ago offers a way back that is not there.

    Clearing the log and clearing the snapshots are separate verbs. Tidying a log and reclaiming a few hundred megabytes are different acts, and only one of them destroys something with no other copy — so it asks first, names what is about to go, and its confirm is not the primary.

    The figure lives on the Operations tab and the bounds live in the settings, which is the split this project draws everywhere: a number is read at the moment somebody is deciding whether to press the button beside it. It is measured when asked for rather than kept, because a stale figure in front of somebody about to destroy something is worse than none.

    And where a copy makes one of the refusals untrue¶

    Everything above stands. What a working-tree backup changes is not the argument but the facts for the operations that go through it: it copies what they are about to write over, before they write, and then there is something to put back.

    The promise is narrow and is stated in those terms: these files, as they were a moment before this operation ran. Not "the repository as it was" — a hard reset moved a ref as well, and putting the files back leaves the branch where the reset put it. So the sentence names that half and points at the reflog, and the verb is "Put the files back" rather than "Undo".

    Four call sites take one, and they are the ones that destroy content held in no git object: a hard reset (over the plan's own list, so exactly the files the dialog named — and never the untracked ones git leaves alone), a file's discard, a hunk's or a line's discard, and a hook being edited or deleted.

    Switching a hook's executable bit takes none, because nothing is destroyed and the way back is the same control pressed again; creating anything takes none either.

    It is a file copy, deliberately, and not a git object. A stash is a commit with a tree, so it needs the index and HEAD in a fit state — which is what they are not, half way through a reset — and it would show up in the stash list where somebody would reasonably drop it. A dangling blob is what git gc exists to delete. A plain copy outside the repository survives every git operation and can be dropped by a size cap without a ref anywhere going stale.

    Best effort, and the row says which. A copy that could not be taken — nothing there, a path that climbs out of the base, a file or a snapshot past the caps — answers with nothing, and the caller does not abort: an operation somebody confirmed is not cancelled because a convenience could not be arranged. A row with no token offers nothing and says why, which is where every destructive row was before this existed.

    What must never happen is a row offering a restore with nothing behind it, so the token is recorded only once the copy has landed, and it is refused whole rather than taken in part — half a snapshot restores one file and leaves its neighbour, a state the repository was never in.

    A path that was not there is part of the state too. A tracked file deleted in the working tree, or a hook that did not exist yet, is recorded as absent, and restoring it deletes what the operation created. And the permission bits travel with the copy, which is the whole of what makes a restored hook a hook: one that came back without the executable bit would sit there being skipped, which reads as the restore not having worked.

    The copies go when the row goes — pruned out of the log, dropped with a repository leaving the fleet, or cleared — so the two cannot disagree about which rows are backed. An old row's answer is "the copies are no longer kept" rather than a failure.

    The log this app keeps about itself¶

    Separate from the operation log, and for a different reader: when something has gone wrong and you want to see what actually left the machine, there is a rolling file.

    Six categories rather than a level, and all of them are on: transport, the forge's HTTP, the replay engines, the working-tree watcher, timing spans, and the app itself. There is no verbosity dial, because the question a log answers is always asked after the thing happened.

    One file a day, with two bounds you can set — how many days to keep, and how many megabytes the directory may hold. Zero is "no bound" in both, retention is read off the file's name rather than its modification time, and today's file is never deleted to make room.

    Every line is redacted as it is written, in the one place every line passes through, so a call site added later cannot forget: userinfo in a URL, an Authorization header (Basic included), a bare bearer token, a JSON-encoded secret, a parameter named for what it holds, and the token shapes the forges use. The host survives, which is what makes the log worth reading, and a test asserts it by reading a written file back.

    Paths are kept, deliberately. That is what makes a transport failure diagnosable, and it is also why Reveal log sits beside the path on the About page: a log that records where your work lives is one you should be able to read before deciding to send it to anybody. Clearing it is a press on the same page.

    What you would have typed¶

    The app is a way of driving git without knowing git, and that is exactly how somebody ends up never learning it. One registry answers "what is the command for this", and both routes into it read it: a hint beside the operation, and the palette printing the line for the entry it has highlighted.

    One registry rather than a string beside each button, because the moment two surfaces offer one verb the literals are two copies that drift.

    A path or a ref comes out safe to paste, and only quoted where it must be. POSIX single quotes — the only form with no interior escapes — and quoting everything was the other candidate and is worse than useless: nobody learns git add src/main.cpp from git add 'src/main.cpp', and somebody who sees quotes on every argument stops being able to tell which of them needed them.

    The safe set holds braces, on the strength of stash@{2}, and ~ when it is not the first character, which keeps HEAD~3 plain while a path beginning with one is quoted rather than silently expanded to somebody else's home directory.

    An id nobody registered answers empty, and the UI then draws nothing. There is no fallback and no guessing. This is the one thing in the app whose output is meant to be run somewhere the app cannot see, so a guess is not a degraded answer — it is a command somebody pastes.

    The command says what the app does, or it is not offered. Every revert carries --no-commit; a file's discard names both sides and a hunk's is git restore --patch, because one goes back to the last commit and the other to the index; the autostashing checkout is three commands with apply && drop rather than pop, since pop discards the entry even when it has just written conflict markers.

    git checkout - is deliberately not offered for re-attaching HEAD: it means "wherever HEAD was", which is only this branch while nothing else has moved HEAD in between, and a command that is equivalent most of the time is the worst kind to teach.

    Two things it does not try to be:

    • Not a record of how this app is implemented. The interactive rebase is registered as git rebase -i <upstream> with the plan printed beneath as the todo file's own comment lines, even though the replay here is driven by cherry-pick.
    • Not complete where git is not. There is no entry for reverting a single hunk, because git has no verb that reverse-applies a chosen subset of one commit's hunks — the nearest spelling offers a different set of hunks, so "the third one" would mean two different things in the two places — and none for renaming a stash, which is a reflog rewrite git has no command for at all. An absent line is the absent-not-greyed rule applied to prose.

    Where it appears is the argument, not whether. Beside the place an operation is decided — the confirmations, the stash detail, the operation banner — and in the palette. A hint on every button would put a monospace line beside forty controls, which is noise rather than a lesson.

    It can be switched off, default on: a line somebody has to switch on is a line for the people who already know what it says.
