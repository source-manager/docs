    Reading a diff¶

    Licensing — Free. Every reading of a diff on this page is free. What a licence adds

    One panel, used everywhere: the working tree, the index, a stash, a commit, a comparison, a file's history, and somebody else's pull request. Which verbs it offers changes; how it reads does not.

    Unified or split¶

    Unified is the default — it is what git diff prints, it survives any width, and a hunk that only adds lines gains nothing from a gutter down the middle. Split earns its width on a rewrite, where the before and after of a line are otherwise rows apart.

    It is a habit rather than a per-panel switch, so it holds for the working tree, the stash viewer and a commit's files alike. Both layouts draw the same cell and both key a selection to a line's index within its hunk, so staging cannot tell which layout a click came from.

    Below about 889px of panel — 55 columns a side, derived from the monospace font rather than a pixel figure somebody picked — the split chip is hidden and the panel says "split view needs a wider panel" rather than lighting a control it is ignoring. Dragging a splitter narrow falls back to unified and keeps the preference, because dragging a splitter is a statement about this window rather than about how you read diffs.

    What is drawn¶

    Syntax highlighting, from the file's extension. Anything unrecognised renders as plain text, exactly as before, because unknown must not look like broken.

    Intra-line marks — a word-level comparison between a line and its partner, drawn in both layouts as washes behind the text rather than in the markup, which is what keeps the plain string authoritative for measuring.

    Rows pair by likeness, not by position. Within a change block a removal is shown against the addition it most reads like, and anything with nothing alike opposite it takes a gap. Pairing by position was tried first and was wrong as often as it was right, confidently showing two unrelated lines as one line's before and after. A gap reads as absence rather than as a mark: a wash a shade deeper than the ground and a hairline at a fifth of the divider's weight, because a divider-weight rule struck across the row was the loudest thing in the panel.

    Four dials¶

    Control What it changes
    Context 3 / 10 / 25 / the whole file
    Whitespace nothing → whitespace → whitespace and blank lines
    Split unified or side by side
    Wrap fold long lines, or scroll sideways

    The first two change what libgit2 was asked rather than how the answer is drawn, so the panel re-takes its diff — and it is the controller that knows whether those hunks came from the working tree, the index, a stash or a commit.

    Whitespace and blank lines are separate switches because they are separate in git, and for a reason: -w disregards whitespace within a line, and a blank line has none to disregard, so no amount of ignoring whitespace hides one. A reformatting sweep normally needs both, so one chip cycles all three states.

    Ignoring whitespace stands the writing verbs down

    Staging, reverting and discarding rebuild the hunk as a patch and apply it, and a diff hiding a re-indent is not a patch of the file on disk. Those verbs are hidden rather than greyed while a filter is on, which is also what makes them genuinely unavailable — a hidden control is in neither keyboard route — and the panel says why, because a missing Stage button reads as a broken Stage button.

    Wrapping is a preference rather than a per-panel switch for the same reason split is: it is a reading habit, so it holds for every diff surface at once, including the three-way conflict columns, which run out of room first at a third of the width. Scrolling is the default — a diff reads by column as much as by row, and a fold pushes everything under it out of alignment.

    A ten-thousand-line hunk¶

    The panel used to virtualise the hunks and build every line of one, so forty small hunks were fine and one contiguous hunk was not — and the context dial's "Whole file" step turns any large file into exactly that. Measured at ~116 KB of resident memory per built row, a thousand changed lines cost 234 MB and ten thousand cost 2.3 GB; that was the whole of the "the app is using 400 MB" report, and nothing on screen said so.

    Slicing the long hunk into smaller pieces was tried and made it strictly worse at every size, which is the finding the present design is built around: a list fills its viewport by creating rows until their heights add up to it, and a row whose height is not known at the moment it is created never adds anything up. Smaller rows only made more of them.

    So the panel draws one flat list of rows whose height is arithmetic — with wrapping off, a row is exactly one monospace line. Hunk headers, file bands and every line are rows of one list, each reporting a floor height from the start. Live cells drop from one per line to a screenful, and a bound test asserts that in all three layouts, because the fix is otherwise undone by the next feature.

    Three consequences are deliberate: the floor is a floor rather than a claim (a row settles to whatever it lays out to); wrapping is virtualised too, one line being a floor for a folded row rather than a guess at it; and the pinning moved with the rows — the header, the file band and a split pair hold themselves at the viewport's width and slide back as you scroll sideways, so the staging button stays reachable instead of riding off the right-hand edge.

    Binary, images and LFS¶

    libgit2 answers a binary delta with no hunks at all, and the panel used to draw that the only way it could: "no textual changes in this file", over a screenshot that had just been replaced. That sentence is true of every binary file that ever changed and is therefore not an answer.

    The provider reports a kind and the panel picks a renderer:

    • binary — a change with a size readout, and the reasons told apart. GitHub withholds a patch for three unrelated reasons and "no textual changes in this file" is true of all three.
    • image — a promise that at least one side is drawable. png, jpeg, gif, bmp, webp and ico, because those decode everywhere this ships and anything whose plugin is optional would draw on the developer's machine and not yours.
    • lfs-pointer — see Git LFS. A pointer is text, so it diffs perfectly well as three lines of the wrong file; the pointer question is therefore asked before the binary one.

    Three ways to compare two pictures¶

    Side by side answers "what are these" and is nearly useless at "what moved": the eye cannot hold two images a panel's width apart well enough to find a few pixels, and each is drawn at whatever scale its own half allowed.

    Swipe puts a boundary through one frame. Onion skin fades the versions into each other. Both are one frame, one scale, and the top-left origin rather than the centre — where the two versions are different sizes, centring shows both of them shifted and reads as a change to each.

    The reading is a preference, like split and wrap. Both overlays are absent where there is one picture: an addition has no "before", and an overlay would be one version drawn under a blank frame, which reads as the other having been erased.

    Nothing in the binary branch writes, and that is the answer rather than a gap: a hunk is what staging, reverting and discarding act on and there is not one, so those verbs — and the whole option row above them, every one of which is about lines — are absent, with a sentence saying so.

    Where a diff cannot be staged¶

    canStage is off for a commit's diff (there is no index behind history), a comparison, a file's history, and somebody else's pull request. Per the absent-not-greyed rule those verbs are not drawn at all rather than drawn dead.

    A forge's diff additionally cannot be re-read, because re-reading matches on the path — so a pull request touching a file also open in Changes would otherwise have the local version silently swapped in the moment a context option changed.

    What a hunk header carries¶

    Beside the @@ line: staging, unstaging, reverting or discarding the hunk; copying a permalink to the lines picked; holding the hunk back for a patch you assemble out of several commits; and on a proposal's diff, Comment.

    Comment is in the header rather than on every line for the reason the permalink is: a button per line is a keyboard entry per line, and the alphabet does not stretch to a diff. It acts on the panel's own selection, which is how staging has always worked here, and a forge takes a comment on a range — so two lines picked and one comment written is exactly the shape both ends already have.

    A comment under a line¶

    The panel takes a map from path|side|line to whatever is there, plus something to draw it with, and puts a row of its own under any line that has something under it. Two things follow: the panel stays a diff viewer, so nothing in it knows that forges exist and the same mechanism would hang a blame annotation off a line; and a thread is a row rather than something inside the line's cell, because a thread's height is only known once it has laid out, and as a sibling it reports the same one-line floor a wrapped row does and grows past it. A test builds five hundred threads and asserts the list still holds a screenful.

    The whole diff in one scroll¶

    A file at a time is the right way to review a file and the wrong way to read a proposal, and both readings exist. The combined one is every file's hunks in one scroll, in file order, with a band naming each file as it goes past.

    It travels as one hunk list with a marker entry carrying a file where a hunk carries lines — the same shape a binary change already uses — which is what makes it cost nothing to draw: one list builds only the rows near its viewport, so a 200-file diff realises incrementally, and the highlighting, the split and wrap preferences and the intra-line marks all apply for free.

    Two things about it are load-bearing. Every hunk carries the path it came out of, because the extension changes as you scroll and without it a column of Python, YAML and C++ would all be highlighted as whatever the first file happened to be — worse than no highlighting, because it is confidently wrong. And a file the forge withheld a patch for keeps its band and its sentence rather than dropping out: a whole diff that quietly omits three files is worse than no whole diff, because the omission is invisible to exactly the reader relying on it being whole.
