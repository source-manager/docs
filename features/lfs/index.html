    Git LFS¶

    Licensing — Free. Pointers, the probe, fetch, checkout and the locks. What a licence adds

    A path matched by a filter=lfs attribute is committed as a pointer — three or four lines naming an object stored somewhere else — and the real content is fetched separately. Everything here follows from that one sentence: a diff of a pointer is not a diff of the file, a checkout that never fetched holds pointers rather than content, and a row that says nothing about it is a row claiming a 40 MB video is a 130-byte text file.

    Reading needs no git-lfs; writing does¶

    Whether a path is LFS-managed is answered through libgit2 reading the same .gitattributes git reads, with the same precedence and the same subdirectory rules. That is worth having for its own sake — a reimplemented glob matcher is one more thing to be subtly wrong about — and it is worth more for what it buys: every reading feature works on a machine with no git-lfs installed at all.

    Only the verbs that move objects need the program. With none, the tab draws the state and the sentence rather than controls that cannot work.

    A pointer is the whole format, never its first line¶

    The cheap test — "the first line mentions git-lfs" — would draw a document about LFS as a file whose content is missing. So a pointer must be a version line first, then key/value lines with an oid and a size among them and nothing that is not a line of that shape, bounded at 1 kB: a pointer is small by definition, and reading a gigabyte to find out it is not one is the cost being avoided.

    In the diff¶

    The pointer question is asked before the binary one, because a pointer is text — the binary tests both say no, and libgit2 produces a perfectly good three-line diff of oid sha256:… under the name of a file you believe you are looking at. Nothing about that reading is broken, which is what makes it worse than a failure.

    The entry carries the size the pointer names rather than the pointer's own hundred-odd bytes: reporting a replaced video as a forty-byte change is the wrong number drawn in the right place.

    One side not being a pointer is its own piece of news. A file moved into LFS and one taken out of it each get their own sentence rather than both reading as "the object changed" — those are the two changes somebody is most likely to be looking for an explanation of.

    On a file row¶

    Three answers and not two:
    (nothing) LFS does not manage this path
    LFS The real file is here
    LFS ↓ This is still a pointer — the objects were never fetched

    "This is not an LFS file" and "this is an LFS file that is not here" are opposite pieces of news, and a boolean draws them alike. It is a word rather than a tint, because colour is never the only channel and here the two states it can be in are ones no amount of tinting separates for somebody who has not been told there are two.

    It is asked per row, which is affordable because the list is virtualised: only a screenful of rows exists at a time.

    Fetch and check out are two verbs and never one¶

    A fetch fills the local object store and leaves every file exactly as it was, so somebody who ran only that would see nothing change and reasonably conclude it had not worked; a checkout writes only what has already been fetched. Folding them into one control would make the cheap local step inherit the expensive network one's failure mode — which is the argument the submodule tab's Init and Update already make.

    Neither is ever automatic. An LFS fetch is a transfer of possibly several gigabytes, and nothing here spends that because a surface was opened.

    Both are absent with no git-lfs, and the sentence under the list says which half is missing rather than reading as "LFS does not work here".

    Tracking a pattern¶

    The exact line is on screen before it is written, and the file is appended to — so a comment, a section or an order somebody chose cannot be lost to a rewrite even in principle. The line ending is copied from what the file already uses, a missing final newline is made good in front of the new line, and the whole thing is taken back out if it did not land in full.

    Untracking appends too, and this is where the app deliberately does something other than git-lfs. git lfs untrack deletes the line, and deleting a line means rewriting the file — which is exactly what the append-only rule exists to protect against. Within one .gitattributes a later line overrides an earlier one per attribute, so <pattern> -filter -diff -merge is git's own spelling for "stop applying that".

    The cost is stated rather than hidden: the file grows, and both lines are visible in it. So the list reads the order — the last mention of a pattern decides — and a superseded row is still listed, saying "no longer applied", because it is there and a list that dropped it would be describing a file you can open.

    That is also why lfs track has a printed git command and untracking has none: git lfs untrack does something else, and printing it would teach a command that produces a different file.

    Tracking needs no git-lfs and the two object verbs do, so the Track button is drawn whatever the probe said. A repository can perfectly well declare its LFS patterns on a machine that cannot yet move the objects, and refusing to let it would be this app deciding what may be installed tomorrow.

    Locks¶

    Read from the server, so they are asked for and never guessed at — and read only when you press Read locks, which is the fetch's rule for the same reason. An empty map draws no badge rather than "nothing is locked": those are different claims and only one is knowable without asking. The state is idle / reading / ready / failed, because an empty map means all four otherwise.

    The verifying form of the listing is used rather than the plain one, and the difference is the whole feature: the plain listing carries an owner's name, which is not the question — two people can share a display name, and "is this mine" is what decides whether a verb is offered at all. The verifying form answers two arrays, and which array an entry is in is the only thing that says whose a lock is. A server that will not verify is a failure with a sentence rather than a column of rows nobody can act on.

    Somebody else's lock is refused, and there is no force. git lfs unlock --force exists and is deliberately never passed: a lock is a claim somebody made about work they are doing, and an app that makes breaking it as easy as honouring it has implemented the opposite of the feature. The refusal names who, since "it is locked" leaves you nowhere to go and "kate holds it" tells you what to do — and the menu row is absent rather than refusing, because what you see instead is her name on the row itself.

    A patch of LFS files says so before it is sent¶

    What travels in a patch is the pointer rather than the content, so it applies cleanly on the far machine and leaves somebody with a hundred and thirty bytes of metadata naming an object they may not have — a patch that "worked" and produced no picture.

    Every patch route inherits a count and a sentence naming what the recipient will still need. It is a note and never a refusal: the patch is valid, the button stays live, and what is wrong with it is on the other machine.

    The fleet says nothing about LFS, and that is a decision¶

    What was asked for is a card that reports a checkout with unfetched objects, and the answer cannot be had from what a fleet summary already reads: "still a pointer" is a file read per managed path, per repository, across every repository in the fleet. That is exactly the cost the fleet page is designed to refuse.

    The tempting substitute is worse than the absence: a root .gitattributes naming filter=lfs is cheap, and it answers "this project uses LFS" — which is not the question. Drawn as an LFS badge on a card, it would be read as "something here needs fetching", which is true of a checkout that has never fetched and false of every properly checked-out one, with no way to tell from the card which kind you are looking at. A badge that is right by coincidence on some cards is worse than no badge.

    The figure lives on Manage's LFS tab, where you have asked about one repository and the walk is affordable.

    With no git-lfs, a commit warns and is allowed¶

    That is git's own behaviour and this app does not improve on it: with the filter absent, git writes the file's content whole where a pointer should have gone. Refusing would be this client inventing a rule git does not have.

    What it must not do is repeat git's silence, because the result is a commit that looks right, pushes, and has to be rewritten — so the warning says what was written and what it will cost, and it warns afterwards, because that is when it is true.
