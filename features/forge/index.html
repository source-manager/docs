    Pull requests and CI¶

    Licensing — Paid. Reading is forge; proposing, reviewing and labelling are forge-write; GitLab and Bitbucket are forge-providers; permalinks are forge-links; writing while the forge is unreachable is offline-comments. What a licence adds

    Pull requests, reviews and CI results come from whichever forge hosts the remote, behind a provider seam the interface never looks past.

    Forge Reads Writes
    GitHub everything proposals, reviews, comments, labels, reviewers, repositories
    GitLab ‡ everything but check runs and a review decision proposals, reviews, comments
    Bitbucket Cloud ‡ everything but per-file patches nothing

    ‡ Fixture-proved and never live-proved: the tests pin the URLs built, the JSON mapped onto the documented fields, the errors told apart and what the transport will and will not let through. No live instance has ever answered.

    Self-hosted instances work, including GitHub Enterprise, GitLab on your own machine — see declaring a host.

    None of this is git transport. Moving objects is a different protocol with a different credential, and nothing on these two surfaces fetches, pushes or pulls anything.

    What the app may write, in one list¶

    Ten endpoints, spelled out in one array in the transport, and a provider cannot add one:

    • Submit a review, and send one that was already begun
    • Comment on a line, and take that comment back
    • Append a comment to the review being written, and throw that review away unsent
    • Open a proposal, ask for a review, put labels on it
    • Create a repository under the signed-in account

    There is no PATCH and no PUT. So nothing retitles, re-bases, closes or merges a proposal; nothing dismisses somebody else's review or rewrites the body of one; and nothing replaces the reviewer or label set somebody else chose — a POST on the labels path adds where the PUT on the same path would replace.

    No read path writes at all, and that is asserted rather than promised: a test drives every read there is — both diff readings, a re-read, both refreshes, a whitespace switch — with a draft open the whole time, and requires the write log to come back empty.

    Nothing writes without a user action. Nothing on a refresh, nothing on a timer, nothing as a side effect of reading.

    The one row that names no operation

    Nine rows name one operation each: read the pattern and you know what may happen. POST /graphql is a single URL behind which every mutation GitHub has lives, and which of them a request performs is decided by a body nothing in the list inspects — so for that row, "what may this app write is answerable by reading one array" is false, and no arrangement of the array makes it true again.

    It is there because the review being written moved onto the forge and REST cannot append a comment to a pending review. The alternatives were a delete-and-recreate on every keystroke, or keeping the draft local. What stands in the guarantee's place is narrower and asserted rather than promised: exactly one mutation is spelled in this app, from a fixed template with its arguments as typed GraphQL variables rather than text spliced into a query, and it is sent only from a control somebody pressed.

    A GraphQL read — the review decision, and the id lookup — goes down its own channel with its own allow-list, and the document is checked: it must be a JSON object whose query begins with the query keyword, carrying no operation name, and containing the word mutation nowhere at all. So the one thing the write row cannot promise about itself, that channel does.

    Every state is a state, not an empty list¶

    no-repo, unsupported, unconfigured, idle, loading, ready, failed — and the surface renders the ones that are not a list.

    An empty list is only ever allowed to mean "this repository has none." Rendering "no token" or "the forge said no" the same way is how a network feature earns its reputation for lying.

    A forge that cannot answer a question refuses with a sentence rather than an empty list. GitLab has no per-commit check concept, so check runs there is Unsupported with a sentence naming the Runs page — that repository's pipelines work perfectly.

    A token is read, never kept if it can be helped¶

    GH_TOKEN, then GITHUB_TOKEN, then gh auth token (asynchronously, and only once a surface asks, so an app never pointed at a forge never shells out), then a token typed into the app.

    That last one lives in the settings file in plain text and the surface says so in as many words, because somebody choosing it deserves to know before rather than after. No token is logged and none reaches an error message.

    With no token nothing is requested at all, since an unauthenticated call to a public repository works and then stops, mid-session, at sixty requests an hour.

    Signing in through the browser¶

    The OAuth device flow — the only mechanism a desktop app can honestly use, since an authorisation-code flow needs either a client secret it cannot keep or a loopback socket it cannot count on. It honours the server's polling interval and keeps a raised one.

    This build ships no client id, because one belongs to whoever registered it. Register an OAuth app, enable device flow, and supply the id through an environment variable or the field the panel offers — "no client id" is a first-class state with instructions, exactly as "no token" is.

    The granted token joins the same order and lands in the same unencrypted settings a pasted one does. The browser removes the copying, not the storage.

    Declaring a host¶

    A host resolves to an instance — which software is there, and where its endpoints are — rather than straight to a class. That is what makes GitHub Enterprise and a private GitLab work: the same class, against <host>/api/v3.

    Four things about it are load-bearing:

    • The URLs are derived from the host, never typed. You declare a host and which software runs there — the two facts nothing in a remote URL can say — and the rest is worked out. Three fields would let somebody point the API at one machine and the browser links at another, which is a phishing shape rather than a configuration.
    • The write allow-list is derived rather than written out. Declaring a host widens where this app may send a body, which is exactly what declaring one is for — and the operations are still fixed: nothing typed into a settings page adds a verb, changes a method, or reaches a path no provider was written against.
    • Everything that is not a bare host name is refused rather than repaired. A scheme, a port, a path, userinfo, a wildcard: each is a way to make one URL look like another once it reaches a derived pattern. A stored row is vetted on the way in exactly as hard as a typed one and dropped rather than fixed up, because the settings file is text somebody can edit and this is the one setting that widens where a credential may be sent.
    • The sign-in panel says which instance is in force, above everything and not optionally. What is about to be pasted is a credential, and "Sign in with GitLab" drawn over somebody's private instance is the one sentence that panel must not print.

    Declaring a host lives on the sign-in panel rather than the settings page for that reason: it is the one control in the app that widens where a credential may be sent, and the panel that hands the credential over is where that belongs.

    What is kept, and asking again is a decision¶

    Every answer goes into a cache under a key naming the question — pulls:owner/name, checks:owner/name@<sha>, detail:owner/name#12 — which is what makes the two verbs different:

    • Load serves what is held and fetches only when nothing is.
    • Refresh means spend a request now, which is what Reload does.

    The slug is in every key, so switching repository invalidates nothing and coming back is free; the commit is in the checks key because HEAD moving asks a different question rather than staling the old answer.

    On GitHub a refresh is cheap as well as explicit: a conditional request earns a 304 that does not count against the rate limit — and a tag is kept only for an answer that arrived in one page, since it identifies one URL and a list assembled from three is not revalidated by the first being unchanged.

    Answers outlive the process, in a database beside the settings, and a stored list is served labelled and refreshing: "stored, read 14h ago · refreshing". Serving one spends the request that will replace it, so the screen is instant and converges without anybody waiting in front of a blank one. What was never acceptable is a stored list wearing a live one's face, and that is a different thing from serving one that admits what it is.

    A failed refresh keeps what it failed to replace. The state stays ready and the refusal is drawn beside the list rather than instead of it, because "showing what was read yesterday, and today's attempt failed" is a state, and a more useful one than an empty frame with a red box in it. That is also why a missing token no longer folds a list already on screen into "unconfigured": signing out should stop the fetching, not erase the reading.

    Signing out is a hard forget — memory and disk both — because a private repository's proposals sitting on disk after the account that read them was forgotten is exactly what somebody pressing that button is asking not to happen. It forgets answers: there is no column a token could occupy, and a test reads the file's bytes back.

    A repository leaving the fleet takes its rows with it, by both path and slug: the path is exact and survives the directory's deletion, the slug catches what a second checkout of the same project overwrote the path of.

    The proposal list¶

    Number, title, author, state, branches, labels and awaited reviewers draw immediately; selecting one adds the description, the counts and the assignees; two more requests add the files and the reviews. Each wave has its own state, so the panel draws what it holds and says what is still coming. Commits are a fourth request spent only when asked for.

    A row before it is opened¶

    The state is on the number, in the four hues every forge's own web UI uses — green open, grey draft, the accent for merged, the failure hue for closed-without-merging. Somebody who has read a proposal list before does not have to learn this, and the tooltip names the state in the forge's own word, which is the only thing separating merged from closed for the one person in twelve who cannot separate the hues.

    Which of the four it is comes out of three fields, and the order they are asked in is load-bearing: state is only ever "open" or "closed", a merge is a closed one with a timestamp, and a draft is a flag. GitHub leaves draft set on one that was closed while still a draft, so asking about the flag first filed an abandoned draft as a draft — drawn in the grey that means "not finished yet", filed under the Open chip, and counted as open by the waits reading, which then flagged it for having waited months on a decision that had been taken.

    The size is a band, not a figure. Five bands over four colours: XS and S share one, because "small enough to read now" is a single answer; L and XL do not, because that is exactly the pair somebody is choosing between when deciding what to pick up before lunch.

    The size genuinely is not in a list — a forge fills the counts only when one proposal is asked about by name, so "a size on every row" is a request per row. They are spent lazily as rows scroll past, capped at thirty per list and never without a token, and the answer lands under the same key the panel and the metrics sample already use, so a proposal is bought once ever including across launches.

    The state matters as much as the figure: a blank column reads as "this proposal has no size", which is the one thing it never means, so a row draws a figure, an ellipsis or an em dash — with a sentence under the list, once the ceiling is actually reached, saying why the dashes are there. A ceiling nobody can see is indistinguishable from a bug, and this one is reached by scrolling, which is exactly the gesture that would make somebody wonder.

    The row bands the forge's raw total and the panel bands a counted one — with lockfiles and vendored directories set aside — so the two legitimately disagree about which letter a proposal earns. What they must never disagree about is what L means, which is why one component draws both. The tooltip says which arithmetic this is and that opening the proposal buys the other.

    Labels arrive with the list and were simply never drawn, which is the odder gap of the two, because the search box and the whole filter vocabulary already match on them. They are capped at two with the rest counted: a repository whose convention is eight labels a proposal would otherwise push the author and the branch off the end of the line, and those are the two facts that tell two similarly-titled rows apart.

    Sorting¶

    By creation or by update, created by default because it is the only one of the two that is stable: ordering by update time alone reorders the page under you while you are reading it, and a row that was third yesterday is fifteenth today for reasons nothing on screen shows.

    It is remembered, and the chips are drawn as their own labelled pair rather than beside the filter chips — a filter decides which proposals are here and a sort decides where each one sits, and one row of identical chips would make the exclusive-group rule read as covering both.

    Filters are a vocabulary, not four chips¶

    A filter is a name and a list of conditions over the documented fields, all of which must hold. The four state chips are built-in filters in that same vocabulary, differing only in being code and in declaring an exclusive group.

    A filter's definition travels everywhere its name does, because a filter is named by its author and a name is a claim. Everything is evaluated over what was already fetched, so the surface says when the fetch stopped at the provider's ceiling — "3 match" must never read as "3 in this repository".

    Two review fields that are each half of a qualifier¶

    This is the part of the vocabulary that was reported three times, and each report was about a different half:

    Field What it is Wrong about
    awaited reviewers The forge's review-requested: — who is on the hook right now A forge drops somebody the moment they answer, so a proposal whose reviewer objected has an empty list and is still owed a review. Lists fewer rows
    Merging requires a review The base branch's protection Knows nothing about approvals, so a proposal already approved still demands one. Lists more
    Review outcome so far The forge's own decision — required, approved, changes-requested, none, unknown Only the forge can put the two together

    The labels are the third fix. "A review is required", offered beside a "Review decision" whose values include required, reads as two spellings of one thing — and somebody who picks the wrong one gets a list that is right and unexplained. Each one's caveat now points at the other, and the pair is asserted against the labels rather than against literals, so a rewording cannot leave two sentences naming fields that no longer exist.

    unknown is a real answer and a common one: reading branch protection needs admin rights on some repositories and a forge answers 404 both for a branch with no protection and for a token that cannot see the protection it has. Reporting it as "no" would quietly drop every proposal on a repository you merely lack a scope for.

    The decision costs one round trip for the whole list — which is why it exists at all, a field on every row not being buyable a request per proposal — and only the open proposals are asked about, that being the only state the question means anything in.

    Other things worth knowing about the vocabulary¶

    • @me resolves at match time, and a saved filter keeps the word rather than the name, so the same filter means the right thing under a second account. An empty login matches nothing, including under the negative operators — not @me with nobody known would be "not nobody", which is everything.
    • state anyOf open excludes drafts, which is the vocabulary rather than an accident: a draft's state is draft, so this clause is the forge's is:open draft:false. A filter wanting both says state anyOf open, draft.
    • "Someone is awaited" counts teams, and naming a login matches people only. A review asked of a team and nobody else is a proposal with somebody awaited, but putting a team in the people list would make "waiting on kate" quietly true of a proposal awaiting a team kate happens to be in.
    • The whole vocabulary is documented in the editor — every field carries one line saying what it is, in a glossary fold beside "Add condition", plus the longer caveat printed under the conditions when that field is in use. Two separate strings on purpose: a glossary of paragraphs is not scanned, and a warning buried among a dozen definitions is not read.
    • A saved filter and a state chip are exclusive, and two saved filters are not. A saved filter is a complete question in a vocabulary that already contains state, so leaving Open lit beside it ands in a condition its author did not write — and a saved filter that "finds nothing" because of the chip nobody looked at is the commonest way one appears broken. Turning off the last thing in force falls back to All rather than Open.
    • A typed query is not a filter. Three characters you are holding in your head for ten seconds live on the surface rather than in the vocabulary, and both hold at once. It is reset when the surface is built, unlike the filters: a list narrowed by a query nothing on screen is showing would be a bug rather than a choice.

    The list was short, and there were three reasons¶

    Worth recording because the fix took three passes:

    1. Teams were dropped from the awaited list, so on a repository whose convention is review teams that was most of the rows.
    2. The window was full of closed proposals — the list is bounded at five pages, and that ceiling is reached by merged ones, so an open proposal nobody had touched in a month was not in the data any filter ran over. The open ones are fetched on their own now, sorted by creation ascending because that pass exists to be exhaustive.
    3. review:required is not the awaited list, which is the part no amount of fixing a clause could reach — see the table above.

    The strip along the foot of the window¶

    A saved question is worth more than the page it was written on, so it earns three routes: a count on its tab's badge, a watch, and a chip on the strip along the foot of the window — which is drawn on every surface, so a count you want in the corner of your eye survives walking to Changes, to History, to the fleet and to Settings.

    A widget there is a filter and a kind — a proposal question, a CI question or a ticket question — so a chip is the filter answering for itself. Pressing one goes to that list with that filter in force.

    Nothing on the strip fetches. A list this window has not read draws — and never 0: a zero is a claim that there is nothing, and the strip is the last place that should be guessed at. The counts follow each list's own change signal, so they move when the page they belong to is read.

    The strip is absent until you add a chip, kept per checkout in .git/config, and the order you put them in is the order they are drawn in. A chip whose filter has since been deleted is kept and says so, rather than vanishing with the question it was asking.

    Which proposals have been waiting too long¶

    Three readings rather than one "stale" flag, because the three ways a proposal gets stuck have different people on the hook:
    open Opened, and still open
    approval Open, and nobody has approved it
    merge Open, approved, and still not merged

    Collapsing them would report one figure to the reviewer who has not looked, the author who has not merged, and nobody in particular — which is how a badge comes to be ignored.

    Mode and value are per reading. The values are on different scales — a fortnight open is ordinary and a fortnight approved-and-unmerged is not — and the mode does not transfer: "above the team average" is a meaningful reading of review latency and nearly meaningless of "open too long", where a mean is dragged by whichever proposal somebody abandoned.

    In average mode the value is a multiple of the mean, defaulting to 1.5 rather than 1.0, because these distributions are right-skewed and a mark that fires on a third of the rows is decoration. Below eight observations the average mode does not answer — not a statistical threshold, there being no honest one for a mean over whatever the forge last changed, but the point at which one abandoned proposal stops being a quarter of the answer.

    The two review-based readings can only be computed for a proposal whose reviews this app happens to hold, so such a row is unjudged, drawn as ?, and counted separately — which is also why those two are off by default: switching one on is the moment somebody accepts a column that mostly says "not read yet", where the open reading needs only the list.

    A row draws one mark and the most actionable wait wins — merge, then approval, then open — because a proposal that is agreed and sitting there needs one press from somebody already convinced. Colour says only look at this, and the four glyphs carry which.

    Nothing here costs a request: the verdicts are recomputed over the list in memory and the reviews already held.

    CI has two questions¶

    Neither list answers the other, and the sentence under the chips saying which is on screen is the load-bearing part — the two lists look alike, and somebody who takes one for the other will conclude their own commit passed on the strength of somebody else's push.

    Page What it holds
    Runs What the forge's own CI has been doing — a run of a workflow, on a branch, with an event behind it, holding jobs holding steps
    Jobs What any CI reported against one commit — the honest question, and the only reading that works for a repository built by something that is not the forge's own CI

    Runs is the page that opens, which reverses what this surface used to do. The old default was the reading keyed to what is checked out; the trouble with it is that a commit's checks are empty far more often than CI is idle — nothing is pushed yet, the fetch is stale, the work is on a branch the forge has not seen — so the page opened on a blank list on a repository whose CI had run forty times that week.

    The keys differ in what they carry, and that is the whole design: the checks key moves with HEAD and the runs key does not, so committing re-asks one and leaves the other alone.

    Jobs are one request per run, bought when a run is opened and never for the list — and served outright rather than served-and-refreshed, which is the one place in this layer that is right: a finished run is immutable, and asking again would spend a request to confirm something that cannot have changed.

    A run is opened rather than unfolded. In-place expansion works for the two or three jobs of an ordinary build and stops working exactly where you need it: a matrix build is twenty rows pushed in under one, and the list you were reading has lost its place.

    A verdict is a colour and a shape, and the palette is broken here on purpose — everything else in the app is one accent and a neutral ramp, because "is anything broken" is the entire question this tab is opened with and a column of identical marks answers it only to whoever stops and reads each one. Three rules keep it from becoming a second palette: colour is never the only channel (every verdict keeps its own glyph and a tooltip naming it); four verdicts, not nine; and the hues are tuned for this ground rather than taken off a stock palette.

    A duration column falls back to the status only while there is still something to be doing — never "how long since it started", which would report a queued run as having taken four hours. But a skipped check is completed with no timestamps at all, so the fallback printed the word "completed" under a heading whose every other value is a length of time. A finished thing with no duration took no time, and nothing is the honest figure there.

    Proposing one¶

    From the Pull requests surface for the branch that is checked out, from a branch row's ⋮ for that branch, or from the comparison page with the left as the base and the right as the head.

    The proposal is the operation; the other two are courtesies. Asking for reviewers and putting labels on are spent afterwards, on a number only the first request can supply, and a failure in either leaves the proposal open — reported as a notice rather than an error, because calling that a failure would report a success as one and this app has no verb for taking a proposal back. Somebody told "it failed" would go looking for a proposal that is sitting there open.

    draft is sent both ways round rather than omitted when false. A repository whose plan has no draft pull requests answers 422 for true, which is a refusal you can act on; omitting the field would quietly open a proposal that is ready for review when a draft was asked for.

    The push is a tick, default off, and the surface owns the order. A forge cannot open a proposal for a branch it has never seen, and getting it there is git's side of the house — so the dialog offers the tick, the surface pushes and waits, and the proposal is opened only if the push landed. A proposal of half a branch is worse than a refusal, and nothing leaves the machine because a dialog was opened.

    What is prefilled comes from the commits it would land: one commit gives its subject and body, several give the branch's name and the list of subjects. Anything else is a form filled in twice.

    The template a proposal starts from¶

    A repository that carries a proposal template expects every proposal to start from it, and this app opened its dialog with a description assembled from the commits — so a project with a checklist got one that skipped it, silently, every time.

    They are read off disk and not fetched. The file is already in the working tree: reading it costs no request, needs no token, works offline, and — the part that decides it — is the same file the forge would use, so what this app prefills and what a browser prefills cannot come to differ. The cost is stated: a checkout that has not fetched the commit adding a template does not have it.

    Where they live is the provider's — GitHub looks in three directories under two spellings plus a directory of several; GitLab has only a directory and no single file at all; Bitbucket has no convention, so the picker is absent.

    The first single file wins and the rest are ignored, which is the forge's own resolution: a repository carrying two has exactly one as far as anybody else is concerned. A directory contributes all of its templates, that being the whole point of the form.

    The picker is absent below two: none at all, and one — a repository that has already made the choice, where a picker would only ever say what happened when the dialog opened. "None" is the first row rather than the last, because its position must not depend on how many templates a repository happens to have, and choosing it restores the commits' prefill rather than emptying the box.

    The title stays the commits' — a template is a description and says nothing about what to call the thing.

    A link somebody else can open¶

    A url to a file, at a commit, at the lines that are picked — for pasting into a chat message or a ticket, where it will be read days later by somebody who was not there.

    It is keyed to the commit and never to a branch. That is the whole reason it is a verb here rather than something you assemble from the repository's front page: a link naming a branch means a different file every time anybody pushes, and this one goes on meaning the same lines next week.

    The shape is the provider's, because GitHub writes #L4-L9 and GitLab writes #L4-9. A forge with no such page leaves the capability false and the verb is absent rather than copying an empty string to the clipboard.

    It costs nothing and asks nobody. A link is a string: no request, no token, and it works on a signed-out repository with a remote.

    Three verbs because there are three questions: the file header's copies a link to the file as this commit left it, the diff's hunk header copies one to the lines picked, and Blame's copies one to the lines picked there — keyed to the commit the file was read at, resolved from whatever was typed in the revision box, because "HEAD" means a different file every time anybody pushes.

    The new side's numbers, and nothing invented. A selection of removals alone has no line to point at in that revision — those lines are in the parent — so it falls back to linking the file rather than pointing somebody at a line number that means something else there.

    What was copied is printed for a few seconds rather than toasted, because somebody about to paste a permalink into a channel can see which commit and which lines they are about to claim, which "Copied!" would not tell them.

    A ticket id, and the page it names¶

    Everything a commit message says about why tends to be one token long — #412, PROJ-88 — and the rest of that reasoning is on a page this app is not.

    A rule lives in .git/config, not in the app's settings: which tracker a repository files its work in is a fact about the repository — the same in every checkout of it and for everybody who works on it. Per checkout rather than committed because .git/config is not cloned, which is also what makes a stored rule safe to act on.

    The forge supplies one by default, so most repositories need no setup: #123 against whichever tracker hosts the remote. It is a template rather than one url, because an issue link is a rule — something that turns a token in prose into a page — and the shape is the provider's, GitHub writing /issues/123 and GitLab /-/issues/123.

    A rule written by hand outranks it, which is why the default is ranked last: a repository whose # means a ticket in somebody else's tracker says so in its own config, and a default that outranked it would be this app overruling a statement somebody made deliberately.

    A Jira/Linear-shaped id (ABC-123) is recognised out of the box once it has somewhere to go — matching the shape costs nothing, and what this app cannot do is guess where it points, since the same id means two different companies' trackers. So the shape is built in and the destination is one line you write once. With no destination there is no rule at all rather than a rule with an empty url.

    Two things about git's config syntax fail silently and are therefore stated everywhere: # opens a comment there, so an unquoted #([0-9]+) is an empty pattern; and a backslash is an escape, so an unquoted \b is a backspace character. Neither arrives as an error, and the symptom is no link at all — which is exactly what a repository with no rules looks like. Writing a rule from the settings page quotes and escapes it, so the trap stops existing for anything typed there; what the page still draws is which rules are in force, which came from the forge, and which were dropped and why.

    Only http and https are allowed, checked on the template before anything is drawn: the answer is handed to the desktop, and a file: or a javascript: there is a different kind of thing entirely. The capture is percent-encoded on the way in, since a loosely written pattern capturing a space is the ordinary way a rule produces something that is not a url.

    Somebody else's Markdown¶

    A proposal's description, a review's body and a comment on a line are all prose somebody typed into a forge, and one component draws all of them.

    Images are stripped before the text is parsed, and this is not a nicety: Qt's Markdown renderer loads images and has no switch for turning that off, so an ![](https://…) in somebody else's description would make opening the panel a read receipt delivered to whoever wrote it, from a private repository, with your address on it. A line saying an image was there replaces it — refusing to fetch and refusing to say anything are different things. A badge is a linked image, so the picture goes and the link stays.

    Blocks rather than one text item, because Qt's importer gives a paragraph no margin at all and there is no property for block spacing — so a description of any length reads as one wall. The source is cut into top-level blocks and the layout puts the space between them, which is also what lets a fenced block sit on a ground of its own.

    The splitting is conservative on purpose: a fence is atomic, a loose list stays one block (cutting at the blanks would make each fragment its own list and restart the numbering at 1), and a construct it does not recognise is passed through whole. Nothing is dropped, and a test walks the input back out of the blocks.

    A numbered list that does not start at 1 cannot interrupt a paragraph, which is CommonMark rather than a Qt fault and is the single commonest way a description renders wrongly: somebody writes a sentence and then a list beginning "2.", and the whole thing comes out as a run-on paragraph with the numbers inline. A blank line is inserted.

    A GFM table is laid out here, because Qt parses one and will not draw it — every column collapsed to the width of its own content with no padding, readable only by somebody who already knows how many columns there are. The parse is bounded at where the pipes fall: a cell's content is handed back as Markdown for the renderer to draw inline, so emphasis, code spans and links go on being somebody else's parser's business. The overflow is the table's own rather than the panel's, so one wide table in the middle of a proposal does not put a horizontal scroll bar under the whole of it.
