    Remotes and transport¶

    Licensing — Free. Fetch, push, pull and clone, and the credential ladder behind them. What a licence adds

    The four verbs that move objects — fetch, push, pull, clone — plus the remotes themselves, one credential ladder, and a background fetch that is off by default.

    None of this is the forge integration. Reading pull requests and CI happens over HTTP with a different credential and moves no commits; see Pull requests and CI.

    One operation at a time, off the interface thread¶

    Each of the four is a single blocking libgit2 call, and each runs on a thread of its own. Two at once is not a slower version of one: it is two remotes on one repository, two threads writing one object database, and two sets of progress figures arriving at one banner.

    So there is a lock, and it is on the object that owns both halves of transport rather than on either controller — a lock owned by one of them is a lock the other consults by arrangement. The bar binds to one property rather than composing a fact out of two, which is what stops it going stale the day a fourth verb lands somewhere else.

    A pull's own fetch is not a second operation: a pull is a fetch and then an integration, called through the sibling rather than reimplemented, so the lock lets a fetch through while a pull holds it. Without that one exception the feature deadlocks against itself on the first press of Pull.

    Only the fetch half is threaded; the merge or rebase runs back on the interface's thread, because both write the index and the working tree and every controller that re-reads off them lives there.

    A verb returns "accepted", and a refusal is still synchronous. Everything decidable without contacting anything — the lock, a build of libgit2 with no threads, a detached HEAD, a non-fast-forward against the tracking ref, a lease with nothing to lease against, a destination that is not empty — is decided before a job starts and reported in the same turn.

    A libgit2 with no thread support is a refusal rather than a fallback: running inline instead would be a second code path nobody exercises, guarding against a state whose other symptom is a corrupt object database found weeks later with nothing to connect it to.

    Progress is in the banner¶

    A row of its own rather than a fifth mode, because the four modes rank against each other (only one can be true at a time) and that argument does not reach a transfer — HEAD can be detached while a fetch runs, and a rebase can be stopped while somebody pushes another branch. Ranking a transfer into the same slot would let starting a fetch hide a stopped rebase.

    A negative fraction — libgit2 has not been told the object count yet, and never is for a local clone — fills the track with a faint wash rather than leaving it empty, since an empty bar beside the word "Fetching" reads as a transfer stalled at zero.

    Cancelling is never gated. Each controller's destructor sets the flag, waits and deletes the job, so quitting during a transport that will not answer is waited out — which is the honest price of it.

    The transport buttons grey rather than disappear while one is running, which is a deliberate exception to the absent-not-greyed rule: "wait ten seconds" is not "this repository cannot do that", the verb is the one about to be pressed again, and taking the three off the bar moved every remaining control sideways at the moment somebody was aiming at one.

    Fetch¶

    With progress, cancellable, and with prune as both a habit and a one-off.

    Whether a fetch removes the tracking refs for branches the server no longer has is one setting with one home and one reader — three routes to a fetch and a flag at each of them would be three places for one choice to be spelled.

    What that has no room for is the occasion: a forge full of merged branches cleaned up under somebody who does not prune by habit, or somebody who does and wants this one fetch to leave a colleague's refs alone until they have read them. So a caret beside Fetch offers the choice this once, and its rows say which of them the button would do — a menu offering "Fetch" beside a button reading "Fetch" has to say what the difference is, and the honest answer is "none, this time".

    Cancelling happens inside the transfer callback and nowhere else: libgit2 is inside a blocking read, so a non-zero return from the callback is the only thing that makes it unwind. A cancelled fetch is not reported as a failure — the object database is consistent either way, git simply has fewer objects than it might have.

    prune() on its own was removed rather than fixed

    It could not have worked: libgit2's prune runs against the ref list a connection populates, so on a remote nothing has connected to it has nothing to compare against and prunes nothing. Nothing in the UI ever called it, which is exactly why that was never found out — and around it had grown a command-line spelling and a "run again" branch dispatching on an id no recorder ever writes. Three dead things propping each other up. git fetch --prune is the honest spelling.

    Push¶

    Push always means push. The button used to replace itself with "Force push (with lease)" whenever the upstream had moved, which was wrong twice: the swap answered once and then went deaf while HEAD and the upstream moved under it, and it made the only push control on screen the forcing one at the moment forcing is dangerous.

    There is one Push, it refuses in its own words, and both ways past that refusal are behind a caret beside it — a second, deliberate gesture.

    Verb What it checks
    Push Refuses a non-fast-forward and stops. However many times it is asked
    Force with lease Against what the far end says it holds right now — a live ref listing compared with the remote-tracking ref
    Force Nothing

    Three named entry points, no boolean: a caller has to type forcePush to get one, because a flag is what gets passed wrongly in silence.

    The lease is the first row and is absent with no remote-tracking ref, saying why — a lease against nothing is a plain force under a safer name. It is checked against a live listing rather than the tracking ref, because a lease that trusted the tracking ref would be a plain force with extra steps: the tracking ref is precisely the thing that goes stale.

    The plain force is the second row, drawn in the failure colour over a wash so the dangerous one reads as such before either label is — and it is still offered where the lease is not, having nothing to lease against in the first place.

    The plain force needs a third gesture

    Choosing it opens a dialog rather than pushing. It is the only confirmation in this app for a gesture inside a menu, because it is the only operation whose damage is on another machine: everything else that writes lands somewhere you can look at it, and the operation log files every push as remote with no way back precisely because nothing here can reach over the wire.

    The dialog keeps two facts apart the way the reset dialog does: the commits that stop being reachable, and that nothing is checked. Its confirm button is deliberately not the primary — this is the one press in the app that should not be arrived at by following the highlight.

    It is also not what a retry does: "Run again" in the operation log cannot re-issue a plain force. The lease stays repeatable, because a repeat of a lease is still a lease and declines on its own.

    A push where one ref was rejected must say which. The refusal happens at two layers because they know different things: a plan compares the branch with its remote-tracking ref before anything is contacted (honest, and only as fresh as the last fetch), and the per-ref callback fires once per ref the server actually considered. Reporting overall success because the call returned zero is the single most common way a git GUI lies about what it did.

    Pull¶

    --ff-only is the default, and it is a refusal rather than a mode: when the histories have diverged the pull declines and names both ways forward, having integrated nothing. The other two strategies each write a commit — a merge commit, or a whole branch replayed — and doing either because a button was pressed once is how a history acquires shapes nobody chose.

    The fetch is kept when it refuses: the commits are in the object database and the tracking ref points at them, so the safe default costs a decision rather than a download.

    A pull is a composition rather than a reimplementation — the existing fetch and then the existing merge, or the existing rebase. A second merge would be a second set of answers to conflicts, fast-forwards and merge.ff, and the two would disagree the first time one of them was fixed. A normal merge still stops, and a pull that stopped is reported as a success: the index is written and the Conflicts surface finishes it.

    An unrecognised stored strategy reads as ff-only, so a hand-edited typo declines instead of picking the destructive one.

    Clone¶

    With progress and cancellation, and on success it announces itself — the fleet registers it and the app opens it, rather than the transport reaching into a registry it does not own.

    A cancelled clone leaves nothing behind, and a flag alone cannot promise that: libgit2's local transport never calls the transfer callback, so on a file:// clone only two callbacks fire and the flag may be set at a moment when nothing is left to read it. So a clone that was asked to stop and nonetheless finished has its directory removed and registers nothing — and only a directory this call created is ever removed, recorded before the clone starts, because deleting a folder you already had is far worse than a stray clone.

    Shallow, and why there is no partial¶

    A depth dial, with shallowCost naming the four surfaces that go quiet — blame stops at the oldest commit fetched, a bisect has nothing older to search, a comparison against anything further back cannot resolve, and the graph starts where the fetch stopped — and naming git fetch --unshallow as the way back.

    A depth against a repository on this machine is refused before anything is written, and libgit2 is the reason rather than a policy: git_clone bypasses the git-aware transport for a local path, and the local transport answers a depth with "shallow fetch is not supported" — after the destination has been created and removed again, seconds into an operation somebody committed to.

    --single-branch is deliberately absent from both the call and the printed line. git implies it from --depth; libgit2 does not, so a shallow clone here fetches every branch to that depth — a larger clone than the same git clone --depth produces and a more useful one. Adding a refspec to imitate git would make the clone quieter than the command line beside it.

    A partial clone is named and never offered

    --filter=blob:none is reachable by shelling out, and doing it would produce a checkout this app cannot read: a partial clone records a promisor remote and leaves most blobs absent, expecting whoever opens the repository to fetch each one on demand — and libgit2 implements none of that. Every blob lookup would fail the moment a diff, a blame or a checkout asked for one.

    A tick producing a repository the app then could not open is worse than no tick, so the sentence saying so is drawn on the dialog whatever is chosen.

    Credentials¶

    One ladder, in order:

    1. ssh-agent
    2. An explicit key path from the settings
    3. The platform keychain, where you asked for it
    4. A token typed into the app, kept in memory for the session

    A credential is asked for through a C callback that libgit2 may call more than once per operation — once per method the server offers, and again after a refusal. Two things follow: the attempts must be counted and capped, because a callback that keeps returning the same rejected credential is an infinite loop inside libgit2 — the operation never returns, and nothing reaches the screen to say why; and which source answered has to survive the call, or the failure can say "authentication failed" but not "ssh-agent had no key for this host", which is the only version of that sentence anybody can act on.

    The keychain rung¶

    Optional, and off by default. Qt ships no keychain API, so the two routes were a third-party library that would be required by a build that works perfectly well without it, or writing both platform halves by hand. Both halves are written and neither is required: Security.framework on macOS (part of the system, so always there) and libsecret through pkg-config on Linux. With neither found the app compiles unchanged and the token behaves exactly as it always did.

    Three answers and never two, and the settings row says which:
    No backend compiled in This build has neither half
    A backend named but unavailable The code is present and the service is not — no keyring daemon, a locked session, a headless machine
    A backend in force Only this one can keep anything

    Collapsing the first two would make "install libsecret" and "start your keyring" read as one problem, and only one of them is yours to fix.

    Off means not read. A switch that stopped saving new tokens while an old one went on answering would be off in name only. And resetting the transport section puts the choice back and touches nothing in the keyring — a settings reset quietly deleting from the platform's password store would be the one destructive thing on that page.

    A stale entry costs a round trip and no more: a refused credential brings the callback straight back and whatever was typed this session is offered next. That is why this is a ladder rather than a choice.

    Both arms are compiled by CI and neither is exercised

    The Linux job installs libsecret-1-dev so that arm is compiled rather than merely written — an optional backend nothing ever builds is a guard that skips in silence. What no runner can do is exercise one: there is no keyring running and no unlocked login keychain, so the suite asserts the fallback.

    The two credential ladders stay separate. A forge token buys a list of pull requests; this one can push. On GitHub the same personal access token can serve both, which is exactly the coincidence that would make one class look right and then be wrong the first time somebody pushes over ssh to a host their forge token knows nothing about. Nothing here can hand a secret to the interface layer, and a test walks the object's own metadata rather than trusting the declaration.

    Background fetch¶

    Periodic fetch of the open repository, off by default, interval a setting. It never touches the working tree, never runs during a stopped operation, and backs off on a credential failure instead of re-prompting every cycle.

    The working tree is watched¶

    An editor saving, a build running or git in another window used to go unnoticed. The watcher supplies the missing signal and says which half moved: a file under the working directory means only the status lists can be wrong, while the index, HEAD or a ref moving invalidates the graph, the drift, the conflicts and the branch lists at once.

    The watch set comes off the index rather than a walk of the disk: one file read instead of a stat per tree entry, and everything ignored is excluded for free, since an ignored file is not in the index. Directories are armed first because they are strictly fewer and answer a different question — a directory watch reports an entry appearing or vanishing, and only a file watch reports a rewrite in place, which is what an ordinary save is.

    Three timings, and they are not the same thing: events are debounced so four hundred writes are one refresh (with a ceiling, so a running build cannot postpone it for ever); a short quiet window drops what the app caused itself, since staging already refreshes explicitly; and each automatic refresh is timed and the next held off by a multiple of it, which bounds what automatic refreshing can take from the interface whatever the repository costs to read.

    That quiet window has to outlast the platform's own delivery latency, which is a number rather than an unknown: on Linux the engine is inotify and the delay is zero; on macOS Qt hard-codes a half-second stream latency it does not expose. For as long as the window was a flat 150 ms, every staging, discard and commit refreshed twice on macOS while the identical code was correct on Linux.
