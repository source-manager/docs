    Patches¶

    Licensing — Free. Writing one, the series, and applying somebody else's. What a licence adds

    A file for a ticket, a chat message, or another machine — and one coming the other way. This and a permalink are the two things this app produces that leave it, and this is the one that carries the work itself.

    The shape is git diff, not format-patch¶

    A diff patch is one file describing a state: what is different from something else. A format-patch series is one file per commit, carrying authorship and a message so git am can replay them as commits.

    Which one you want follows from what you are sending, and that is why both exist rather than one being a mode of the other: "here is the change, look at it" is a diff, and "here are my four commits, put them on your branch" is a series. A flag would be a file whose shape depended on an argument.

    Six subjects¶

    From What the patch holds
    The working tree Everything uncommitted, or only what is staged, or the files you picked
    A stash Its tree against the commit it was taken from — what git stash show -p prints
    A branch Against a base you choose, three dots by definition
    A comparison In the reading on screen, two dots or three
    A commit git show — the commit against its first parent
    Held hunks A patch you assembled out of several commits

    They are subjects of one dialog rather than six dialogs, because what a patch is of changes and what it costs to write one does not: the plan, the counts, the empty refusal, the path field and the platform's chooser are the same questions whichever subject is in front of them.

    Everything uncommitted means everything¶

    all is HEAD against the working tree — which is git diff HEAD and not index-to-workdir: the narrower diff omits everything already staged, and a patch of "what I have done" that silently leaves out half of it is the commonest way this would be wrong.

    The scope is not remembered between openings: "everything uncommitted" is what the button's words mean, and a narrower scope left on from last time is a patch missing work nobody chose to leave out.

    Untracked files are a tick, and the count beside it is why¶

    git diff does not mention them — they are in no tree to be diffed against — so the honest default omits them, and a patch that quietly leaves out the three files you have just written is the failure this feature would be remembered for. The plan says how many are being left out, which is what makes the tick findable at the moment it matters.

    Two dots and three dots¶

    A comparison is the one subject where you picked a notation, on a page that names it in git's own spelling — so the patch is taken under that reading and the dialog states it.

    The failure this is arranged around

    A file labelled A...B that holds A..B applies, backwards and quietly, undoing the base's own newer commits on whatever machine it was sent to.

    So the branch route is a separate entry point rather than a flag: its doc comment forbids two dots and it is therefore not reachable with them. The diff itself is built in one private place, so the two routes cannot come to disagree about what a patch of two refs holds, and the plan publishes the notation it was taken under so the dialog reads that rather than keeping a second copy of the flag.

    A branch's base defaults to the branch you are standing on. It was the trunk for a while, on the reading that a patch is a thing you send and so wants a base the reader at the other end certainly has — true of that errand, and not of the gesture: the verb is reached from a branch row, and what it is reached for is "what does that branch have that this one does not", asked from the branch it is being asked from. The trunk is one press away in the picker, and the branch's upstream is a third row, which is a trap either way: it is the forge's copy of that same branch, so a patch against it holds only what has not been pushed.

    A commit's patch drops the authorship, and says so¶

    The working tree and a stash have no authorship to drop; a commit does. The dialog says so outright, because that is the fact somebody finds out at the far end otherwise, when whoever applies it commits your work under their own name and words. Replaying a commit verbatim is format-patch and am — a different file format for a different errand.

    The refusal that matters¶

    An empty patch is refused. git apply accepts a file with nothing in it and reports success, so a patch of no changes is a file that looks like it worked and does nothing wherever it is taken — the worst outcome available here. It is refused in the plan's own sentence, and the button is off before it is pressed.

    Beside it: a folder that does not exist is refused rather than created, since a patch is one file you named. The write is atomic, so a failure half way leaves whatever was there rather than a truncated patch — which would be applied.

    A patch you assemble¶

    The five subjects above are each one question with one answer, and the one thing none of them can say is "these two hunks out of the commit that added it, and the one out of the commit that fixed it".

    Hold in a hunk header keeps a hunk back; the set survives walking between commits; and writing it out produces one file. Lazygit's custom patch is the same idea and stops at one commit at a time — the crossing is the whole reason this exists.

    Six decisions in it:

    • What is held is the hunk's own patch text, not a coordinate. A (rev, path, index) triple would have to be read again to be written, and the reading depends on the context and whitespace preferences in force at the time — so "the second hunk", picked with three lines of context and written with ten, would be a different second hunk.
    • Only a hunk of a file the commit modified. An added file's patch opens with new file mode, a deleted one with the mirror, and a renamed one names two paths — every one of those a claim about the file rather than the hunk, and none true when only some of the file's hunks were picked. It refuses and points at the whole file's patch, which is what somebody asking about a new file wanted anyway.
    • A path held from more than one commit is a note and not a refusal. Two commits' hunks of one file are measured against two different versions of it, so they do not compose: git apply places the later ones by the lines around them and refuses the whole patch when it cannot, which is the safe failure. What must never happen is this app implying that they compose, so the plan names every such path.
    • The text is checked by git and written as it was assembled. git's own reader is asked first, because text built by hand is exactly the kind that is plausible and wrong — but the parse is a check and not a round trip: a diff parsed from a buffer carries no modes and no object ids, so serialising it back out omits the ---/+++ pair and produces a file that would not parse a second time.
    • The empty patch is refused here too.
    • Nothing is kept between runs. A held set is a scratch buffer somebody fills over a few minutes, and it holds patch text lifted out of commits — content this app has no business writing outside the repository that already holds it. It is dropped when the repository changes.

    The Hold button is in the hunk header and asks the controller which diff it is over, so every surface that draws a commit's diff is covered by construction — including the three written before the question existed, and not one surface file changed. It is a toggle rather than Hold beside Drop, it takes the whole hunk and never the line selection the three verbs beside it act on, and it is away while a diff filter is on: what would be held is the text of a diff hiding a re-indent, sent to somebody as though it were the file.

    A strip says a patch is half built, because assembling one takes several minutes in several places and something has to be on screen the whole time. It is on the diff panel rather than in the operation banner, which is the doctrinally tidier home and the wrong one: the banner is for an operation that is running or stopped, with a way out that has to be reachable, and nothing here is running.

    A series¶

    One file per commit, oldest first — and that is not presentation: a series is applied in the order it is written, and every list in this app is newest-first, so a series written that way fails on its second file, asked to lay a commit on one that is not there yet.

    A directory rather than a file, which is the one place this verb's shape differs from every other write here: a series is N files and naming one of them would be naming the first. The numbering and the names are git's own — 0001-fix-the-thing.patch — so somebody who has seen a series before knows what these are. There is no -- <version> trailer, which git puts at the foot of each file: it names the git that made it, this is not git, and a version this app is not is a claim rather than a courtesy.

    Writing is all or nothing, since half a series applies half a branch. The empty series is refused for the empty patch's reason.

    Replaying one¶

    The whole series or none of it, and that is where it deliberately differs from git am. That one stops on the file it could not apply and leaves a half-finished operation with its own state files, its own --skip, --continue and --abort, and its own way of being walked away from. This app already carries three such sequencers, each with a banner mode and a stop the Conflicts surface finishes — a fourth is a real feature and not a flag on this one.

    So a file that will not apply rewinds to where HEAD was, names the file and why, and what you are left with is exactly what you started with.

    That is only honest because it refuses a dirty working tree first, which is load-bearing rather than tidy: the rewind is a hard reset, and one taken over your uncommitted work would destroy the thing this verb was never asked to touch. An unborn HEAD is refused for the mirror reason.

    The author is the file's and the committer is this machine's, which is what git am does and what the amend's own rule already argues: who wrote a change and when are facts about the change, and replaying it is not a new authorship. The [PATCH 2/7] marker is stripped from the subject, being the series' and not the message's, and a missing Date: falls back to your own clock rather than refusing. A missing Subject: or From: is refused by name: a directory of patches with one stray file in it is the ordinary way this goes wrong, and a plain diff among them is a patch to apply rather than one to replay.

    It is the one entry in this class the log may honestly offer to reverse — the replay wrote commits and nothing else, so a mixed reset leaves the working tree exactly as it went in.

    Reachable from no UI yet

    The series verbs are implemented and tested and no control opens them. The patch dialog is built around a file field and a single-diff plan, and another subject there means a directory field, a different plan shape and a different set of counts — a restructure rather than a row. It is recorded here rather than left to be discovered, because a verb reachable from nothing reads as done.

    Applying one somebody else wrote¶

    The other direction, and the only thing in the patch feature that writes to the repository. Apply patch… on Changes.

    The plan is the dialog. It runs a real check pass, so what is drawn is a statement about this working tree as it stands rather than a reading of the patch text — the difference between "this patch touches four files" and "this patch will apply". Every file it names is listed, all of them, one elided line each, because a cap with "… and 12 more" hides exactly the paths you are deciding about while the count sits in the sentence above doing the counting. A refusal is drawn instead of the counts rather than beside them.

    Nothing is committed, so nothing is confirmed. What it writes lands on Changes to be read and committed or discarded like any other edit, so the way back is the surface you are standing on. The dialog earns its place by describing rather than by asking. The apply is all-or-nothing for libgit2's own reason: it applies deltas one at a time, and a half-applied patch is a state nobody asked for.

    The file is read when it is settled, not while it is typed. A missing file reports through the toast, so re-reading per keystroke would fire that toast for every prefix of a path you are halfway through typing. It is read on Enter, on Browse, and on opening with a path already in it.

    One tick, and two that are absent¶

    --index is offered: apply to the index and the working tree, so what arrives is already staged. Off by default, because the honest reading of "apply this" is that edits arrive where edits arrive.

    • --cached — the index alone — is supported by the controller and not drawn. What it produces is a repository whose index and working tree disagree about every file in the patch, with nothing on Changes saying why: a thing to reach for deliberately at a prompt, not a tick beside a file chooser.
    • -3 is absent because libgit2 cannot do it. Its apply options carry exactly one flag, and there is no option meaning "merge this in where it does not apply cleanly". It could be built by hand — a patch carries index <old>..<new> lines, so where that blob is in this object database the pre-image can be reconstructed and merged — and that is a real feature rather than a flag to pass. A tick that quietly did an ordinary apply would be worse than the absence.

    What stands in -3's place is that the refusal names the file whose pre-image did not match, which is what you need in order to go and do it at a prompt.

    Its button is not governed by the change count, unlike the Patch button beside it, and that is the one place absent-not-greyed points the other way: a clean working tree is the state a patch is most often applied into, so keying the control to having changes would take it away at exactly the moment it is wanted.
