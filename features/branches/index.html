    Branches¶

    Licensing — Free, with paid parts. Creating, renaming, deleting, checking out, upstreams and the drift are free. Stacks — the recorded base, the chain, the restack and the tree reading — are stacked-branches, and what has been proposed off a branch is forge. What a licence adds

    Manage → Branches. Reading branches and writing them are two different jobs and they live apart: the breadcrumb's picker narrows the history to a branch and moves nothing, and this tab is where branches are created, renamed, deleted and checked out.

    That split is deliberate rather than an accident of layout — people rely on the picker not moving HEAD, and it says so in as many words.

    What a row says¶

    Four facts, and they are four rather than one "stale" flag because the ways a branch gets stuck have different people on the hook:

    Fact Means
    ↑3 ↓12 main Ahead of and behind the trunk — what a delete would throw away, and how much of the trunk this has not seen
    origin/foo Its upstream, and its drift against that
    merged into main Every commit is already reachable from the trunk
    upstream gone Config still names a remote-tracking ref that has been pruned away
    on feature-2 Its recorded stack base, if it has one
    an age When the tip was last committed to

    merged into main is a floor, never a total

    It is a reachability test over the commit graph, so it catches an ordinary merge and a fast-forward, and it cannot catch a squash merge or a rebase merge: both rewrite the commits, the original tip is then reachable from nothing, and a thoroughly merged branch reads as unmerged.

    Nothing here is called "fully merged", because "fully" is exactly the claim the commit graph cannot support. The tests assert the wrong-looking answer on purpose, so the limitation is on the record rather than waiting to be discovered and "fixed" into a claim.

    What can catch those is the forge, and it does — see what has been proposed off a branch.

    The trunk is worked out from refs/remotes/<remote>/HEAD first (the server's own answer, and the only source that is right for a trunk called neither main nor master), then a local main, then a local master — and which of those answered is published, because a guess nobody can see is how a surface comes to state something untrue with confidence.

    Which commit the trunk is at is a second question, and answering it with the first's answer was a live bug: measured against origin/main, a local main eighty commits ahead is not an ancestor of anything — including itself — so on a repository where git branch --merged main listed two branches, the merged filter came back empty and every row's drift was measured against a commit you had left behind weeks ago.

    The measurements are asked for, not refreshed¶

    Measuring one branch is an upstream resolution, three ahead/behind counts, a merge base and a descendant test. On a repository with 121 branches and 3000 commits that was 481 ms of a 601 ms refresh — paid on every repository switch, every staged hunk and every working-tree event, for numbers only this tab draws.

    So the names, the tips and which branch HEAD is on are read cheaply and always; the four facts are a second pass, asked for when the tab is opened, batched against a time budget. A row carries detailed: false until the pass reaches it, drawn plainly, because no upstream, zero drift and not-merged is exactly what a branch cut this morning looks like.

    Narrowing the list¶

    Three scope chips — All / Local / Remote — with a count each, remembered as a habit. In all, the locals come first ahead of the alphabet: interleaving origin/main between main and next would bury the eight rows that can be acted on among forty that mostly cannot.

    Merged only is a fourth control and deliberately not a fourth scope chip: the three above it are readings of which kind of ref and at most one holds, where this is a question about state and composes with whichever is lit. Grouped with them, "merged" would cancel "local", which is the pairing somebody tidying up wants. It is absent in the remote scope, where the only thing pressing it could do is empty the list.

    A name filter lives on the surface rather than in the settings, unlike the scope: a scope is a reading habit worth remembering and a query is three characters you are holding for ten seconds — a list narrowed by a word nothing on screen shows is the one asymmetry that would be a bug.

    Sorting — by name or by when the tip last moved — sits behind one control rather than two chips, because that strip already carries three scope chips, a merged chip and a filter field and, at the window's 900px minimum, has to fit all of that beside eight tabs. Alphabetical is the default: it is the only ordering that holds still, so a branch is where it was last time and a row does not move under the pointer because somebody else pushed. An unmeasured row is held at the end by name rather than sorted as its zero, or every row the page has not reached would sit at the bottom and then walk up as the pass landed.

    A row is three controls, and the rest is a menu¶

    It had five appearing on hover, and the gutter is a fixed width — so on a narrow window what appeared pushed Check out past the right edge, and the verb you were reaching for left the window at the moment you hovered the row it was on.

    The menu is opened from the ⋮ and by right-clicking the row — one set of verbs, two ways in, so they cannot come to differ. Two of its rows are routes to surfaces that already existed and could not be reached from here: Compare with current, and Rebase current onto this, both absent on the branch HEAD is on.

    Checking out¶

    git_checkout_tree and then git_repository_set_head, in that order — the detaching variant leaves the repository detached and orphans the next commit, silently.

    What a checkout may destroy is computed before anything is written, as the intersection of what is dirty with what the two trees disagree about. That is git's own rule, and it is why switching branches normally carries work in progress along instead of refusing; it is also the only way the refusal can name the files, which libgit2's "1 conflict prevents checkout" cannot.

    With nothing in the way the branch is checked out at once, because a dialog whose answer is already known is a habit rather than a safeguard.

    Autostash is its own button rather than a tick, because it is a different operation. Untracked files go into that stash too, unlike git's own autostash: an untracked file the target branch also has is exactly the sort of thing that blocks a checkout, and stashing everything except the blocker would be a joke. Coming back, the stash is applied and then dropped rather than popped — git stash pop reports success after writing conflict markers into the file and dropping the entry, which would leave the only intact copy being the marked-up file you are now staring at.

    Deleting¶

    Refuses without force where the branch is unmerged, and "merged" here means reachable from HEAD or from the branch's own upstream — a branch that has been pushed is safe to drop even when whatever you are standing on has never seen it.

    Deleting the checked-out branch is refused with or without force, because there would be nothing left for HEAD to point at.

    The confirmation has three sentences and picks one:

    1. A name and nothing more.
    2. The count, and where the commits go.
    3. Landed but rewritten — the proposal number, and why git cannot see it.

    That third one exists because the dialog was telling a false alarm: a squash-merged branch reads as unmerged to git, so it counted four commits and said deleting them would make them reachable from nothing — about work that is already on the trunk under different ids. A false alarm on the one dialog in that list that destroys something is what teaches somebody to press through the real one.

    The force is still passed and the confirm is still not the primary, because git's own answer has not changed and the forge reading may be a day old — so the button that makes commits unreachable stays the one the highlight does not lead to. What changed is that the sentence beside it is true.

    Several rows at once¶

    The same gesture the file lists use — plain click, ⌘-click, shift-click from an anchor — scoped to one kind of row, because a local branch and a remote-tracking ref share almost no verb.

    A plain click on a row that is already the whole set lets go of it, which is the only way out of a set now that the strip of bulk buttons is gone.

    The set's verbs are on the menu, for this project's rule that an operation is entered from the object it acts on — and because five buttons appearing the moment a second row was picked moved every other control sideways at the one moment somebody was aiming at a row. The header counts ("11 branches"), a verb that cannot honestly apply to a set is absent rather than relabelled (no checking out eleven branches, no rename, no comparison, no proposal), and the destructive one names them.

    A set operation reports every refusal, by name, once. Each is a loop over the single verb it is the plural of, so nothing about what is safe is decided twice — what they add is that eleven refusals are collected and emitted together rather than arriving in a toast that holds the last one.

    Upstreams¶

    Set or clear what a branch tracks. "Nothing" is the first row of the picker rather than the last — it is the one answer whose position must not depend on how many remotes a repository happens to have.

    There is no confirmation: nothing about it moves a ref or writes a file, and the dialog says so. What it changes is what the ahead/behind counts are measured against and where a plain push and pull go.

    Checking out a remote branch¶

    A remote-tracking ref cannot be checked out, renamed or deleted by anything here, so a remote row is a different component rather than a local row in another mode — a mode would be one component every line of which asks which of two things it is drawing.

    What it carries is the one verb that is available — Check out as…, with the ellipsis load-bearing, since this means making a local branch at that commit and calling it "Check out" would claim the app can put HEAD on a remote ref — and tracked by, so "origin/main, tracked by main" and "origin/spike, tracked by nothing here" are told apart.

    The verb is absent once something tracks the ref: the local branch is a few rows up with its own Check out button.

    Stacked branches¶

    A branch cut from another branch rather than from the trunk is an ordinary way to work — three changes that depend on each other, each reviewable — and git records nothing about it. That absence is the whole design.

    Making one out of a branch you already have

    A stack is usually recorded as you go, a branch at a time. To turn one branch that has grown too big into a stack after the fact — a commit, a file, a hunk or a few lines at a time — see Splitting a branch.

    It is recorded, never inferred. After a base has moved on, the merge base of two branches says where they last agreed and not which was cut from which; and two branches off one trunk share a merge base that names the trunk. A stack inferred from the graph would be right about the common cases and confidently wrong about a rebase.

    So it is a note — branch.<name>.sourcemanager-base in .git/config — and three things follow from where it lives:

    • It is this checkout's. A colleague does not receive it, because there is nowhere in git to put it where they would.
    • It is namespaced, so nothing git or another client writes can collide with it.
    • It survives every operation this app performs, because config does.

    What it buys¶

    The drift is measured against the base. On feature-3 over feature-2 over main, "12 ahead of main" is the whole stack's work and says nothing about this link; aheadOfBase is the three commits this branch actually adds. The row draws one or the other and never both — two numbers about one branch with nothing saying which question each answers is worse than either alone.

    And a proposal per link: each is that link's base against that link's head.

    Three refusals¶

    A base that is not a local branch (a remote-tracking ref cannot be checked out, rebased onto or proposed against from here, so offering it would be an offer the app cannot keep); a branch on itself; and a base that would close a cycle — a on b on a is a chain with no trunk, and every reader of it would walk it for ever. The cycle check runs against what is stored now rather than trusting the refusal to have held, because .git/config is a text file somebody can edit.

    A deleted base keeps its note and says so. Dropping it silently would lose the one record of what this branch was cut from at exactly the moment somebody is working that out.

    How to use it¶

    1. Manage → Branches, open a branch's ⋮, choose Set base branch.
    2. Its drift is then measured against that base.
    3. Propose the links one at a time.

    What has been proposed off a branch¶

    A badge on the row, from the pull requests this app already holds. It costs nothing and asks for nothing — a pass over the list in memory — so a repository whose proposals have never been read has no badge rather than a "no proposals" claim.

    merged is sticky and the number is not: a branch proposed twice and merged once did land, which is the fact the delete warning must not lose. merged as #140 outranks merged into main and replaces it rather than joining it — they are the same fact at two strengths, and the forge's is the one that is right when they disagree.
