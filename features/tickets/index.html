    The tracker¶

    Licensing — Paid. The tracker is tickets. The link rules that turn an id into something to press are free, permanently. What a licence adds

    What the work is for is on a page this app is not: a ticket in GitHub Issues, Jira or Linear. Tickets is a destination of its own that reads that board and writes back to it — what is assigned to you, what a commit's PROJ-88 actually says, and moving one when the work lands.

    The link rules are not replaced and never will be. Turning #412 into something to press needs no key, no network and no configuration, works on a tracker this app has never heard of, and is free — see A ticket id, and the page it names. Everything on this page is what you get in addition, once you have said which tracker and handed over a key.

    Its own destination, not a tab of Manage¶

    Manage's tabs are things a repository holds — its stashes, its worktrees, its hooks. A tracker is somebody else's service and the tickets on it outlive this checkout, which is the argument that moved Branches out of Manage and gave Pull requests and Checks seats of their own.

    There are three states before there is a list, because an empty list is the one answer this must never give by default: no tracker configured, no key, and the tracker said no are facts about everything except the board. Drawing all four as an empty frame is how an integration earns its reputation for lying.

    Setting one up¶

    Four keys go in .git/config under sourcemanager.tickets — provider, host, scope, account — which is the link rules' rule and its reason: a statement about this repository's tickets cannot arrive with somebody else's branch, and two checkouts of two projects do not share a board.

    No key is written there. It goes in the platform password store, keyed by host, and a test asserts that nothing credential-shaped reaches a file you might share.

    Where the tracker is the forge your remote is on, there is nothing to paste at all — being signed in for the proposals is being signed in for the issues. The host has to match: a remote on github.com with a tracker on an enterprise host is two accounts, and handing one's token to the other would send a credential somewhere it was not issued for.
    GitHub Issues Scope is owner/repo. No key needed where you are already signed in for proposals
    Jira Scope is a project key. An API token and your account email — Jira's tokens are HTTP Basic, which is why this provider alone draws a second field
    Linear Scope is a team key. A personal API key

    A tracker with no scope is refused rather than written. Half-configured is the worst state to be in: every request 404s and that reads as a broken key.

    Changing a setting is not a one-way door. The fields are drawn filled in from what is configured, and pressing the same button writes whatever is in them — so moving to a second Linear team, or pasting a token that was rotated, is one field. Use a different tracker means "start from the picker", and clearing everything is its own row, named for what it does, last on the page because it is the destructive one.

    Two fields for a state, and why you see both¶

    Tracker What it actually has
    GitHub Two states, plus a reason on a closed one since 2022
    Jira A workflow per project, named by an administrator
    Linear Five fixed types, any number of named statuses under each

    A shared vocabulary holding all three would be Jira's, and the other two would be pretending. So a ticket carries both: status is the tracker's own word, drawn verbatim, and state is one of four categories — open, started, done, cancelled — which is what a colour, a filter and a count are built on.

    Jira maps onto three of the four, having no notion of cancelled apart from done, so a ticket resolved "Won't Do" is done here. That is a real loss and it is the honest mapping — inventing cancelled out of a resolution name would be guessing at words an administrator chose — and what stops the loss being invisible is that their word survives beside it.

    What a tracker tracks is declared, never assumed¶

    A table written against the union of three trackers draws six empty columns on GitHub Issues, which is how a reader learns to stop reading a list. One written against the intersection throws away most of what Linear knows. So each provider declares its fields, and a field it does not declare is absent from the table, the ticket page and the menu.

    GitHub Issues Jira Linear
    Status read/write read/write (a transition) read/write
    Assignee read/write, several read/write, one read/write
    Labels read/write read/write read/write
    Cycle milestone, write sprint, read cycle, write
    Priority — read/write read/write
    Estimate — story points, read read/write
    Due — read/write read/write
    Parent / sub-issues — read parent, write
    Blocking / blocked by — read read
    Project / team — project, read read/write

    Present and writable are two questions, and the asymmetry is real rather than an oversight: Jira reports story points and will not take them from here, the field's id being per site and a control that wrote it blind putting a number in some other field entirely. A field a tracker will not take is refused by name and without a request — the alternative is what makes a write look like it worked, Jira accepting a PUT naming a field it does not have, answering 204 and changing nothing.

    The columns default to five, not to everything¶

    Status, assignee, priority, due, last moved. Linear declares nineteen fields and a table opening with all of them is the "too cluttered to read" report the branch table already earned once.

    The title is never a column — it is the one elastic thing on the row — nor is the body, which is a document rather than a cell, nor the key, which is the row's own leading slot so it lines up down the list.

    Filters, not three hard-coded readings¶

    The chips are the same vocabulary the proposals and the CI runs use, and a chip narrows what has already been read — it costs no request. What replaced was three readings (Mine, Open, and a search box) that each sent a different request: exactly three questions, no way to ask a fourth, and a round trip between them.

    The search box stays, because it is not a filter — it asks the tracker to look through tickets this app has never read.

    The built-in readings are Unfinished, In progress, Finished and All, plus three that earn their place:

    • Unfinished is the resting reading and what an unmarked tab counts. Deliberately not open, which is one of the four categories and would drop everything anybody has started.
    • Ready to start — unfinished, unstarted and unblocked. This is the reading that makes the blocking fields worth filling: a board where everything is blocked by something looks busy and is stopped.
    • Overdue, which is a due date further in the past than nothing at all.
    • Mine, absent where no login is known rather than drawn as a chip that could only ever be empty.

    The vocabulary is the shared one rather than the configured tracker's, and that is the opposite of what the columns do, deliberately: a saved filter is yours and travels with you, so a reader with a Linear repository and a GitHub one would otherwise find their filters silently changing meaning as they walked between the two. A clause naming a field this tracker does not fill matches nothing rather than everything — the safe way round, because a filter that found nothing is visibly wrong where one that found everything looks like it worked.

    A saved question earns three routes: counted on the tab's badge, kept as a chip on the strip along the foot of the window, and watched. A watched one announces a ticket that matches, once, and never off the first list read — everything on a board when you open it has already happened, and a hundred notifications on arrival is how a notification is taught to be ignored.

    Reading and writing one ticket¶

    The description, the comments and every declared field are on the ticket's own page, with an editor where the tracker will take one and absent entirely where it declares nothing — a panel of eight empty rows on GitHub Issues being what the catalogue exists to avoid. The title, the description and your own comments can all be rewritten, which is the ordinary reason somebody opens a ticket they already know about.

    The status is one drop-down, opening onto where the ticket can go from where it stands. The choices are asked for when the control opens, never per row, and on Jira they are the transitions — what a ticket can move to depends on where it is, so they are replaced rather than accumulated. A tracker that cannot be written to draws a tag instead.

    Whether a comment is yours is the provider's answer, not a comparison of two display names: GitHub answers a login, Jira a display name beside an account id whose email is hidden by default, and Linear a bit. Comparing strings would offer Edit on somebody else's comment about half the time.

    A write is re-read rather than claimed. A Jira workflow can have a post-function that changes the assignee, a field or a resolution, and a claim would be confidently wrong about every one of them — which is why Jira's transition endpoint answers 204 with an empty body. Jira also hands a comment back changed, its descriptions being a JSON document tree rather than markdown.

    Creating one takes a title and a body and nothing else, deliberately, and the dialog says so: a tracker's create form is a project's own — issue types, components, required custom fields — and a form drawing half of it would fail on submission with a message about a field it never showed.

    Nothing costs a request that was not asked for¶

    refresh() is a config read and no request at all, which is what lets it sit on the general refresh path while the list does not. The list is asked for, by Reload or by a query being pressed; typing in the query box fetches nothing per keystroke. The ticket hover on a commit subject in History answers out of the list already read, and says nothing where that list has never been read.

    Arriving on a list read longer ago than your page-refresh setting asks again. Zero minutes is never, and a board never read at all is not stale — that is a first fetch, and this destination does not make one on arrival, or every ⌃Tab would carry a request.

    Both lists are paged, and say when a bound stopped them¶

    A GraphQL connection answers a page, and publishing that page as the answer is how a board of two hundred reads as a board of fifty with a count on screen to prove it. On GitHub it is worse than a truncation: /issues answers pull requests too and they are dropped afterwards, so a repository that proposes more than it files gets a first page that is entirely pull requests and a tab that is empty for a reason nothing explains.

    So both page, both are bounded — a board of ten thousand is a hundred requests behind one press, which is a rate limit rather than a feature — and the count line says when the bound stopped the read.

    A read reports two things. As well as "it failed and here is why", there is "it worked and here is what you cannot see from the rows": how many were read, how many were dropped and why, and whether a bound stopped it. The page has three empties with three sentences — a filter matching none of what was read, a board with nothing on it, and a read that fetched rows and showed none of them — because an empty list is only the thing empty means if everything else says which it is.

    Licensing and what is proven¶

    The tracker is a paid feature (tickets). The link rules are free, permanently.

    Fixture-proved, not live-proved

    Nothing here has been run against a live Jira or Linear. Their tests pin the requests built and the JSON mapped onto the documented fields, from recorded replies; a green suite says the mapping is right about the JSON that was recorded and says nothing about the API having that shape today. GitHub Issues is the one that could be live-proved, its token being the one this project has.

    No fixture carries a credential, asserted by a test that reads its own bytes back.
