    The fleet¶

    Licensing — Free, with paid parts. A fleet of up to three repositories is free. An unlimited one (fleet-unlimited), importing a folder (fleet-scan), a second window (windows) and the proposal and CI summaries on a card (forge) need a licence. What a licence adds

    The page the app opens on, and the answer to "what is the state of everything I work on". One card per registered repository, carrying its branch, its drift, how much uncommitted work is in it, and whether an operation is stopped in it.

    Nobody else in the field has this on a home page with drift and stopped operations beside each other; GitKraken's Workspaces are the nearest thing and are a paid feature there.

    Four ways in¶

    Add ▾ is one control with four rows, ordered cheapest to most:

    Row What it does
    Import repository Take on a checkout that is already on disk
    Clone Bring one down, with a depth dial and what shallow gives up
    New repository git init here — and, where a token says it can, the same repository on the forge with origin wired up
    Scan a folder Walk a directory and offer every checkout beneath it

    The path fields are asked for rather than always there: two mono text boxes stating a question that is answered once would push the cards down on every visit, so each sits behind a button that reveals it, focused, and Esc puts it away.

    Scanning¶

    Registering twenty checkouts one typed path at a time is what a single path field cannot do. The walk is breadth-first, a batch per turn of the event loop against a time budget — a scan of a home directory has to leave the window alive, and has to be abandonable.

    Nothing is registered by the walk. What it finds is offered, to pick from, because a scan of anyone's home directory turns up plenty nobody wants in the fleet.

    A repository is a directory holding a .git directory, which is the single test that excludes both submodules and linked worktrees — theirs is a .git file — and neither belongs in the fleet on its own, since each is reached through the repository that owns it. A found repository is never descended into; node_modules, build, Pods and DerivedData are never entered; hidden directories and symlinks are skipped, because a symlink back up the tree is how a walk like this loops.

    A repository that does not exist yet¶

    New repository does git init in a folder you name, and optionally creates the same repository on the forge and points origin at it. Four things about the forge half are deliberate:

    • auto_init is off. A forge-made initial commit is exactly what turns your first push into a rejected non-fast-forward, and the only ways past that are a force or pulling a commit nobody wrote.
    • Nothing is pushed. The remote is wired up and Push — which knows about leases and upstreams and refuses in its own words — is how the first commit gets there.
    • Private is the default, and the tick says so: a public repository is visible to everybody the moment it exists, and that is not a state to arrive in by not reading a dialog.
    • The order is local, then forge, then remote, each only if the last succeeded. A repository on the forge with nothing local to push into it is litter somebody has to delete by hand.

    It refuses rather than clobbers three times: a folder that is already a repository (it offers to import it instead), a folder that holds anything at all, and a path inside another repository's working tree — a nested repository is invisible to the outer one's status, because git does not descend into one.

    What a card says¶

    The branch, ↑ahead ↓behind, the count of uncommitted files, tags for a stash, a worktree or submodules, and a marker when an operation is stopped in there.

    The whole tile opens the repository — a card is a repository the way a row is a file, and the Open button in the corner is the label on the target rather than the target.

    An unread card says so

    Summarising a repository costs an open, a status walk, an ahead/behind, and three list reads. Doing that for nine checkouts of twenty thousand files blocked the window for 4.1 seconds, so it is batched now: the list is immediate, and each entry's git fields fill in over the following turns.

    An entry that has not been read yet carries summarised: false and the card says so, because every one of those fields is a claim if it is drawn as an answer: no branch is "detached", nothing ahead or behind is "in sync", and nothing dirty with nothing untracked is "clean" — the last being the one somebody reads to decide a checkout needs nothing doing to it.

    The fleet is deliberately outside the app's general refresh: summarising it opens every registered repository, so it is refreshed when the page is shown rather than after every staged hunk.

    Groups¶

    Free-text labels you assign. A repository belongs to at most one, and one that belongs to none still renders, in a section of its own at the end.

    Four verbs sit behind one control — make a group, rename one, delete one, and file a repository into one — and none of them re-summarises anything: a label is a fact about the fleet rather than about the repository, so assigning one rewrites the cached entries in place instead of opening every registered repository again.

    Deleting a group deletes a label and never a repository. Its members are un-filed into the section at the end, still registered and still on disk, because losing a checkout while tidying up a name is not a trade anybody would make knowingly.

    Three things about grouping that are separate on purpose¶

    • Drawn — whether sections are shown at all. Turning it off leaves every label where it was, so turning it back on returns to what was there.
    • Declared — a group can exist with no members, so "make three groups, then sort thirty checkouts between them" no longer has to be done one card at a time and in the wrong order.
    • Inferred — group by parent directory is a shortcut, and it is reversible because every label it writes is recorded as derived. Undoing it takes back exactly those and cannot discard a name you typed. A label stops being derived the moment you touch it.

    The order is yours¶

    Alphabetical was the first answer and the objection to changing it was that any other order would have to be persisted, migrated and given a way to change. It is all three now: sections are dragged by a grip, or moved with arrow buttons that are visible always rather than on hover — a hover-revealed button is invisible to the palette and to the hint keys.

    A name the arrangement has never heard of ranks past the end of it, so with no arrangement every name ties and the alphabetical tie-break decides the page. There is no second mode to keep in agreement with the first. The unlabelled leftovers stay pinned last.

    Dragging a section by its grip and a card by its body carry different things, so the shared drop target tells the two gestures apart without guessing, and they draw different marks: a wash for "file into here", an insertion rule for "put it between these two".

    Filtering¶

    Chips narrow the page — dirty, ahead, behind, stopped — and the sections are computed from what the chips left, so filtering and grouping compose.

    Removing one¶

    Three answers, not a boolean, because they are three different acts and a tick beside one button would make the destructive one the same press as the harmless one:

    1. Forget the entry — the checkout stays on disk.
    2. Move the folder to the trash — offered first, and the primary, because a checkout is often the only copy of something and this is the one form the operating system can take back.
    3. Delete it permanently — deliberately not the primary.

    Three rules keep the offer honest. The folder goes first and the entry only if it went, because a fleet that has forgotten a repository whose files are still there is recoverable while the reverse reads as "deleted" and is not. The trash failing refuses rather than escalating — quietly turning a reversible request into an irreversible one is the worst thing that function could do. And the dialog is composed from the same plan the operation consults, so it says what is actually in there: uncommitted files, untracked files, stashes, and commits no remote-tracking ref can reach — the one figure that says the folder holds something that exists nowhere else.

    The repository being open is not a refusal: it is a reason to close it first, which the app can do and you cannot conveniently. The dialog says the app will go back to the fleet.

    Two windows¶

    New window opens an empty one on the fleet — somewhere to put the next checkout — and a card's Open in a new window opens that repository beside whatever is already open, landing on Changes.

    A second window is a second repository, genuinely: each window holds its own set of controllers. What is shared is everything about the reader rather than about a checkout — the preferences, the fleet, the command counts, the language, the editor template, the keychain, the snapshot store. So the theme you pick in the second window is the theme the first one is drawn in, because there is one preferences object rather than two agreeing by arrangement.

    A repository open in one window draws as open on the other window's card, and removing it closes it everywhere.

    Repository tabs are recorded as the shape that could not have delivered this

    A tab strip over one set of controllers is a visible drawing of the ⌃Tab list: pressing a tab swaps the repository underneath every surface, which is what the switcher already does with no chrome at all. Two repositories side by side needs two windows.

    The free tier keeps three¶

    The fleet cap is the one licence limit with a number in it, and it bounds growth and never the fleet: forty registered repositories still list, still open and still refresh under a lapsed licence, and only the forty-first is refused. Nothing deletes an entry to enforce anything.

    The Add control is disabled with a sentence beside it when the fleet is full — disabled rather than absent, which is a deliberate exception to the absent-not-greyed rule, because the verb applies, it is the one about to be wanted, and a control that vanished would take the sentence explaining it with it.
