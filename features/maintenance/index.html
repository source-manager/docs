    What the git directory is made of¶

    Licensing — Free. The breakdown and all nine verbs. What a licence adds

    Manage → Maintenance is a breakdown of .git — where the bytes are, how many objects are loose, what is reclaimable — and nine verbs that change it.

    It exists because the two questions a reader actually has are "why is this checkout four gigabytes" and "is there anything safe I can press about it", and the usual answer is a command somebody found on the internet, run in a terminal, whose destructive half is indistinguishable from its harmless half at a glance.

    The breakdown reads with no git at all¶

    The walk is of the directory itself, so it works on a machine with no git command line — which is the ordinary state of somebody who has only ever used this app.

    Part What it is Reclaimable
    Loose objects One file per object, before anything packs them yes
    Packs The packed object database yes
    Reflogs Where HEAD and every branch have been yes
    LFS The local LFS cache — drawn only where it holds something no
    Worktrees Linked worktrees' admin directories no
    Submodules Submodules' whole object databases no
    Other Refs, the index, config, hooks, everything else no

    The total is the directory's own size, not the sum of the rows, and Other closes the gap — so a part this app does not know about is reported rather than silently dropped. Anybody comparing this page against du has to get the same number or the page is worthless, and a test asserts the two agree.

    A count of — is not a count of zero. A pack directory holding no packs and a directory whose files nobody counts are different facts, and "0 files" beside a row holding 40 KiB reads as a bug.

    It is asked for rather than refreshed: a stat per loose object is tens of thousands of them on an unpacked repository, so arriving on the tab takes the reading, exactly as Blame and the metrics page are asked for. It is dropped when you change repository, a breakdown of the previous one drawn under this one's name being a claim rather than an answer.

    The verbs need git, and say so rather than disappearing¶

    libgit2 has no gc, no repack, no prune and no maintenance — not reduced versions of them, none of them. So every verb runs git, and where there is no git the controls are drawn, disabled, with the sentence that says why.

    That is the one exception to absent rather than greyed: the refusal is about this machine rather than about the verb, and a page that vanished would leave a reader with no way to discover the feature exists or what it needs.

    Verb Runs What it loses
    Run maintenance git maintenance run Nothing
    Write a commit graph git commit-graph write --reachable Nothing
    Collect garbage git gc Unreachable objects older than two weeks
    Repack git repack -a -d --depth=250 --window=250 Nothing
    Aggressive gc git gc --aggressive The same as gc, slowly
    Prune git prune Every unreachable object
    Expire the reflogs git reflog expire --expire=now --all Every reflog entry
    Start background maintenance git maintenance start Nothing
    Stop background maintenance git maintenance stop Nothing

    Run maintenance is the primary button, and that is a recommendation rather than a layout decision. It is git's own modern answer — an incremental repack, a commit graph, a loose-object pass — and the only one here you can press without first having to think about what is reachable.

    Writing a commit graph is on this page because this app benefits from it. Every history walk, every ahead/behind, every merge base and the whole lane pass are commit-graph traversals, and a written graph file makes all of them dramatically cheaper. It is the one verb whose benefit is to this program rather than to the repository in general.

    Aggressive gc is offered and is not recommended, and the page says so. It recomputes every delta with a much larger window, takes minutes to hours on a large repository, and is worth running roughly once — after an import, a filter-repo, or a clone of something with a pathological history. Repack with an explicit depth and window is the same thing done deliberately and without the pruning, and the numbers are git's own documented recommendation for that case rather than a guess.

    The two destructive verbs are offered because the alternative is worse. Expiring the reflogs and then pruning is how anybody actually reclaims space after deleting a large file from history, and a maintenance page that could not do it would send you to a terminal. Each asks first, and each confirmation names what stops being recoverable — the reflog being the one thing standing between you and a branch you deleted, which is why prune's own sentence says to press it after expiring and not before.

    Background maintenance is two verbs rather than a toggle, whose label would claim a state. And the state is read from git's own global config, where git maintenance start writes it, rather than remembered here: somebody who ran the command in a terminal is told the truth rather than this app's opinion.

    What the panel says after a run¶

    The size is measured before the run rather than read off the last walk, or pressing "Measure again" in between would show a difference against the wrong baseline.

    The figure is signed, and that is not pedantry: writing a commit graph and running maintenance routinely make the directory larger — they write a file — and a figure clamped at zero would report "reclaimed nothing" for an operation that did exactly what it was asked to.

    One at a time. A second run is refused while one is in flight, which is the refusal the transport lock makes one layer along and for the same reason: two gits writing one object database.

    Every run gets a row in the operation log with the command you would have typed. None of them offers a way back, and that is stated rather than left to be discovered — what a gc reclaimed is gone.

    What is verified¶

    A real git gc against a real repository is what proves the command reaches git, that the size is taken again and that the log gets a row. What is deliberately not asserted is that the repository got smaller: a three-commit fixture has almost nothing to pack, and a test demanding a number go down is one that fails on a repository that was already tidy.

    The three destructive verbs are never run in the suite. Prune and reflog expire against a fixture would prove nothing the plan does not already say, and aggressive gc takes long enough that it has no business in a test run.
