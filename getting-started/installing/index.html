    Installing¶

    From a release¶

    Tagged releases carry four artifacts:

    Platform Artifact Self-contained?
    macOS SourceManager-<version>-macOS.dmg yes
    Windows SourceManager-<version>-Windows-x64.zip yes
    Debian, Ubuntu source-manager_<version>-1_amd64.deb no — needs system Qt and libgit2
    Linux SourceManager-<version>-Linux-x86_64.tar.gz no — needs system Qt and libgit2

    Releases are published to source-manager/dist.

    macOS: Homebrew, or the disk image¶

    brew tap source-manager/tap
brew install --cask --no-quarantine source-manager

    That is the shorter road, and --no-quarantine is the whole of why. macOS runs its first-launch check on the com.apple.quarantine attribute, which is set by whatever downloaded a file; Homebrew sets it by default and this asks it not to. Without the flag the app installs and then refuses to launch, because these builds carry an ad-hoc signature rather than a Developer ID one.

    It is arm64 only — built on an Apple Silicon runner against a non-universal Qt — and the cask declares it, so brew refuses on an Intel Mac instead of installing something that cannot run.

    The disk image is the other way: open it and drag the app onto the Applications folder beside it. Being unsigned, it is refused on first launch — and on macOS 15 and later the Control-click > Open bypass no longer exists. Open it, let it be refused, then go to System Settings > Privacy & Security and press Open Anyway.

    Debian and Ubuntu: the apt repository¶

    Add it once and the app upgrades with the rest of the system:

    sudo install -d -m 0755 /etc/apt/keyrings
sudo curl -fsSL -o /etc/apt/keyrings/source-manager.asc \
  https://source-manager.github.io/apt/source-manager.asc
sudo curl -fsSL -o /etc/apt/sources.list.d/source-manager.sources \
  https://source-manager.github.io/apt/source-manager.sources
sudo apt update && sudo apt install source-manager

    Check it landed, and see where it came from:

    apt policy source-manager

    Then it is an ordinary package:

    sudo apt upgrade                             # with everything else
sudo apt install source-manager=<version>-1  # a particular release
sudo apt remove source-manager               # or `purge` to take the config too

    Every release stays in the repository, so a pin and a downgrade work as well — which matters on the day a release is the thing you need to get away from.

    The second file names the key in its Signed-By:, so this project's key is trusted for this source rather than for every source on your machine, which is what the old apt-key route did.

    There is no Homebrew route on Linux: brew has no casks there, and a formula cannot install a .deb — no dpkg, no root, and a package whose dependencies come from apt landing in a brew prefix.

    apt update says NO_PUBKEY

    The signing key was rotated and your copy predates it. Re-download the key file over the first curl above and run apt update again; nothing else needs to change, and the packages you have already installed are unaffected.

    apt says the package has unmet dependencies

    It is built against Ubuntu 26.04's Qt 6.10 and declares that, so apt refuses it on anything older rather than installing something that will not start. On an older release take the tarball and its system Qt, or build from source — both are below.

    Or take the .deb off the release and install it by hand with apt rather than dpkg — apt pulls the dependencies in, where dpkg only reports that they are missing:

    sudo apt install ./source-manager_<version>-1_amd64.deb

    Either way it is built against Ubuntu 26.04's Qt 6.10, so apt refuses it on anything older — which is the good version of that failure. The tarball is the same tree without the metadata, for distributions that are not dpkg ones.

    A test build somebody sent you¶

    A .deb handed over directly, rather than taken from the repository above. It is the same package; it is just not signed for, indexed by, or upgraded through apt, so everything here is manual and deliberate.

    sudo apt install ./source-manager_<version>-1_amd64.deb

    apt, not dpkg -i: apt resolves the Qt and libgit2 the package declares, where dpkg only reports that they are missing. If apt refuses it over dependencies, your distribution is older than the build targets — say which one you are on rather than forcing it, because a forced install produces an app that starts and then fails somewhere else entirely.

    Run it from the applications menu, as Source Manager, or in a terminal:

    SourceManager

    It needs a graphical session. Over plain ssh with no X or Wayland forwarding it exits on the platform plugin, which reads as a broken package and is not one.

    When something goes wrong, what makes a report answerable is:

    • what you did and what happened instead;
    • lsb_release -ds and apt policy source-manager;
    • the log, at ~/.local/share/pasdam/SourceManager/logs/sourcemanager-<date>.log.

    The log records the paths of repositories you opened — deliberately, since most questions about this app are about a particular checkout — so read it before sending it on if any of those names are private.

    Removing it is ordinary:

    sudo apt remove source-manager     # --purge to drop the settings as well

    Signing is optional, and the release says which

    The pipeline builds and packages whether or not signing certificates are configured, and says what is unsigned in the step log, the job summary and the release notes. An unsigned macOS build is refused by Gatekeeper on a machine that did not build it; an unsigned Windows zip raises SmartScreen.

    There is no AppImage, no Flatpak, no .rpm and no Windows installer — both Linux artifacts need Qt and libgit2 from the distribution, and the Windows one is a zip of the deployed tree. Each is its own piece of work rather than a step to bolt on untested.

    Building¶

    cmake -B build .
cmake --build build

    That is the whole of it on every platform. Nothing platform-specific is needed to build; only the install rules differ.

    What it needs¶

    • Qt 6.2 or later. There is no Qt 5 arm — it was removed rather than kept as a set of conditionals nothing exercised. The app builds against 6.2; the test suite needs 6.5, because eleven QML suites call waitForPolish.
    • libgit2, through pkg-config.
    • OpenSSL's libcrypto, which arrives with libgit2 (which requires it) and is what verifies a licence key.
    • Qt's Linguist tools — lupdate and lrelease. Translations are compiled on every build, and a configure without them stops with the package to install rather than quietly producing a build that speaks one language.
    sudo apt install ninja-build pkg-config libgit2-dev \
     qt6-base-dev qt6-declarative-dev libqt6sql6-sqlite \
     qt6-tools-dev qt6-l10n-tools \
     qml6-module-qtquick qml6-module-qtquick-controls \
     qml6-module-qtquick-layouts qml6-module-qtquick-window \
     qml6-module-qtquick-dialogs qml6-module-qtquick-templates \
     qml6-module-qtqml-workerscript qml6-module-qttest \
     qml6-module-qt-labs-platform qml6-module-qt-labs-folderlistmodel

    The -dev packages carry the CMake config files and the qml6-module-* ones carry what the engine loads at run time. They are separate packages, and a machine with only the first builds everything and then fails every QML test with "module not installed".

    Optionally libsecret-1-dev, which enables the keychain rung for an https token. Without it the app compiles unchanged and the token stays in memory for the session.

    brew install qt libgit2 pkg-config

    Homebrew's qt already carries the Linguist tools.

    Qt through aqtinstall, libgit2 through vcpkg — whose pkg-config file is what keeps the root CMakeLists.txt from needing a third dependency arm. MSVC 2022 x64; there is no MinGW arm.

    Nothing Windows has been executed

    Every line of the Windows support was written on Linux. CI is the only evidence it works, and a green Windows job means the tree configures, compiles, links and passes the suite headless. It says nothing about window chrome, the native file choosers, high-DPI scaling, or a path typed with a drive letter.

    The build output¶

    build/SourceManager.app on macOS, build/src/SourceManager on Linux, build/src/SourceManager.exe on Windows.

    -Wall -Wextra (/W4 on MSVC) are on and -Werror deliberately is not: turning warnings on is one decision, and failing the build on them is a second one with a different cost — a toolchain upgrade adds diagnostics, and a build that stops on those is a build that gets the flag removed rather than the code fixed.

    The build with no paid tier on screen¶

    cmake -B build -DSOURCEMANAGER_FREE_ONLY=ON .

    Hides the paid features, the switch that would show them, and the licence window — for handing a copy to somebody who should not be offered something they cannot buy. It is not a second product: the gate, the feature table and the licence check compile in exactly as they do otherwise, and only what is drawn changes. The suite passes in both configurations.

    Installing¶

    cmake --install build

    On none of the three platforms is the result self-contained: the app goes on loading Qt and libgit2 from wherever this machine keeps them. Re-run it after every build — the old copy is replaced outright, not merged over.

    Installs bin/SourceManager, a desktop entry under share/applications/ and six icon sizes under share/icons/hicolor/, through CMAKE_INSTALL_PREFIX as any other program does.

    The default prefix is ~/.local rather than CMake's /usr/local, so installing needs no sudo and the desktop finds the entry with no configuration — ~/.local/share is $XDG_DATA_HOME. Pass -DCMAKE_INSTALL_PREFIX=/usr for a package; --prefix and DESTDIR both work normally.

    Puts SourceManager.app in ~/Applications, where Finder, Spotlight and Launchpad all find it. Reconfigure with -DSOURCEMANAGER_INSTALL_DIR=/Applications for a machine-wide install.

    That variable, not --prefix, is what moves the bundle — Qt Creator forces CMAKE_INSTALL_PREFIX to /tmp from a deferred call that runs after everything in CMakeLists.txt, so the destination deliberately does not go through it.

    Installing ad-hoc signs the bundle, which is not optional on Apple Silicon: copying the app rewrites its rpath, invalidating the signature the linker applied, and the kernel then refuses to execute it — the app dies on launch with no dialog and nothing in the log.

    bin/SourceManager.exe under CMAKE_INSTALL_PREFIX, and nothing beside it. There is no icon to install (it is compiled into the binary) and no desktop entry.

    This is the platform where the "not self-contained" caveat bites hardest: Windows has no system place for a library, so an executable finds its DLLs beside itself or on PATH and the install rule arranges neither. What makes a Windows build runnable elsewhere is windeployqt over the staged tree, which the pipeline runs and the install rules do not.

    Redistributing a macOS bundle¶

    Shipping to anyone else needs macdeployqt to copy the Qt frameworks in, then a Developer ID signature and notarisation to get past Gatekeeper. Between those two steps run:

    tools/verify-macos-bundle.sh <bundle>

    It reports any load command naming an absolute path outside the bundle — a Homebrew libgit2 that macdeployqt did not copy in works on the machine that built it and on no other. The script is macOS-only and was written on Linux, so it has never been executed.

    See Third-party notices for what a redistributed build owes the libraries it carries.

    From Qt Creator¶

    CMakePresets.json is committed, so Qt Creator offers each preset as a build configuration — pick Debug, then install to ~/Applications and ⌘B builds and installs in one go.

    Qt Creator only imports presets when it has no configuration of its own, so on a project it has already opened, delete .qtcreator/CMakeLists.txt.user and reopen. That also discards which kit the project was using, so check the kit's Qt is still valid afterwards — a Homebrew upgrade moves the Cellar path, the kit is left with no Qt, and Qt Creator then passes an empty -DCMAKE_PREFIX_PATH= and nothing is findable.

    The robust answer is a gitignored CMakeUserPresets.json that inherits from the committed ones and pins Qt itself, because it does not depend on the kit being right:

    {
  "version": 3,
  "configurePresets": [
    {
      "name": "local-debug",
      "inherits": "debug",
      "cacheVariables": {
        "CMAKE_PREFIX_PATH": "/path/to/Qt/6.10.1/macos",
        "Qt6_DIR": "/path/to/Qt/6.10.1/macos/lib/cmake/Qt6"
      }
    }
  ],
  "buildPresets": [
    { "name": "local-debug-install", "configurePreset": "local-debug",
      "targets": ["all", "install"] }
  ]
}

    Qt6_DIR is set as well as CMAKE_PREFIX_PATH because Qt Creator puts its own (possibly empty) prefix path on the command line too; Qt6_DIR is something it never sets, so it cannot be overridden.

    A configure that fails this way leaves a cache with the empty path in it, so fix the path and delete the build directory — reconfiguring in place keeps failing.
