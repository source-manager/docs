    Releasing¶

    Two versions, and they answer different questions¶

    What it is What it answers
    The release 1.0.0, declared once in project(VERSION) What an installer upgrades from, what a licence is bought against, what to quote in a support request
    The build The full commit sha, stamped in per build Which code is running — what a bug report needs

    Neither is derived from the other, and each is wrong for the other's question. The sha cannot say which release somebody has: there is one per commit and most commits are not releases. The release number cannot identify the code: it is the same string for every build between two releases.

    Both are in About, and Copy details carries both.

    Why the release version is declared rather than described¶

    git describe is the obvious alternative and fails exactly where it matters: a release tarball, an export and a shallow CI clone carry no tags — and "unknown" is not a version a bundle or an MSI will install.

    So the number is committed and reviewed like any other source change. Its failure mode is drift from the tag, and that is what makes declaring it safe: a test asserts the two agree whenever HEAD carries a release tag, and skips otherwise, because between releases the declared version legitimately runs ahead of the last tag.

    It compares against the tag on HEAD and never a described one: that walks back to the nearest ancestor tag and would compare this build against a release two months old, which is the comparison that must not fail.

    One to three dot-separated integers, no suffix

    1.0.0-beta is valid semver and is rejected by Apple, Windows and MSI alike, so the test refuses it here rather than letting it surface at packaging time on a platform you may not be sitting at. A field above 65535 is silently truncated by the Windows resource compiler, so that is asserted too.

    To cut a release¶

    1. Bump project(VERSION).
    2. Commit.
    3. Tag that commit vX.Y.Z.

    In that order — the test compares the tag on HEAD against the declared number, so tagging first tags the bump that has not happened yet.

    And the build version is read per build, not per configure¶

    Three git calls made inline in a CMakeLists would answer once, when the build directory was configured, and go on answering that after every commit — a stamp that is silently a week old is exactly the failure a stamp exists to prevent, and it is invisible. So it runs from a custom target the library depends on.

    It costs nothing per build: the header is written through a compare, so an unchanged answer keeps its timestamp and nothing recompiles.

    Two facts travel with the sha because it misleads without them. The commit's date, since a hash cannot say how old it is and "does this build have the fix" is what a version is normally consulted for. And whether the tree was modified, because a build from an edited checkout is not that commit — the ordinary state of a working build directory, and the one a bug report must not silently claim otherwise about. Modified is a word beside the number rather than a -dirty suffix on it, because a suffix says the same thing quieter and makes the sha unpasteable into git show or a url.

    A source tree that is not a checkout is a state, not a blank: the row reads "not built from a checkout", and nothing is invented in its place.

    The Qt and libgit2 versions in About are the ones loaded, not the ones compiled against. They disagree exactly when it matters — two Qt installations, a distribution upgrade under an installed binary, an rpath pointing somewhere unexpected — and an About box is read when something is behaving oddly.

    The packaging versions are a different claim

    CFBundleVersion and its short-string sibling are still the release version, and the desktop entry's Version=1.0 is the Desktop Entry Specification's own version, which is what that key means in freedesktop's schema. A sweep that "fixed" it would declare this app conformant to a spec revision that does not exist.

    The release pipeline¶

    .github/workflows/release.yml runs on a v* tag. CI asks whether the tree works; this asks whether this thing is shippable, and the difference in failure cost is the whole reason it is a second file: a red CI run is a commit somebody fixes, and a bad release is on other people's machines.

    It fails before it builds¶

    A first job reads the declared version out of the root configuration and refuses a tag that disagrees, in fifteen seconds rather than after three platform builds. The test suite asserts the same thing, and both are worth having: the suite's copy is the one that cannot be forgotten, and this one is the one that answers before the money is spent.

    Release configuration, and the suite runs against it¶

    CI builds Debug on every push and has never once run the tests against an optimised build — a different program, with different timing, different inlining and different undefined behaviour, and the one people actually get. The release jobs run the suite after building Release.

    It also means the diagnostics are compiled out, so a shipped build carries no trace flag and cannot draw a panel of its own timings over somebody's window.

    Signing is skipped loudly or not at all¶

    A certificate belongs to whoever ships the app and nothing in this repository can hold one, so every signing step is conditional — and the condition is announced three times over: a warning in the log, a section in the job summary, and a sentence in the release notes beside the artifact it applies to.

    This project has been bitten twice by a guard that skipped in silence, and an unsigned release is that failure with the worst blast radius available: the reader finds out when Gatekeeper refuses to open it.

    Supply any of these as repository secrets to change that:

    Secret For
    MACOS_CERTIFICATE, MACOS_CERTIFICATE_PASSWORD, MACOS_SIGNING_IDENTITY Developer ID signing
    MACOS_NOTARY_APPLE_ID, MACOS_NOTARY_PASSWORD, MACOS_NOTARY_TEAM_ID Notarisation and stapling
    WINDOWS_CERTIFICATE, WINDOWS_CERTIFICATE_PASSWORD Authenticode signing

    Set SOURCEMANAGER_GITHUB_CLIENT_ID as a repository variable — not a secret, it is public by design — to ship a build that can sign in to GitHub through your own OAuth app.

    The obvious spelling of 'skip when there is no certificate' fails silently

    A step's own env: block is not in scope for that step's own if: — the condition is evaluated before the environment is applied — so if: env.X != '' naming a secret the step declares is always false and the step silently never runs. Which is to say the obvious spelling fails in exactly the way this file exists to prevent.

    The presence check is computed once at job level and the steps read that.

    The status files exist because the publish job must not guess¶

    Each build job writes whether it signed and whether it notarised beside its artifact, and the notes are composed from those rather than from whether a secret is configured.

    Those are different questions and they diverge the moment signing fails for any reason other than an absent certificate — at which point inferring from the secret prints a sentence that is confidently wrong on a page whose entire purpose is telling a reader what they are about to download. A missing status file is an error there and never a default.

    The notes are a script, not a block of YAML¶

    tools/release-notes.sh is the branchiest thing in the pipeline — signed and notarised, signed and not, neither, twice over for two platforms — and inline it would be logic whose first execution is a real release.

    Its test drives it across every combination and asserts the claims rather than the prose, since the wording is meant to be edited and a test pinning it would be deleted rather than read.

    The release is a draft¶

    Everything up to it is automation and the last step is a judgement: read the notes, check there are four artifacts, publish. A workflow that published outright would turn an accidental tag into a public release.

    workflow_dispatch runs the whole thing and publishes nothing, because a release pipeline whose first execution is a real release is one nobody has ever tested — and the publish job is gated on the tag rather than merely on the event, so a dry run cannot reach it by another door. Worth doing once before the first real tag.

    Three repositories, and what each holds¶

    source-manager/app is the source and is private. source-manager/dist is public and holds nothing but releases. source-manager/homebrew-tap is public and holds the cask.

    The split exists for one reason: a private repository's release assets answer 404 without a token, so nothing — not a browser, not brew — can fetch them. Publishing to dist makes the binaries downloadable without publishing a line of source.

    Crossing that boundary needs a token the workflow is not given. GITHUB_TOKEN is scoped to the repository it runs in and no permissions: block widens it, so RELEASE_TOKEN — a fine-grained PAT with contents: write on dist, homebrew-tap and apt — is the one required secret in the pipeline. It is checked by name in its own step, because every other secret here is optional and skipped loudly, and this one being absent means there is no release at all.

    The cask is bumped by a second workflow¶

    Homebrew cask (cask.yml) is a button pressed after the draft is published, and that ordering is the point rather than an inconvenience: a draft release's assets are not downloadable. A cask bumped in the same run as the draft is wrong for as long as the draft sits there, and the failure lands on whoever installs in that window as a 404 or a checksum error — neither of which says "the maintainer has not pressed publish yet".

    So the workflow proves the difference rather than assuming it. It fetches the .dmg the way a reader's brew will — anonymously, over the public URL — and stops if that does not answer. It digests what it downloaded rather than copying a line out of the SHA256SUMS.txt a different machine produced three jobs earlier, since the digest a cask carries has to describe the bytes a reader actually receives. The edit itself is tools/bump-cask.sh, which is tested (test_bumpcask) for the reason every other release script is: this is the only thing that runs it, and a cask whose version moved and whose digest did not tells a reader their download is corrupt.

    The artifacts¶

    macOS    SourceManager-<version>-macOS.dmg           self-contained
Windows  SourceManager-<version>-Windows-x64.zip     self-contained
Linux    source-manager_<version>-1_amd64.deb        needs Qt and libgit2
Linux    SourceManager-<version>-Linux-x86_64.tar.gz needs Qt and libgit2

    Two of them are built by scripts this pipeline does not own. tools/make-dmg.sh and tools/make-deb.sh are what the dmg and deb CMake targets run on somebody's own machine, and what ci.yml runs on every push — the .deb built, installed with apt and started, the disk image built unsigned and mounted. So by the time a tag reaches the release job, everything except the certificate has already been exercised. What is left here is the half that can live nowhere else: the signing identity, and the notarisation.

    Three things about the macOS job are load-bearing and were wrong first:

    • The install destination is a cache variable set at configure time, which is why the packaging script copies the bundle out of the build tree instead: installing would replace whatever is in the reader's ~/Applications when the same script is run on a person's own Mac.
    • macdeployqt rewrites load commands and therefore invalidates the ad-hoc signature, so the script re-signs before the bundle verifier runs — which checks the signature as its last step and would otherwise fail every run for a reason that is neither a fault nor the one it is looking for.
    • The disk image is what is notarised and stapled, rather than the app, so the ticket travels with the thing the reader downloads and Gatekeeper can check it offline on first launch.

    Neither Linux artifact is self-contained, and both say so wherever they appear. The .deb links the distribution's Qt and libgit2 and declares them, so apt resolves what it needs and refuses the package on a distribution that cannot satisfy it — a refusal from the package manager rather than an app that starts and fails. The tarball is the same tree without that metadata, for distributions that are not dpkg ones. An AppImage is what would make either self-contained and is deliberately not attempted: building one means third-party binaries downloaded at release time, and the first execution of that path would be a real release.

    The dependency list of the .deb is discovered for the half that can be discovered — dpkg-shlibdeps reads the binary's own load commands — and declared by hand for the half that cannot: a QML module is a plugin found by name at run time and appears in nothing. That declaration is packaging/deb/qml-modules, and test_debpackage fails on an import under qml/ that is missing from it, because the package it would otherwise produce installs cleanly, starts, and draws a blank panel.

    That job also builds on the older LTS where CI pins the newer image, and the reasons are opposite: there the newest Qt is wanted so the pipeline and the desk agree and the whole suite can run, here the oldest supported LTS is wanted so the binary starts on the widest range of machines. The cost is that its Qt predates waitForPolish, so the QML suites are excluded there by name — a shorter test list nobody notices is how a release comes to be built from an untested tree, and those suites have already run on the newer image on the commit being tagged.

    Releasing from your own Mac, without CI¶

    Nothing about the pipeline is load-bearing for publishing — gh release create against source-manager/dist is the whole of it, and every piece the workflow uses is a script in tools/ you can run yourself. The sequence is:

    cmake --build build --target dmg          # the disk image, on your Mac
cmake --build build --target deb          # the .deb, in a container, also on your Mac
./tools/changelog.sh v1.2.3 > changelog.md
./tools/checksums.sh <the artifacts> > SHA256SUMS.txt
./tools/release-notes.sh 1.2.3 macos-status.txt windows-status.txt changelog.md SHA256SUMS.txt > notes.md
gh release create v1.2.3 --repo source-manager/dist --target main --draft \
  --title "Source Manager 1.2.3" --notes-file notes.md <the artifacts> SHA256SUMS.txt
./tools/bump-cask.sh …/homebrew-tap/Casks/source-manager.rb 1.2.3 <the dmg's digest>

    What you give up by not using CI, in the order it will bite:

    • Windows. There is no way to produce that artifact on a Mac, and tools/release-notes.sh requires a Windows status file and prints the zip in its table regardless. A hand-made release is therefore macOS and Linux only, and the notes will name a download that is not attached unless you edit them. That is the one real obstacle: everything else on this list is a check you are choosing to skip, and this one publishes something untrue.
    • The tag check. release.yml refuses a tag that disagrees with project(VERSION) before it builds anything. By hand, the version in the filename, in the notes and in the cask are three strings you are typing.
    • The test run. The pipeline builds and tests in Release configuration, which no local workflow does; ci.yml is Debug.
    • The Linux build's distribution. The container gives you that back, provided you use the same base image the pipeline pins.

    So it is a fair thing to do for a build you are handing to a few people, and a poor way to cut a real release. The middle road is what the split already allows: let CI build and publish the draft, and use the local targets for the copies you hand over directly.

    The token is the same either way. gh needs to be authenticated against an account with write access to source-manager/dist, which for a hand-made release is just your own login; RELEASE_TOKEN exists because a workflow has no login of its own.

    What it does not do yet¶

    No AppImage, no Flatpak and no .rpm, so neither Linux artifact is self-contained and only Debian-family distributions get a package; and no Windows installer, only a zip of the deployed tree. Each is its own piece of work — see the job comments for why none was bolted on untested.

    There is also no .pkg on macOS. It would need a Developer ID Installer certificate, which is a different certificate from the Application one the pipeline handles, and what it buys over a drag-to-install disk image is the ability to run scripts at install time — which this app does not need.
