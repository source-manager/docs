    These docs¶

    The site is built with MkDocs and Material for MkDocs. The whole project is rooted at docs/: the config is docs/mkdocs.yml, its docs_dir is docs relative to that (so the pages are docs/docs/), and the pinned requirements are inside it.

    Building it locally¶

    pip install -r docs/docs/requirements.txt
mkdocs serve -f docs/mkdocs.yml

    mkdocs serve watches the tree and reloads, which is what you want while writing. mkdocs build -f docs/mkdocs.yml writes docs/site/ — gitignored, since it is generated. site_dir resolves against the config's own directory, so the output lands beside it whichever directory you invoke the build from.

    The dependencies are pinned, for the reason the CI runner images are: a floating version means the toolchain this site is built with changes without a commit saying so, and the first sign of it is a broken build on an unrelated pull request.

    The build is strict, and that is deliberate¶

    strict: true

    A broken internal link is a documentation bug, and the build should say so rather than shipping a 404 nobody notices. It fails on a link to a page that does not exist, a page absent from the navigation, and a reference to a file that is not there.

    The cost is that renaming a page breaks the build until every link to it is fixed, which is the point.

    What goes here, and what does not¶

    Here: what the app does, how it compares, what is coming, and how to build and test it. Written for somebody deciding whether to use it, or using it and wanting to know why something behaves the way it does.

    Not here: the architecture reference. AGENTS.md is that, it is the authority, and duplicating it would produce a second copy to go stale — which is this project's own argument about two spellings of one fact, applied to itself. Where a page needs to explain a mechanism it links there instead.

    So the architecture page is an orientation: the shape of the tree, the structural decisions that explain the rest, and pointers. If you find yourself transcribing a section of AGENTS.md into it, stop.

    Three conventions carried over from the app¶

    All three are what makes the rest of the site trustworthy, and each is easy to lose by writing a sentence that reads better without it.

    An unverified claim says so where it is made. Not once at the top and not in a footnote — Windows, GitLab, Bitbucket, X.509 signing, the keychain backends, the sparse verbs and every AI provider are implemented and unexercised to some degree, and every page that touches one repeats the caveat. A reader arrives at one page from a search engine and reads that page.

    A feature that is absent for a reason states the reason. An absence read as an oversight costs a reader nothing to work around and costs the project its credibility on everything else — so a declined feature says what it would cost and what would unblock it, and a non-goal says what position it is. That is why Closed as decisions and Deliberate non-goals are pages rather than a bullet list.

    A feature page says what it costs, on its first line. Every page under features/ opens with a **Licensing — …** line naming Free, Paid, or Free with paid parts, and naming the feature ids its controls carry — the same ids Licensing::catalogue() gates on, so a reader can match a control that is absent to the row that explains it. A new feature page without that line is the drift this convention exists to stop: a page that describes a paid control as though everybody has it is worse than no page, because the reader concludes the app is broken rather than that they have not paid.

    The tiers themselves are not restated per page beyond that line. The table in Licensing is written from the app's own catalogue, and a second copy of it in twenty-six places would be twenty-six things to forget when one word moves.

    Publishing¶

    .github/workflows/docs.yml builds on every push to main that touches docs/ or the workflow itself, and pushes the built site into a second repository, source-manager/docs, which serves it from its main branch at https://source-manager.github.io/docs/.

    Why two repositories¶

    GitHub Pages cannot be enabled on a private repository below GitHub Pro — it is a paid feature there, and free on a public one. This repository is private, so actions/deploy-pages answered 404 and no setting would have made it stop. The docs repository is public and holds only the build product: nothing is authored there, and anything committed there by hand is overwritten by the next run.

    Two things follow from the split, and neither is optional:

    • site_url is the published address, https://source-manager.github.io/docs/. It feeds the canonical links, the sitemap and the social-card metadata, so a wrong one is wrong in three places at once.
    • repo_url and edit_uri stay pointed here, because the "edit this page" link has to reach a file somebody can actually change.

    The rest of the decisions in it¶

    It builds on a pull request and publishes only from main. A pull request that breaks the strict build should fail there, where it can be fixed before merging — and a job that only ran after merging would report the breakage on somebody else's commit.

    Building and publishing are two jobs. The build runs pip and mkdocs; the publish job holds a credential that can write to another repository. Keeping them apart means the credential is never in scope for the step that runs third-party code, and the site travels between them as one tar through the artifact store.

    The publish is a real commit, and it deletes. The target's tree is replaced wholesale rather than added to, so a page renamed here stops serving at its old address there. A run whose build output is byte-identical to what is already published commits nothing.

    Concurrency is grouped and not cancelled in progress. Cancelling a publish half way is not the same kind of harmless as cancelling a superseded test run.

    It is a separate workflow rather than a job on CI. They answer different questions and hold different credentials: CI writes nothing, where this one can write to the docs repository. Adding that to a workflow that builds and runs code would widen what a compromised build step could reach.

    Setting it up, once¶

    Three things, and the workflow's failure names the first of them.

    1. Mint a key pair. It is never used to identify a person, so it is generated with no passphrase and no comment worth keeping:

    ssh-keygen -t ed25519 -N '' -C 'source-manager docs publish' -f /tmp/docs_deploy_key

    2. Install the public half on the docs repository. source-manager/docs → Settings → Deploy keys → Add deploy key. Title it something like source-manager docs publish, paste /tmp/docs_deploy_key.pub, and tick "Allow write access" — without it the push is refused and nothing else is wrong.

    3. Install the private half here. source-manager/app → Settings → Secrets and variables → Actions → New repository secret, named exactly DOCS_DEPLOY_KEY, holding the whole of /tmp/docs_deploy_key — the -----BEGIN OPENSSH PRIVATE KEY----- line, the body, the -----END----- line and the trailing newline. Then delete both files from disk.

    Or with the gh CLI, which does all three without the private half touching a browser:

    ssh-keygen -t ed25519 -N '' -C 'source-manager docs publish' -f /tmp/docs_deploy_key
gh repo deploy-key add /tmp/docs_deploy_key.pub \
  --repo source-manager/docs --title 'source-manager docs publish' --allow-write
gh secret set DOCS_DEPLOY_KEY --repo source-manager/app < /tmp/docs_deploy_key
rm -f /tmp/docs_deploy_key /tmp/docs_deploy_key.pub

    Why a deploy key rather than a personal access token. GITHUB_TOKEN cannot reach another repository at all, so something has to be stored, and a deploy key is the narrowest thing GitHub offers: it is registered on one repository, it cannot be widened by editing a scope list, and it does not expire. A fine-grained token with Contents: read and write on that repository would work and is worse on all three counts — it is minted against an account, it can be re-scoped afterwards, and it expires on a date nobody will remember.

    There is a second consequence of not using GITHUB_TOKEN, and it is load-bearing: a push made with that token does not start a workflow, and the Pages build on the far side is a workflow. A deploy key's push starts it.

    Enabling Pages on the docs repository, once¶

    source-manager/docs → Settings → Pages → Build and deployment → Source → Deploy from a branch, branch main, folder / (root).

    That is the other way round from what this repository used to do, and deliberately: the docs repository holds a finished site rather than a build, so there is nothing there for Actions to run. Until the first successful push there is no branch to select, so do this after the workflow has run once.

    A custom domain configured there writes a CNAME file into the branch. The publish step reads that file before it replaces the tree and puts it back afterwards, so the domain survives — but it is a decision made over there, and nothing in this repository declares it.
