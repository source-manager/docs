    Deliberate non-goals¶

    Positions this project has taken and written down. These are not backlog, and an agent or a contributor working through the outstanding list should leave them alone.

    Each is here because the absence would otherwise read as an oversight — which is the same reason the decisions are recorded rather than left silent.

    No "Undo everything" button¶

    The reflog records refs, not files. A commit that left a branch is still in the object database; an uncommitted edit that reset --hard wrote over was never in an object at all.

    A button that cannot tell those apart is at its most confident exactly when it is most wrong, because it is pressed at the moment the work was destroyed.

    What ships instead is a typed operations log that offers a way back only where one can be kept, and working-tree backups before the four writes that destroy content held in no git object — which makes some of those rows recoverable and says plainly when a row is not.

    No agentic AI¶

    Nothing edits files, runs commands, or takes more than one turn. Generation produces a draft a reader reviews before it is used.

    Every argument for that arrangement is an argument against the other one: an agent producing work nobody read is the failure the original refusal to generate anything was protecting against, restored at a larger scale.

    What would change it is not a better model. It is a way for a reader to review a sequence of edits as cheaply as they review a sentence — and this app's answer to that is Changes, which is where a patch applied by hand already lands.

    No streaming generated text¶

    A second shape on the transport, on the replay and on every surface that draws a partial answer, to save a moment on answers that are short and reviewed anyway.

    Non-git version control¶

    Subversion, Mercurial and the rest are not on a list of things to get to.

    Every controller here is written against libgit2's object model — a commit graph, an index with stages, a reflog, refs — and none of those is a shape the others share. Supporting one would not be a backend behind an existing seam but a second application in the same window, with its own answers for staging, for what a branch is, and for what an "undo" can honestly promise.

    The two things this project spends most of its care on — refusing rather than clobbering, and saying exactly what an operation did — are where that would go wrong first: a Subversion "revert" and this app's are not the same act, and a client that used one word for both would be doing the thing the whole documentation exists to prevent.

    git subtree is the one place a non-libgit2 mechanism is used at all, and it is shelled out to with its cost stated.

    In-repository distributed code review¶

    SmartGit ships this, as a separately licensed add-on: review state kept as objects or refs inside the repository, so a review travels with a clone and needs no server.

    It is a genuinely good idea and it is not this app's. Reviewing here goes through the forge's own API, because the review a team actually argues in is the one on their forge — and a second review store, visible only to people using this client, would be a place for comments to be written that nobody else can see or answer. That is worse than not offering it.

    What this app does instead is make the forge's own review readable and writable from here, with the band saying which of the three kinds of comment you are looking at.

    A branch picker that checks out¶

    The breadcrumb's picker narrows the history to a branch and moves nothing, and it says so in as many words. That is what clicking a branch has always meant here and people rely on it.

    Checking out lives on the Branches tab, where the row also tells you what the checkout would overwrite before you press it.

    Greying a control that cannot apply¶

    Absent, not greyed. A verb that does not apply to this repository is not drawn at all, which also takes it out of the palette and off the hint keys, since a control registers those on being enabled and visible.

    The cost is stated rather than hidden: it makes coverage read as thinner than it is on a repository where a verb does not apply, which is why several pages here say "the button is absent because…" rather than leaving you to wonder.

    There are four deliberate exceptions, each argued where it lives: the transport buttons grey while a transfer runs (the verb applies, it is busy); the fleet's Add control greys when the free cap is reached (a control that vanished would take the sentence explaining it with it); an AI control with no provider configured stays live so that pressing it can explain itself; and the confirm button inside a dialog is what disappears when the plan says no, rather than the button that opens the dialog.

    Arbitrary shell steps inside action sequences¶

    A step is one of this app's own verbs, so every refusal a sequence meets is a controller's own, in the words you would have seen pressing the button.

    Custom commands exist as a separate template rather than a widening of that rule: an argument list, never a shell.

    No --force on a tag, and no force for submodule deinit¶

    Both refusals name something to go and settle instead.

    A tag name pointed at a different commit is a different tag wearing an old one's clothes and nothing on disk records what it displaced — plain git tag declines for the same reason. And a forced submodule deinit would be the only route in this app to losing work that is nowhere else.

    No confirmation on per-hunk and per-line verbs¶

    A dialog per keystroke is a habit rather than a safeguard, and both land somewhere you can look at them and change your mind. The same trade revert already makes.

    What replaces it is refusing: a conflicted path, a selection with nothing undoable in it, and — through the apply itself — a file whose content has moved on since the diff was read. An empty patch applies cleanly and reports success for having done nothing, which is exactly how a destructive verb comes to be trusted.

    No PUT on the forge write list, and no mark-as-viewed row¶

    The three things a PUT would carry are the three ways of changing something somebody else made: rewriting the body of a review, dismissing one, and replacing the label set. The audit asserts each is refused.

    Mark-as-viewed would have been a fourth and is GraphQL-only. The argument that used to keep it out — that no GraphQL URL may be on the list — has expired rather than been answered, since the review being written needed that row. So it is now simply unimplemented, which is a smaller and more honest thing to say.

    No fully-merged claim the commit graph cannot support¶

    Nothing here is called "fully merged", because a reachability test cannot catch a squash or a rebase merge. The wording says what was checked, and the forge's answer is drawn beside it where there is one.
