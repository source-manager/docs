    Closed as decisions¶

    Five things that look like gaps in the comparison and are not. Each says what it would cost and what would unblock it, because a decision is a deliverable here and an entry left implying work nobody has thought about is not.

    An embedded terminal¶

    GitKraken, Sublime Merge (its git console) and Lazygit have one.

    The argument the external merge tool is offered on applies here with more force: the reader already has a terminal, and it is theirs — their shell, their prompt, their profile, their multiplexer, their keybindings, fifteen years of muscle memory. A pane here would be a second, worse terminal that has to be configured separately.

    What it would cost is three problems rather than a widget:

    1. A pty, which is forkpty() on Linux and macOS and CreatePseudoConsole on Windows — two unrelated APIs, and the Windows half would be unrunnable code in a port whose own record says nothing about it has ever been executed.
    2. A terminal emulator. A pty hands over a byte stream of escape sequences: cursor addressing, scroll regions, the alternate screen, SGR, character sets, mouse reporting, bracketed paste. That is what libvterm and QTermWidget exist for, so it is a new hard dependency — and the rule the keychain was settled under is that a dependency is settled before anything is written and a platform-only implementation is worse than none. QTermWidget is a widgets library besides, so it does not compose with this window even if the dependency were taken.
    3. The suite could not say whether it worked. Every assertion that matters — does a prompt render, does resizing reflow, does ⌃C reach the child — is a question about the emulator, offscreen, in a headless runner.

    That last one decides it. A pane that draws something terminal-shaped and is not a terminal is the one outcome worse than the absence, and it is the outcome a feature nothing can test converges on.

    What exists instead: an external terminal template that opens yours, in this repository's directory.

    A Windows Explorer shell extension¶

    TortoiseGit's whole point, and Git Extensions has one.

    Status overlays in the file manager are the headline Windows integration every competitor ships, and it is refused on four grounds rather than deferred:

    1. It cannot share a line of this codebase. An overlay handler is an in-process COM server loaded into explorer.exe, so it must not link Qt — wrong process, wrong threading model, and a crash takes the shell down with it. It would need its own libgit2, or its own IPC to a service, which is a second application with a second answer to "what is this file's status".
    2. The overlay slots are capped at fifteen, system-wide, handed out alphabetically by registry key. That is why every product that ships one prefixes its key with spaces to win the race, and why a new entrant on a machine that already has a cloud drive realistically gets none. A feature whose visibility depends on beating other vendors in a sort is not one to build on the strength of it compiling.
    3. CI could prove it compiles, and that is the wrong bar. The SDK headers are on the runner, so a job could build and link a COM DLL — and nothing on a runner can register one (elevation), load one (no Explorer, no session) or exercise a single thing it does. A component that compiles and has never run is precisely the silent-skip guard this project has a position on, and committing one blind would read as done.
    4. The port it is meant to follow has not landed in any verified sense. What is known about Windows is that the tree builds and the suite passes headless, and an integration with the shell is the furthest thing from that from being answerable.

    What would unblock it: a Windows machine somebody actually uses this app on — not to write the COM, which is well-documented, but to answer whether the overlays appear at all on a real desktop, and whether a status-per-directory cache can answer inside Explorer's own budget.

    What exists instead: "Show in File Explorer", which needs no DLL, no registry and no elevation.

    Partial clone¶

    SmartGit and Git Extensions offer it.

    libgit2 has no promisor support, so a --filter=blob:none clone — reachable by shelling out — would produce a checkout this app cannot read: a partial clone records a promisor remote and leaves most blobs absent, expecting whoever opens the repository to fetch each one on demand. Every blob lookup would fail with a not-found the moment a diff, a blame or a checkout asked for one.

    A tick producing a repository the app then could not open is worse than no tick, which is the absent-not-greyed rule applied to a capability rather than to a control.

    It is named on the clone dialog rather than silently absent, whatever else is chosen, because it is a fact about this build and not about anything on the form.

    Shallow clone is offered, with what it gives up named beside it. See Remotes and transport.

    LFS state on the fleet¶

    The answer asked for — "this checkout has objects it never fetched" — costs a file read per managed path, per repository, across every repository in the fleet. That is exactly the cost the fleet page is designed to refuse, and it is why the fleet is outside the app's general refresh in the first place.

    The tempting substitute is worse than the absence: a root .gitattributes naming filter=lfs is cheap, and it answers "this project uses LFS" — which is not the question. Drawn as a badge on a card it would be read as "something here needs fetching", which is true of a checkout that has never fetched and false of every properly checked-out one, with no way to tell from the card which kind you are looking at. A badge that is right by coincidence on some cards is worse than no badge.

    What exists instead: the figure on Manage's LFS tab, where one repository has been asked about and the walk is affordable.

    Auto-resolving "mechanical" conflicts¶

    GitKraken does it.

    It requires trusting a classifier about which conflicts are mechanical, and the failure mode is silent by construction: a conflict resolved without being shown is one nobody reads, so a classifier that is wrong one time in fifty produces a commit nobody can tell from the other forty-nine.

    Everything else in this app that writes says what it is about to do first, and this is the one verb where the whole point would be not saying.

    What would change it: a mechanism for showing afterwards what was decided without asking — an operation-log row per hunk with the two sides in it. At which point the reader is reading the hunks anyway, which the whole-file suggestion verb already offers.

    Virtual branches¶

    GitButler's whole thesis.

    Stacked branches landed. GitButler's virtual-branch model — several branches applied to one working directory, each change assigned to a lane, committed independently — is a different thesis about what a working tree is, not a missing verb.

    It is worth noting that this app's line-level staging would be an unusually good substrate for one: it already assigns individual lines to an outcome and reconstructs patches to apply them. The hard parts are conflicting lanes and unapplying one, and both need answering on paper first.

    Repository tabs¶

    Recorded as the shape that could not have delivered what was asked for.

    One set of controllers holds one repository path, so a tab strip over one of them is a visible drawing of the ⌃Tab list: pressing a tab swaps the repository underneath every surface, which is what the switcher already does with no chrome at all.

    Two repositories side by side needs two sets of controllers, which is a second window — and that is what shipped.
